### Step 1. 컨테이너 오케스트레이션 개요 — 왜 K8s인가

| 학습 항목 | 학습 목표 |
|----------|----------|
| 컨테이너 오케스트레이션이란 | 여러 컨테이너의 배포, 확장, 네트워킹, 장애 복구를 자동 관리하는 시스템. Docker Compose로는 단일 호스트만 관리 가능한 한계를 설명 가능. |
| 왜 K8s인가 | 자동 스케일링, 자가 치유(Self-healing: Pod 죽으면 자동 재시작), 롤링 업데이트, 서비스 디스커버리, 선언적 배포(desired state). Google 내부 시스템(Borg) 기반의 사실상 표준. |
| K8s가 해결하는 문제 | "서버 10대에 컨테이너 50개를 어떻게 배치하고, 장애 나면 어떻게 복구하고, 트래픽 늘면 어떻게 확장하는가?"에 대한 자동화된 답을 설명 가능. |
| Docker Compose vs K8s | Compose: 단일 호스트, 개발/테스트 용도. K8s: 다중 호스트(클러스터), 프로덕션 운영. 선택 기준을 설명 가능. |
| K8s 대안 | Docker Swarm(단순하지만 기능 제한), AWS ECS(AWS 종속), Nomad(HashiCorp)의 존재를 알고 있음. K8s가 사실상 표준인 이유를 설명 가능. |

### Step 2. K8s 아키텍처 — Control Plane, Node, 핵심 컴포넌트

| 학습 항목 | 학습 목표 |
|----------|----------|
| 클러스터 구조 | Control Plane(마스터) + Worker Node(워커)의 전체 구조를 그림으로 그릴 수 있음. |
| Control Plane 컴포넌트 | **kube-apiserver**(모든 요청의 진입점, REST API), **etcd**(클러스터 상태 저장소, 키-값 DB), **kube-scheduler**(Pod를 어떤 Node에 배치할지 결정), **kube-controller-manager**(ReplicaSet, Deployment 등 컨트롤러 실행). 각각의 역할을 설명 가능. |
| Worker Node 컴포넌트 | **kubelet**(Pod 생명주기 관리, 컨테이너 런타임과 통신), **kube-proxy**(네트워크 규칙, Service → Pod 라우팅), **Container Runtime**(containerd/CRI-O, 실제 컨테이너 실행). 각각의 역할을 설명 가능. |
| 선언적 모델 (Declarative) | "Pod 3개를 실행해라"(명령형)가 아니라 "Pod 3개가 실행 중이어야 한다"(선언형)를 YAML로 선언. K8s가 현재 상태를 원하는 상태(Desired State)로 맞추는 Reconciliation Loop를 설명 가능. |
| kubectl | K8s CLI 도구. 모든 K8s 조작의 기본. kube-apiserver와 통신하는 클라이언트. |

### Step 3. K8s 환경 구축 — Minikube/Kind, kubectl 기본

| 학습 항목 | 학습 목표 |
|----------|----------|
| 로컬 K8s 환경 | Minikube(단일 노드 클러스터) 또는 Kind(Docker 위에 K8s 클러스터)를 로컬에서 기동 가능. |
| kubectl 기본 명령어 | kubectl get (pods/deployments/services), kubectl describe, kubectl logs, kubectl exec, kubectl apply -f, kubectl delete 사용 가능. |
| YAML 매니페스트 기본 | apiVersion, kind, metadata(name, labels), spec 구조를 이해하고 기본 YAML을 읽을 수 있음. |
| kubectl 컨텍스트 | 여러 클러스터를 kubectl config로 전환하는 방법. kubeconfig 파일의 역할을 알고 있음. |
| 첫 배포 실습 | nginx Pod를 YAML로 작성 → kubectl apply → kubectl get pods → kubectl logs로 확인하는 전체 흐름을 직접 실행 가능. |
| 로컬 개발 워크플로 도구 (심화) | "코드 수정 → Docker 빌드 → K8s 배포" 반복이 느린 문제를 해결하는 도구: **Skaffold**(코드 변경 감지 → 자동 빌드 → 자동 배포), **Telepresence**(로컬 프로세스를 원격 K8s 클러스터에 연결하여 로컬에서 디버깅). 존재와 용도를 개념 수준 알고 있음. K8s 환경 개발 생산성을 고민하는 팀 리더 관점을 설명 가능. |

### Step 4. Pod — 가장 작은 배포 단위

| 학습 항목 | 학습 목표 |
|----------|----------|
| Pod란 | K8s에서 가장 작은 배포 단위. 1개 이상의 컨테이너를 포함. 같은 Pod의 컨테이너끼리 네트워크(localhost)와 스토리지를 공유하는 이유를 설명 가능. |
| 1 Pod = 1 컨테이너 (일반적) | 대부분의 경우 Pod에 메인 컨테이너 1개만. 멀티 컨테이너는 사이드카 패턴(로그 수집, 프록시 등)에서 사용하는 이유를 설명 가능. |
| Pod 생명주기 | Pending → Running → Succeeded/Failed. 각 상태의 의미와 전이 조건을 설명 가능. |
| Pod를 직접 만들지 않는 이유 | Pod는 일회성. 죽으면 다시 안 살아남. Deployment/ReplicaSet이 원하는 수의 Pod를 유지하는 역할. "Pod는 가축(Cattle)이지 애완동물(Pet)이 아니다"를 설명 가능. |
| 사이드카 패턴 | 메인 컨테이너 옆에 보조 컨테이너(로그 수집, 모니터링 에이전트, Envoy 프록시 등)를 함께 배치하는 패턴을 설명 가능. |
| Service Mesh 개념 (심화) | 사이드카 프록시(Envoy 등)가 모든 Pod에 자동 주입되어 서비스 간 트래픽을 가로채는(Intercept) 원리를 설명 가능. iptables 규칙으로 Pod의 인바운드/아웃바운드 트래픽을 사이드카로 리다이렉트하는 메커니즘을 개념 수준 설명 가능. 이를 통해 앱 코드 수정 없이 트래픽 관리(라우팅, 재시도, 서킷 브레이커), 보안(mTLS), 관찰성(메트릭, 트레이스)을 인프라 레벨에서 제공. Istio, Linkerd의 존재와 차이를 개념 수준 알고 있음. MSA 학습과 연계. |
| Init Container | Pod 메인 컨테이너 시작 전에 실행되는 초기화 컨테이너. DB 마이그레이션, 설정 파일 생성 등에 활용. |

### Step 5. ReplicaSet + Deployment — 배포와 롤링 업데이트

| 학습 항목 | 학습 목표 |
|----------|----------|
| ReplicaSet | 지정한 수(replicas)의 Pod를 항상 유지하는 컨트롤러. Pod가 죽으면 자동으로 새 Pod를 생성하는 자가 치유(Self-healing)를 설명 가능. |
| Deployment | ReplicaSet을 관리하는 상위 리소스. 롤링 업데이트, 롤백을 지원. 실무에서 Pod/ReplicaSet을 직접 만들지 않고 Deployment를 사용하는 이유를 설명 가능. |
| Deployment YAML | metadata(name), spec(replicas, selector, template)의 구조를 작성 가능. |
| 롤링 업데이트 | 새 버전 Pod를 하나씩 생성하면서 구 버전을 하나씩 종료. maxSurge(최대 추가 Pod 수), maxUnavailable(최대 중단 Pod 수) 설정의 의미를 설명 가능. |
| 롤백 | kubectl rollout undo로 이전 버전으로 롤백. kubectl rollout history로 배포 이력 확인. 롤백이 가능한 이유(이전 ReplicaSet을 보존)를 설명 가능. |
| kubectl scale | kubectl scale deployment --replicas=N으로 수동 스케일링 가능. |
| Graceful Shutdown (심화) | K8s가 Pod를 종료할 때: ① Service에서 제거(트래픽 차단) → ② SIGTERM 전송 → ③ terminationGracePeriodSeconds(기본 30초) 대기 → ④ SIGKILL 강제 종료. 이 순서를 설명 가능. Spring Boot의 server.shutdown=graceful 설정으로 처리 중인 요청을 완료 후 종료하는 패턴을 설명 가능. terminationGracePeriodSeconds와 Spring Boot의 spring.lifecycle.timeout-per-shutdown-phase의 관계(K8s 타임아웃 ≥ Spring 타임아웃이어야 함)를 설명 가능. preStop 훅으로 Service 제거와 앱 종료 사이 타이밍을 맞추는 패턴(sleep 5 등)을 설명 가능. |

### Step 6. Service — ClusterIP, NodePort, LoadBalancer

| 학습 항목 | 학습 목표 |
|----------|----------|
| Service란 | Pod 집합에 대한 안정적인 네트워크 엔드포인트. Pod IP는 변하지만(재시작 시) Service IP/DNS는 고정. 서비스 디스커버리의 역할을 설명 가능. |
| Label과 Selector | Service가 어떤 Pod에 트래픽을 보낼지 Label Selector로 결정하는 메커니즘. Pod에 label(app: my-app) → Service의 selector(app: my-app)로 매칭. |
| ClusterIP (기본) | 클러스터 내부에서만 접근 가능한 가상 IP. 내부 서비스 간 통신에 사용. |
| NodePort | 각 Node의 특정 포트(30000~32767)로 외부 접근 가능. 개발/테스트에 적합. 프로덕션에서는 비권장인 이유(포트 제한, 보안)를 설명 가능. |
| LoadBalancer | 클라우드 프로바이더(AWS ELB, GCP LB)의 외부 로드밸런서를 자동 프로비저닝. 프로덕션 외부 접근의 표준. |
| Service DNS | 같은 Namespace에서 서비스명(my-service)으로, 다른 Namespace에서 my-service.namespace.svc.cluster.local로 접근하는 DNS 기반 디스커버리를 설명 가능. |

### Step 7. Ingress — HTTP 라우팅, 도메인 기반 접근

| 학습 항목 | 학습 목표 |
|----------|----------|
| Ingress란 | HTTP/HTTPS 트래픽을 클러스터 내부 Service로 라우팅하는 규칙. 도메인 기반(api.example.com → API Service), 경로 기반(/api → API, /web → Web)의 라우팅을 설명 가능. |
| Ingress Controller | Ingress 규칙을 실행하는 실제 구현체. Nginx Ingress Controller, AWS ALB Ingress Controller 등. Ingress 리소스만 만들면 안 되고 Controller가 설치되어 있어야 동작하는 이유를 설명 가능. |
| Ingress YAML | host, path, backend(service name, port) 설정을 작성 가능. |
| TLS 설정 | Ingress에 TLS 인증서를 설정하여 HTTPS를 제공하는 방법을 알고 있음. cert-manager의 존재를 알고 있음. |
| Ingress vs LoadBalancer Service | Service LoadBalancer는 서비스마다 LB 1개(비용 높음). Ingress는 LB 1개로 여러 서비스 라우팅(비용 절약). 선택 기준을 설명 가능. |

### Step 8. ConfigMap + Secret — 설정과 시크릿 분리

| 학습 항목 | 학습 목표 |
|----------|----------|
| ConfigMap | 설정 데이터를 키-값으로 저장. 환경 변수, 설정 파일로 Pod에 주입. 이미지에 설정을 하드코딩하지 않는 이유(환경별 설정 분리)를 설명 가능. |
| Secret | 민감 정보(비밀번호, 토큰, 인증서)를 Base64 인코딩으로 저장. ConfigMap과의 차이(Secret은 메모리에만 저장, 접근 제한 가능)를 설명 가능. Base64는 암호화가 아님을 알고 있음. |
| Pod에 주입하는 방법 | 환경 변수(envFrom, valueFrom), 볼륨 마운트(파일로 주입) 두 가지 방법을 적용 가능. |
| 설정 변경 시 Pod 반영 | ConfigMap 변경 시 자동 반영 안 됨(Pod 재시작 필요). 볼륨 마운트 방식은 일부 자동 갱신됨. 이 차이를 설명 가능. |
| Spring Boot 연동 | application.yml을 ConfigMap으로 관리하고, DB 비밀번호를 Secret으로 관리하는 패턴을 설명 가능. |

### Step 9. Volume + PersistentVolume + PVC — 데이터 영속성

| 학습 항목 | 학습 목표 |
|----------|----------|
| 컨테이너 스토리지의 문제 | 컨테이너 파일시스템은 일시적(Ephemeral). 컨테이너 재시작 시 데이터 사라짐. DB, 파일 저장에 영속 스토리지가 필요한 이유를 설명 가능. |
| Volume | Pod 수준의 스토리지. emptyDir(Pod 생명주기 공유), hostPath(노드 디스크)의 차이를 설명 가능. |
| PersistentVolume (PV) | 클러스터 관리자가 미리 프로비저닝한 스토리지 자원. Pod와 독립적인 생명주기. |
| PersistentVolumeClaim (PVC) | 사용자가 PV를 요청하는 방법. "10Gi ReadWriteOnce 스토리지를 달라"고 Claim하면 K8s가 적합한 PV를 바인딩. |
| StorageClass | 동적 프로비저닝. PVC 생성 시 StorageClass에 따라 PV를 자동 생성. 클라우드(AWS EBS, GCP PD)와 연동하는 구조를 설명 가능. |
| StatefulSet (개념) | DB처럼 안정적인 네트워크 ID + 영속 스토리지가 필요한 워크로드에 사용. Deployment와의 차이를 개념 수준 설명 가능. |

### Step 10. Namespace — 환경 분리

| 학습 항목 | 학습 목표 |
|----------|----------|
| Namespace란 | 클러스터 내 논리적 분리 단위. dev, staging, prod 환경을 같은 클러스터에서 격리하는 방법을 설명 가능. |
| 기본 Namespace | default, kube-system(K8s 시스템 컴포넌트), kube-public, kube-node-lease의 역할을 알고 있음. |
| ResourceQuota | Namespace별 리소스 상한(CPU, 메모리, Pod 수)을 설정하여 한 팀이 클러스터 자원을 독점하는 것을 방지. |
| kubectl -n | kubectl get pods -n staging처럼 Namespace를 지정하여 조회하는 방법. |
| RBAC 기초 (심화) | **ServiceAccount**(Pod가 K8s API에 접근할 때 사용하는 신원), **Role**(특정 Namespace 내 리소스에 대한 권한 정의), **RoleBinding**(ServiceAccount와 Role을 연결)의 관계를 설명 가능. ClusterRole/ClusterRoleBinding(클러스터 전체 범위)과의 차이를 설명 가능. "이 Pod가 다른 Pod 목록을 조회하려면 어떤 RBAC 설정이 필요한가?"에 답변 가능. 엔터프라이즈 환경에서 최소 권한 원칙(Least Privilege)이 중요한 이유를 설명 가능. |

### Step 11. Resource Limits + Requests — CPU/메모리 관리

| 학습 항목 | 학습 목표 |
|----------|----------|
| Requests | Pod가 보장받는 최소 리소스. 스케줄러가 Node에 Pod를 배치할 때 Requests를 기준으로 판단. |
| Limits | Pod가 사용 가능한 최대 리소스. CPU Limit 초과 시 쓰로틀링(속도 제한), 메모리 Limit 초과 시 OOMKilled(강제 종료). |
| Requests vs Limits 설정 전략 | Requests = 평균 사용량, Limits = 최대 사용량으로 설정하는 일반적 전략. Requests 없이 Limits만 설정하면 안 되는 이유를 설명 가능. |
| QoS 클래스 | Guaranteed(Requests = Limits), Burstable(Requests < Limits), BestEffort(설정 없음). OOM 시 BestEffort가 먼저 죽는 이유를 설명 가능. |
| Java 앱의 리소스 설정 | JVM 힙(-XX:MaxRAMPercentage) + 컨테이너 메모리 Limit의 관계. Limit보다 힙이 크면 OOMKilled 발생하는 이유를 설명 가능. (Docker 학습 Step 7과 연계) |

---

### Step 12. Probe — Liveness, Readiness, Startup

| 학습 항목 | 학습 목표 |
|----------|----------|
| Liveness Probe | "컨테이너가 살아있는가?" 실패 시 컨테이너 재시작. 데드락 등 응답 불가 상태를 감지하는 용도를 설명 가능. |
| Readiness Probe | "트래픽을 받을 준비가 되었는가?" 실패 시 Service에서 제외(트래픽 안 보냄). 기동 중이거나 일시적 과부하 시 트래픽을 차단하는 용도를 설명 가능. |
| Startup Probe | "초기 기동이 완료되었는가?" 기동이 오래 걸리는 앱(Spring Boot 등)에서 Liveness가 기동 중에 컨테이너를 죽이는 문제를 방지. |
| Probe 방식 | HTTP GET(엔드포인트 호출), TCP Socket(포트 연결 확인), exec(명령 실행). Spring Boot Actuator /actuator/health와 연동하는 패턴을 설명 가능. |
| 설정 파라미터 | initialDelaySeconds, periodSeconds, timeoutSeconds, failureThreshold의 의미와 적절한 값 설정 기준을 설명 가능. |
| 잘못된 Probe 설정의 위험 | Liveness가 너무 민감 → 정상 Pod 반복 재시작. Readiness 없음 → 기동 중인 Pod에 트래픽 유입 → 에러. 실무 사례를 설명 가능. |

---

### Step 13. HPA (Horizontal Pod Autoscaler) — 오토 스케일링

| 학습 항목 | 학습 목표 |
|----------|----------|
| HPA란 | CPU/메모리 사용률 또는 커스텀 메트릭에 따라 Pod 수를 자동으로 늘리거나 줄이는 컨트롤러. |
| HPA 동작 원리 | Metrics Server에서 현재 메트릭 수집 → 목표 사용률과 비교 → Pod 수 조정. 조정 공식(원하는 Pod 수 = 현재 Pod 수 × 현재 메트릭 / 목표 메트릭)을 설명 가능. |
| HPA YAML | minReplicas, maxReplicas, targetCPUUtilizationPercentage 설정을 작성 가능. |
| Metrics Server | Pod의 CPU/메모리 사용량을 수집하는 클러스터 컴포넌트. HPA가 동작하려면 Metrics Server가 필수. |
| 커스텀 메트릭 HPA | CPU/메모리 외에 Prometheus 메트릭(요청 수, 큐 깊이 등)으로 스케일링하는 구조를 개념 수준 설명 가능. |
| VPA (Vertical Pod Autoscaler) 개념 | Pod 수가 아닌 Pod의 리소스(CPU/메모리)를 자동 조정하는 VPA의 존재를 알고 있음. HPA와의 차이를 설명 가능. |

---

### Step 14. Helm — 패키지 관리, Chart 작성

| 학습 항목 | 학습 목표 |
|----------|----------|
| Helm이란 | K8s 매니페스트의 패키지 매니저. "K8s의 apt/yum". 여러 YAML 파일을 하나의 Chart로 묶어 관리하는 이유를 설명 가능. |
| Helm이 없으면 | Deployment + Service + ConfigMap + Ingress + HPA 등 여러 YAML을 각각 kubectl apply해야 하는 불편함. 환경별(dev/prod) 값만 다른데 YAML을 복사하는 문제를 설명 가능. |
| Chart 구조 | Chart.yaml(메타정보), values.yaml(변수), templates/(YAML 템플릿) 구조를 설명 가능. |
| 템플릿과 Values | `{{ .Values.replicaCount }}` 같은 Go 템플릿으로 환경별 값을 주입하는 원리를 설명 가능. |
| Helm 명령어 | helm install, helm upgrade, helm rollback, helm uninstall, helm list 사용 가능. |
| 공개 Chart 활용 | Bitnami 등 공개 Chart 저장소에서 PostgreSQL, Redis, Kafka 등을 helm install로 간편 배포하는 방법을 알고 있음. |
| Helm vs Kustomize 심화 | Helm: Go 템플릿 기반, 변수 주입, Chart 패키지 배포, 공개 Chart 생태계. 강력하지만 템플릿 복잡도 높음. Kustomize: kubectl 내장, 베이스 YAML + 환경별 패치(overlay), 템플릿 없이 순수 YAML 유지. 단순하지만 고급 로직 표현 제한. **선택 기준**: 공개 Chart 활용/복잡한 조건 분기 → Helm, 팀 내부 매니페스트 관리/단순 환경별 차이 → Kustomize, 조합(Helm으로 설치 + Kustomize로 커스터마이징)도 가능. "Helm이 오버엔지니어링이 되는 경우"(간단한 YAML 몇 개를 굳이 Chart로 감쌀 필요 없음)를 판단 가능. |

### Step 15. K8s 배포 전략 — Rolling Update, Recreate, Blue-Green, Canary

| 학습 항목 | 학습 목표 |
|----------|----------|
| Rolling Update (기본) | Deployment 기본 전략. 새 Pod 생성 → 구 Pod 종료를 점진적으로. 무중단 배포. maxSurge/maxUnavailable 설정 영향을 설명 가능. |
| Recreate | 모든 구 Pod 종료 → 새 Pod 생성. 다운타임 발생. DB 스키마 변경 등 구/신 버전 공존 불가 시 사용. |
| Blue-Green | 구 버전(Blue)과 신 버전(Green)을 동시 운영 후 Service의 Selector를 전환. 즉시 롤백 가능(Selector 복원). K8s에서 2개 Deployment + Service Selector 전환으로 구현하는 방법을 설명 가능. |
| Canary | 신 버전을 소수 Pod(예: 10%)에만 배포 → 모니터링 → 문제 없으면 점진 확대. K8s에서 2개 Deployment(replicas 비율 조정) 또는 Istio로 구현하는 방법을 개념 수준 설명 가능. |
| 배포 전략 선택 기준 | 무중단 필수 → Rolling/Blue-Green/Canary, 리스크 최소화 → Canary, 즉시 롤백 → Blue-Green, 비용 최소 → Rolling. 비즈니스 요구에 맞게 판단 가능. |

---

### Step 16. K8s 트러블슈팅 — Pod 상태 진단, 로그, 이벤트

| 학습 항목 | 학습 목표 |
|----------|----------|
| Pod 상태 확인 | kubectl get pods에서 Pending, Running, CrashLoopBackOff, ImagePullBackOff, OOMKilled 등 상태의 의미를 설명 가능. |
| CrashLoopBackOff | 컨테이너가 시작 → 즉시 종료 → 재시작 반복. 원인(앱 에러, 설정 오류, 리소스 부족) 진단 순서(kubectl logs → kubectl describe → 이벤트 확인)를 설명 가능. |
| ImagePullBackOff | 이미지를 가져올 수 없음. 원인(이미지명 오타, 레지스트리 인증 실패, 네트워크 문제) 진단 가능. |
| OOMKilled | 메모리 Limit 초과로 강제 종료. 원인(JVM 힙 설정 미스매치, 메모리 누수) 진단 가능. |
| kubectl describe pod | Events 섹션에서 스케줄링, 이미지 Pull, Probe 실패 등 상세 이벤트를 확인하는 방법. |
| kubectl logs | 컨테이너 로그 확인. -f(실시간), --previous(이전 컨테이너, CrashLoop 시 유용) 옵션을 사용 가능. |
| 진단 순서 | "Pod가 안 뜬다" → kubectl get pods(상태 확인) → kubectl describe pod(이벤트 확인) → kubectl logs(앱 로그 확인) → 리소스/설정/이미지 확인 순서를 설명 가능. |
