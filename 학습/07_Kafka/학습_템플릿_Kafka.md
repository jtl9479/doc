# Kafka 학습 템플릿

> 유형: **개념 + 설정/코드 + 아키텍처 다이어그램**
> 적용: 학습_07_Kafka.md의 Step 1~16

## 공통 원칙

| 원칙 | 설명 |
|------|------|
| **왜 먼저** | "동기 호출만 쓰면 이런 문제. Kafka를 쓰면 이렇게 해결" |
| **비유 먼저** | 메시징/이벤트 개념을 일상 비유로 직관 잡기 |
| **트레이드오프** | 모든 설정(acks, 커밋 전략 등)에 "얻는 것 vs 잃는 것" 명시 |
| **버전 차이** | ZooKeeper→KRaft 전환, Kafka 2.x→3.x 차이 언급 |

### 비유 예시
```
Kafka = "우체국 사서함 시스템. 보내는 사람(Producer)이 사서함(Topic)에 편지를 넣으면, 받는 사람(Consumer)이 자기 속도로 꺼내감. 편지는 사라지지 않음(보존)"
Partition = "우체국 창구. 창구가 3개면 3명이 동시에 우편물 처리(병렬)"
Consumer Group = "팀별 사서함 공유. 마케팅팀은 1팀이 나눠서 처리, 영업팀은 별도로 같은 편지를 따로 받음"
Offset = "책갈피. 내가 어디까지 읽었는지 표시"
acks=all = "등기 우편. 상대방이 받았다는 확인까지 기다림(안전하지만 느림)"
acks=0 = "일반 우편. 보내고 끝(빠르지만 분실 가능)"
Rebalancing = "팀원 퇴사/입사 시 업무 재분배. 재분배 중에는 전체 업무 일시 중단"
```

### 트레이드오프 예시
```
acks=all: 데이터 안전↑ ↔ 지연시간↑ 처리량↓
acks=1: 적당한 균형 ↔ Leader 장애 시 유실 가능
자동 커밋: 간편 ↔ 처리 전 커밋 → 데이터 유실 가능
수동 커밋: 정확 ↔ 코드 복잡, 커밋 실패 시 재처리
Exactly-Once: 정합성 완벽 ↔ 성능 오버헤드, 설정 복잡
파티션 수↑: 병렬 처리↑ ↔ 브로커 부하↑, 리밸런싱 비용↑
```

## 설명 흐름
1. **왜 써야 하는가**: "이걸 안 쓰면 / 이 설정을 모르면 이런 장애"
2. **비유로 직관 잡기**
3. **아키텍처 다이어그램** (텍스트)
4. **핵심 개념 + 설정값 + 트레이드오프**
5. **코드 예제** (Spring Kafka / CLI)
6. **장애 시나리오**: "이러면 어떻게 되는가?"
7. **오해하기 쉬운 부분 + 버전 차이**:
```
"Kafka는 메시지 큐다" → 큐가 아니라 이벤트 로그. 소비해도 안 사라짐
"파티션을 많이 만들면 무조건 좋다" → 브로커 부하↑ 리밸런싱 비용↑. 줄일 수도 없음
"Exactly-Once가 기본이다" → 기본은 At-Least-Once. EOS는 별도 설정 + 성능 비용
"Consumer Group이 많으면 성능 저하" → 아님. 각 그룹이 독립적으로 오프셋 관리
ZooKeeper → KRaft: Kafka 3.x+에서 ZooKeeper 없이 자체 합의로 전환 중
```
