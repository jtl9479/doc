## 1. 개요

**현재 수준**: Java 개발자로서 스레드/IO 사용 가능. 하지만 OS/네트워크 이론을 체계적으로 정리한 경험 없음.
**학습 목표**: 기술스택 학습 전에 CS 기초를 깔아두어 흡수력을 높인다. 면접에서도 즉시 답변 가능.
**예상 시간**: 10시간
**분기 배정**: 1~2분기 (2026.04 ~ 2026.09)
**학습 방식**: **직전 사전학습 (Just-in-Time)** — 관련 기술스택 공부 직전 주에 해당 CS Step을 1시간 먼저 진행.

### CS 기초 학습 방침

| 항목 | 내용 |
|------|------|
| **방식** | 직전 사전학습 — 기술스택 학습 직전 주에 관련 CS를 먼저 깔아둠 |
| **시간** | 평일 30분 + 주말 1시간 (주 ~3.5시간 가용, Step 분량에 따라 조절) |
| **핵심 원칙** | CS를 몰아서 배우지 않음. 맥락 없이 이론만 들어가면 추상적 → 직후 기술스택과 연결해야 체화 |

**진행 순서 예시:**

| 순서 | CS Step (1시간) | → 직후 기술스택 학습 |
|------|---------------|-------------------|
| 1 | Step 1 (프로세스/스레드) + Step 3 (CPU 스케줄링) | → Java 동시성 (Step 10~14) |
| 2 | Step 2 (메모리) | → JVM 메모리 + GC (Step 16) |
| 3 | Step 4~5 (동기비동기/IO 모델) | → Java NIO (Step 19) 또는 Spring WebFlux |
| 4 | Step 6 (네트워크) | → Spring MVC + 김영한 HTTP 강의 |
| 5 | Step 7 (면접 총정리) | 2분기 말 종합 복습 |

> CS를 먼저 깔면 기술스택이 빠르게 들어온다.
> 프로세스/스레드를 알아야 Java 동시성이 왜 그렇게 동작하는지 보이고,
> IO 모델을 알아야 Spring WebFlux가 왜 필요한지 납득된다.

### Step 1. 프로세스와 스레드 — 차이, 컨텍스트 스위칭, PCB/TCB

| 학습 항목 | 학습 목표 |
|----------|----------|
| 프로세스란 | 실행 중인 프로그램의 인스턴스. 독립된 메모리 공간(Code, Data, Heap, Stack)을 가짐. 프로세스 간 메모리 공유 불가(IPC 필요). |
| 스레드란 | 프로세스 내의 실행 흐름. 같은 프로세스의 스레드끼리 Code/Data/Heap을 공유하고 Stack만 독립. |
| 프로세스 vs 스레드 핵심 차이 | **메모리**: 프로세스(독립) vs 스레드(공유). **생성 비용**: 프로세스(높음) vs 스레드(낮음). **안정성**: 프로세스(하나 죽어도 다른 프로세스 무관) vs 스레드(하나 죽으면 전체 프로세스 영향). **통신**: 프로세스(IPC: 파이프, 소켓, 공유메모리) vs 스레드(공유 메모리 직접 접근). |
| 컨텍스트 스위칭 | CPU가 실행 중인 프로세스/스레드를 전환할 때 현재 상태(레지스터, PC, 스택 포인터)를 저장하고 다음 상태를 복원하는 과정. 비용(오버헤드)이 발생하는 이유(캐시 무효화, 상태 저장/복원). 프로세스 전환 > 스레드 전환 비용인 이유(메모리 공간 전환 여부)를 설명 가능. |
| PCB / TCB | PCB(Process Control Block): 프로세스 상태 정보 저장. TCB(Thread Control Block): 스레드 상태 정보 저장. 개념 수준 설명 가능. |
| Java에서의 연결 | Java Thread = OS Thread(1:1 매핑, Platform Thread). Virtual Thread = 경량 스레드(M:N 매핑). (Java 학습 Step 7~12와 연계) |

### Step 2. 메모리 관리 — 가상 메모리, 페이지 폴트, 페이징/세그먼테이션

| 학습 항목 | 학습 목표 |
|----------|----------|
| 가상 메모리란 | 각 프로세스가 독립된 메모리 공간을 가지는 것처럼 보이게 하는 기술. 실제 물리 메모리보다 큰 메모리를 사용 가능한 이유(디스크를 확장 메모리로 활용)를 설명 가능. |
| 페이지 / 페이지 테이블 | 가상 메모리를 고정 크기(보통 4KB) 페이지로 분할. 가상 주소 → 물리 주소 변환을 페이지 테이블로 수행. |
| 페이지 폴트 | 접근하려는 페이지가 물리 메모리에 없을 때 발생. OS가 디스크에서 해당 페이지를 메모리로 로드. 빈번하면 성능 급락(Thrashing). |
| TLB (Translation Lookaside Buffer) | 페이지 테이블 조회를 가속화하는 캐시. TLB 히트 시 빠른 주소 변환. 개념 수준 설명 가능. |
| 페이지 교체 알고리즘 | LRU(가장 오래 안 쓴 페이지 교체), FIFO(먼저 들어온 페이지 교체), Optimal(미래에 가장 늦게 쓰일 페이지, 이론적)의 차이를 설명 가능. |
| 페이지 캐시 (Page Cache, 심화) | OS가 디스크에서 읽은 데이터를 메모리에 캐싱하여 반복 접근 시 디스크 I/O를 생략하는 메커니즘. 파일을 읽으면 페이지 캐시에 적재 → 다음 읽기는 메모리에서 즉시 반환. **Kafka가 디스크 기반인데도 빠른 이유**(Sequential Write → 페이지 캐시에 적재 → Consumer가 읽을 때 디스크 대신 캐시에서 서비스 + Zero Copy). **Oracle Buffer Cache**도 유사 원리(SGA 내 데이터 블록 캐싱). 페이지 캐시 크기 확인: `free -h`의 buff/cache 영역. (Kafka 학습 Step 3, DB 학습과 연계) |
| Java에서의 연결 | JVM 힙이 가상 메모리 위에 동작. GC가 메모리를 관리하지만 OS 관점에서는 가상 메모리 + 페이징의 영향을 받음. JVM이 메모리를 많이 쓰면 페이지 캐시 공간이 줄어 파일 I/O 성능이 저하될 수 있음(Kafka/Redis와 같은 서버에서 JVM 힙을 너무 크게 잡으면 안 되는 이유). (Java 학습 Step 13과 연계) |

### Step 3. CPU 스케줄링 — FCFS, SJF, RR, 우선순위, 멀티레벨 큐

| 학습 항목 | 학습 목표 |
|----------|----------|
| CPU 스케줄링이란 | 여러 프로세스/스레드가 CPU를 공유할 때 "누가 먼저, 얼마나 쓸 것인가"를 결정하는 알고리즘. |
| 선점 vs 비선점 | 선점(Preemptive): OS가 실행 중인 프로세스를 강제로 전환 가능. 비선점(Non-preemptive): 프로세스가 자발적으로 CPU를 반납할 때까지 대기. |
| FCFS (First Come First Served) | 먼저 온 순서대로. 단순하지만 Convoy Effect(긴 작업 뒤에 짧은 작업이 대기)의 문제를 설명 가능. |
| SJF (Shortest Job First) | 실행 시간이 짧은 순서. 평균 대기 시간 최소. 하지만 실행 시간을 미리 알 수 없는 현실적 한계. 기아(Starvation) 문제. |
| RR (Round Robin) | 시간 할당량(Time Quantum)만큼 순환 실행. 시분할 시스템의 기본. Quantum이 너무 크면 FCFS, 너무 작으면 컨텍스트 스위칭 오버헤드. |
| 우선순위 스케줄링 | 우선순위가 높은 프로세스 먼저. 기아 문제 → Aging(대기 시간에 따라 우선순위 점진 증가)으로 해결. |
| 실무 연결 | "왜 이 스레드가 CPU를 못 받는가?" → OS 스케줄링 이해 필요. Java의 Thread.setPriority()가 OS 스케줄러에 힌트를 주는 것임을 이해. |

### Step 4. 동기/비동기 + Blocking/Non-blocking — 4가지 조합

| 학습 항목 | 학습 목표 |
|----------|----------|
| 동기 (Synchronous) | 호출자가 결과를 직접 기다림. "내가 직접 확인한다". |
| 비동기 (Asynchronous) | 호출자가 결과를 기다리지 않고 콜백/이벤트로 통보받음. "알려줘, 나는 다른 일 한다". |
| Blocking | 호출 시 제어권을 넘김. 결과가 올 때까지 호출자가 멈춤. |
| Non-blocking | 호출 시 즉시 반환. 결과가 없으면 "아직 없다"고 즉시 반환. 호출자가 멈추지 않음. |
| 4가지 조합 | **동기+Blocking**(일반 함수 호출, JDBC 쿼리), **동기+Non-blocking**(폴링, while(!ready) check()), **비동기+Non-blocking**(Node.js, Spring WebFlux, 콜백/Future), **비동기+Blocking**(드물지만 select() 시스템 콜이 해당). 각 조합을 예시와 함께 설명 가능. |
| 면접 핵심 | "동기/비동기는 **결과를 누가 처리하는가**(호출자 vs 콜백)", "Blocking/Non-blocking은 **제어권이 돌아오는가**(멈춤 vs 즉시 반환)"로 구분. 이 2x2 매트릭스를 명확히 설명 가능. |
| Java/Spring 연결 | Spring MVC = 동기+Blocking, Spring WebFlux = 비동기+Non-blocking, CompletableFuture = 비동기. (Java 학습, Spring 학습과 연계) |

### Step 5. IO 모델 — Blocking IO, Non-blocking IO, IO Multiplexing, Async IO

| 학습 항목 | 학습 목표 |
|----------|----------|
| Blocking IO | read() 호출 → 데이터 준비까지 스레드 대기 → 데이터 복사 → 반환. 가장 단순하지만 스레드가 낭비됨. 전통적 Java IO(InputStream). |
| Non-blocking IO | read() 호출 → 데이터 없으면 즉시 EAGAIN 반환 → 호출자가 반복 확인(폴링). CPU 낭비(busy-waiting). |
| IO Multiplexing | **select/poll/epoll**로 여러 IO를 하나의 스레드에서 감시. "어떤 소켓에 데이터가 준비되었는가"를 효율적으로 확인. Netty/NIO/Reactor의 기반. Linux epoll이 select보다 효율적인 이유(O(1) vs O(n))를 설명 가능. |
| Async IO (AIO) | 커널이 IO 완료 후 콜백으로 알림. 사용자 스레드가 전혀 대기하지 않음. Linux에서는 io_uring이 최신 구현. |
| Java NIO 연결 | Java NIO의 Channel + Selector가 IO Multiplexing 기반임을 설명 가능. Netty가 epoll을 활용하는 이유. (Java 학습 Step 16, Spring WebFlux와 연계) |
| 면접 핵심 | "Blocking IO → 스레드 낭비", "IO Multiplexing → 적은 스레드로 다수 연결 처리". Spring MVC(스레드 풀, Blocking IO) vs WebFlux(이벤트 루프, IO Multiplexing)의 성능 차이 근거를 설명 가능. |

### Step 6. 네트워크 기초 — TCP/IP, HTTP, DNS (면접 단골 정리)

| 학습 항목 | 학습 목표 |
|----------|----------|
| TCP 3-way Handshake | SYN → SYN+ACK → ACK. 연결 수립 과정을 설명 가능. 왜 3번인가(양방향 통신 확인)를 설명 가능. |
| TCP 4-way Handshake (연결 종료) | FIN → ACK → FIN → ACK. TIME_WAIT 상태가 왜 필요한지(늦게 도착하는 패킷 처리) 설명 가능. |
| TCP vs UDP | TCP(연결 지향, 순서 보장, 재전송, 느림) vs UDP(비연결, 순서 미보장, 재전송 없음, 빠름). 선택 기준(신뢰성 필요 → TCP, 속도 필요 → UDP)을 설명 가능. |
| HTTP/1.1 vs HTTP/2 vs HTTP/3 | HTTP/1.1(텍스트, 연결당 1요청, Keep-Alive), HTTP/2(바이너리, 멀티플렉싱, 헤더 압축, 서버 푸시), HTTP/3(QUIC/UDP 기반, 연결 수립 빠름). 핵심 차이를 설명 가능. |
| DNS | 도메인 → IP 변환. 재귀적 조회(클라이언트 → Local DNS → Root → TLD → Authoritative) 과정을 개념 수준 설명 가능. DNS 캐시(TTL)의 역할. |
| L4 vs L7 로드밸런싱 (심화) | **L4(Transport Layer)**: IP + Port 기반으로 트래픽 분산. TCP 연결 수준에서 동작. 빠르고 단순. AWS **NLB**가 대표. **L7(Application Layer)**: URL 경로, HTTP 헤더, 쿠키 기반으로 라우팅. 요청 내용을 파싱하므로 L4보다 느리지만 유연(경로별 서비스 분기, 인증 등). AWS **ALB**, K8s **Ingress**가 대표. 선택 기준: 단순 분산 → L4, URL/헤더 기반 라우팅 필요 → L7. (AWS 학습 Step 6 ELB, K8s 학습 Step 7 Ingress와 연계) |
| 타 학습 연계 | TCP/HTTP → 김영한 HTTP 강의, DNS/로드밸런싱 → K8s/AWS 학습에서 자연 습득. |

### Step 7. CS 면접 단골 질문 총정리

> **시기**: 2분기 말 종합 복습. Step 1~6 완료 후 진행.
> **목적**: 사전학습한 CS 개념들을 면접 답변으로 체화.

| 질문 | 핵심 답변 포인트 |
|------|----------------|
| "프로세스 vs 스레드 차이" | 메모리 독립/공유, 생성 비용, 안정성, 통신 방식 |
| "컨텍스트 스위칭이란?" | 상태 저장/복원, 오버헤드(캐시 무효화), 프로세스 > 스레드 비용 |
| "가상 메모리란?" | 물리 메모리 추상화, 프로세스별 독립 공간, 페이지 폴트 |
| "페이지 폴트란?" | 물리 메모리에 없는 페이지 접근 → 디스크에서 로드, 빈번 → Thrashing |
| "동기 vs 비동기 차이" | 결과를 누가 처리하는가(호출자 vs 콜백) |
| "Blocking vs Non-blocking 차이" | 제어권이 돌아오는가(멈춤 vs 즉시 반환) |
| "TCP 3-way Handshake" | SYN → SYN+ACK → ACK, 양방향 확인 |
| "TCP vs UDP" | 신뢰성(TCP) vs 속도(UDP) |
| "HTTP/1.1 vs HTTP/2 차이" | 텍스트/바이너리, 멀티플렉싱, 헤더 압축 |
| "DNS 동작 과정" | 재귀적 조회 → Root → TLD → Authoritative, 캐시 |
| "교착 상태(Deadlock) 조건 4가지" | 상호배제, 점유대기, 비선점, 순환대기 |
| "캐시 지역성이란?" | 시간적 지역성(최근 접근 → 다시 접근), 공간적 지역성(인접 데이터 → 함께 접근). ArrayList가 LinkedList보다 빠른 이유 |
| "CPU 캐시 계층(L1/L2/L3)이란?" | L1(코어 전용, ~64KB, ~1ns) → L2(코어 전용, ~256KB, ~4ns) → L3(코어 공유, ~수MB, ~10ns) → RAM(~100ns). **캐시 라인(64바이트)** 단위로 데이터를 로드. ArrayList(연속 메모리) → 캐시 라인에 여러 요소가 함께 적재 → 캐시 히트율 높음. LinkedList(힙 흩어짐) → 포인터 따라갈 때마다 캐시 미스 → 느림. "Big-O가 같아도 하드웨어 친화적(Cache Friendly)이면 실제 성능이 수배 차이" |
| "L4 vs L7 로드밸런싱 차이" | L4: IP/Port 기반, 빠름, NLB. L7: URL/헤더 기반, 유연, ALB/Ingress |
| "페이지 캐시란?" | OS가 파일 데이터를 메모리에 캐싱. Kafka가 빠른 이유의 핵심 |
