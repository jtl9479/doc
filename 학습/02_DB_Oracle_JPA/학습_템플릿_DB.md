### 비유 예시
```
인덱스 = "책 뒤의 색인(찾아보기). 색인 없으면 책 전체를 넘겨야 함(TABLE ACCESS FULL)"
B-Tree = "사전. 'ㄱ→가→감' 순서로 좁혀감. 전체를 안 봐도 원하는 단어를 빠르게 찾음"
실행계획 = "네비게이션 경로. 같은 목적지라도 경로에 따라 시간이 다름. DBMS_XPLAN = 네비 경로 보기"
트랜잭션 격리 = "시험 중 커닝 방지 수준. READ COMMITTED = 옆 사람 답안지 제출 후에만 참고. SERIALIZABLE = 완전 독방"
MVCC = "문서 버전 관리(Google Docs). 누가 편집 중이어도 이전 버전을 볼 수 있음"
JPA 영속성 컨텍스트 = "장바구니. 담아두고(persist) 계산할 때(commit) 한꺼번에 처리"
N+1 = "학생 30명 출석부 확인인데, 이름 1명씩 따로 호출(30번 DB 조회). 한 번에 부르면(Fetch Join) 1번"
힌트 = "네비에게 '고속도로 타지 마' 지시. 옵티마이저(네비)가 최적 경로를 못 찾을 때 개발자가 강제 지정"
AWR = "건강 검진 결과지. 일정 기간 DB의 전체 건강 상태(Top SQL, 대기 이벤트, 성능 지표)를 한눈에"
파티셔닝 = "서류 캐비넷을 연도별로 나눔. 2024년 서류를 찾을 때 전체 캐비넷이 아니라 2024년 서랍만 열면 됨"
커넥션 풀 = "은행 창구. 창구(커넥션) 5개를 미리 열어두고 손님(요청)이 오면 빈 창구에 배정. 창구를 매번 열고 닫으면(커넥션 생성/삭제) 느림"
Data Guard = "비상 발전기. 주 전원(Master)이 끊기면 자동으로 발전기(Standby)가 가동"
Lost Update = "동시에 같은 문서를 편집. A가 저장 → B도 저장 → A의 변경이 사라짐"
CBO + 통계 = "네비의 교통 정보. 도로(테이블)의 차량 수(행 수), 정체 구간(데이터 분포)을 모르면 네비(CBO)가 엉뚱한 경로(실행계획) 제시. 통계가 오래되면 = 어제 교통 정보로 오늘 출근하는 것"
Flush vs Commit = "장바구니(영속성 컨텍스트) → 계산대(Flush, SQL 전송) → 결제 확정(Commit). 계산대에 올려놨지만(Flush) 결제 취소(Rollback) 가능. 결제 확정(Commit) 전까지는 다른 사람(다른 트랜잭션)이 이 상품을 볼 수 없음"
Lock Escalation = "MSSQL에서 행 잠금(Row Lock)이 너무 많아지면 테이블 전체 잠금(Table Lock)으로 자동 승격. Oracle은 이런 자동 승격이 없음(항상 Row Lock 유지)"
```

### 트레이드오프 예시
```
인덱스: 조회 빠름 ↔ DML 느림 + 저장 공간 증가
Fetch Join: N+1 해결 ↔ 컬렉션은 데이터 뻥튀기 + 페이징 불가
Optimistic Lock: 성능 좋음(락 없음) ↔ 충돌 빈번하면 재시도 비용
Pessimistic Lock: 정합성 확실 ↔ 동시성 저하 + 데드락 위험
파티셔닝: 대용량 쿼리 빠름 ↔ 관리 복잡성 + 파티션 키 제약
```

## 설명 흐름

### 1단계: 왜 써야 하는가
- "안 쓰면 실무에서 이런 장애/성능 문제가 발생한다"

### 2단계: 비유로 직관 잡기
- 위 비유 예시 활용
- 비유 → 기술 용어 순서

### 3단계: 핵심 개념 설명
- Oracle 실무 경험자임을 전제
- "왜 이렇게 동작하는가"의 내부 원리 중심
- 그림/다이어그램(B-Tree 구조, 실행계획 트리 등)을 텍스트로 표현

```sql

-- Good: 어떻게 고쳤는지 (INDEX RANGE SCAN)
-- 트레이드오프: "인덱스를 추가하면 조회는 빨라지지만 INSERT/UPDATE 성능이 저하. 이 테이블의 DML 빈도를 고려하여 판단"
```

## Step별 특이사항
- Oracle 튜닝 Step(1~4): SQL + 실행계획 비교가 핵심. 힌트는 "왜 써야 하고, 왜 남용하면 안 되는가" 트레이드오프 필수. **Step 2에서 CBO + 통계 정보 반드시 설명**: "쿼리는 완벽한데 왜 느린가? → 통계가 오래됐기 때문. DBMS_STATS.GATHER_TABLE_STATS를 언제 돌려야 하는가?" 네비 비유 활용
- 트랜잭션 Step(5~7): 동시 접근 시나리오("세션 A가 수정 중일 때 세션 B가 조회하면?"). Lost Update → Optimistic/Pessimistic Lock 비교. **MSSQL/PostgreSQL과의 Lock 차이도 언급**: Oracle(Row Lock 고정, Escalation 없음) vs MSSQL(Lock Escalation 자동 승격 → 의도치 않은 Table Lock) vs PostgreSQL(MVCC는 유사하지만 Vacuum 필요). "Oracle은 이 상황에서 블로킹이 안 되는데 왜 MSSQL은 되는가?"를 설명하면 DB 전체를 보는 눈이 열림
- AWR Step(8): AWR 리포트 핵심 섹션 읽기 + "이 대기 이벤트의 의미는?" 시나리오
- 튜닝 실전 Step(9): 바인드 변수/부분 범위 처리/소트 튜닝. "왜 이렇게 해야 하는가" + 실행계획 비교
- 파티셔닝 Step(10): "왜 파티셔닝이 필요한가"(대용량 테이블 관리) + Partition Pruning 원리 + 트레이드오프(관리 복잡성)
- 레플리카 Step(11): Data Guard/RAC 개념 수준. "왜 이중화가 필요한가" + HA/DR 비유(비상 발전기)
- 커넥션 풀 Step(12): HikariCP 설정값의 의미 + "왜 이 크기가 적정한가" 공식 + Oracle PROCESSES/SESSIONS 한도와의 관계. 은행 창구 비유
- JPA 기초 Step(13~17): Oracle 개발자에게 JPA의 패러다임 차이(SQL 중심 → 객체 중심) 설명. "왜 JPA를 써야 하는가" + MyBatis와의 트레이드오프
- JPA 심화 Step(18~21): Java 코드 + 생성 SQL + "이렇게 하면 왜 문제인가" 비교. N+1 데이터 뻥튀기 + 페이징 트레이드오프. **Step 18에서 Flush vs Commit 정합성 반드시 설명**: "장바구니(영속성 컨텍스트)에 담았다고 DB에 반영된 게 아님. Flush(SQL 전송)해도 Commit 전이면 다른 트랜잭션에 안 보임. ERP처럼 데이터 정합성이 핵심인 시스템에서 이 간극을 모르면 '저장했는데 왜 안 보여요?' 장애로 이어짐." 장바구니→계산대→결제 비유 활용
- MySQL 차이 Step(22): Oracle과의 비교표 중심. "면접에서 MySQL 경험 물어보면?" 대비
