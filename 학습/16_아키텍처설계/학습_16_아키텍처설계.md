## 1. 개요

**현재 수준**: ERP 시스템(20만 줄+ 규모) 개발 경험 있음. 하지만 "설계"가 아닌 "구현"에 참여. 전체 아키텍처를 처음부터 설계한 경험 없음.
**학습 목표**: 20만 줄 규모의 프로젝트를 처음부터 설계 가능. 요구사항 분석 → 아키텍처 결정 → 문서화 → 트레이드오프 판단까지 일관되게 수행 가능. "왜 이렇게 설계했는가?"를 논리적으로 설명 가능.
**분기 배정**: 3분기 (2026.10 ~ 2026.12)
**선수 조건**: 학습_03 DDIA, 학습_10 DDD, 학습_13 MSA 학습 후 진행 권장

### Step 1. 아키텍처 설계 개요 — 왜 설계가 필요한가, 설계자의 역할

| 학습 항목 | 학습 목표 |
|----------|----------|
| 왜 설계가 필요한가 | 설계 없이 코딩하면 단기적으로 빠르지만 장기적으로 변경 비용이 기하급수적으로 증가하는 이유를 설명 가능. "기술 부채(Technical Debt)"의 개념을 설명 가능. |
| 아키텍처란 | "변경하기 어려운 결정들의 집합". 언어, 프레임워크, DB, 모듈 분리, 통신 방식 등 나중에 바꾸기 비싼 것들. 세부 구현(알고리즘, 변수명)은 아키텍처가 아님. |
| 아키텍처 설계자의 역할 | ① 비즈니스 요구를 기술 구조로 변환, ② 트레이드오프 판단(정답은 없고 상황에 맞는 최선), ③ 팀이 따를 수 있는 가이드 제공, ④ 리스크 식별 및 완화. |
| "만든 적은 있지만 설계한 적은 없다" | 본인 ERP 경험: 개별 화면/기능은 구현했지만 전체 시스템 구조를 결정한 경험은 부족. 이 학습은 "구현자 → 설계자"로 전환하는 과정임을 이해. |
| 20만 줄 프로젝트의 의미 | 20만 줄 = 약 500~1000개 클래스 = 10~20개 모듈 = 50~100개 API. 한 사람이 전체를 머릿속에 담을 수 없는 규모. 따라서 "구조적 분리"가 필수. |

### Step 2. 좋은 아키텍처의 특성

| 학습 항목 | 학습 목표 |
|----------|----------|
| 변경 용이성 (Modifiability) | 새 기능 추가/기존 기능 변경 시 영향 범위가 제한되는 구조. "한 곳을 고치면 다른 곳이 깨진다" = 나쁜 아키텍처. |
| 테스트 용이성 (Testability) | 외부 의존성(DB, 외부 API) 없이 핵심 로직을 테스트할 수 있는 구조. 헥사고날/클린 아키텍처가 이를 지향. |
| 이해 용이성 (Understandability) | 새 팀원이 시스템 구조를 빠르게 파악 가능한 구조. 모듈/패키지 구조가 비즈니스 도메인을 반영(screaming architecture). |
| 배포 독립성 (Deployability) | 특정 모듈 변경 시 전체를 재배포하지 않아도 되는 구조. 모듈러 모놀리스 이상에서 가능. |
| 성능/확장성 (Scalability) | 트래픽 증가에 따라 수평/수직 확장이 가능한 구조. 병목 지점이 명확. |
| SOLID와의 관계 | SRP(단일 책임), OCP(개방-폐쇄), LSP(리스코프 치환), ISP(인터페이스 분리), DIP(의존성 역전)가 모듈/서비스 수준에서도 동일하게 적용되는 이유를 설명 가능. |

---

### Step 3. 설계 프로세스 — 요구사항 → 제약조건 → 설계 → 검증

| 학습 항목 | 학습 목표 |
|----------|----------|
| 설계 프로세스 전체 흐름 | ① 요구사항 분석(기능/비기능) → ② 제약조건 식별(팀, 기술, 시간, 예산) → ③ 후보 아키텍처 도출 → ④ 트레이드오프 분석 → ⑤ 결정 + 문서화(ADR) → ⑥ 검증(프로토타입, 리뷰). 전체 흐름을 설명 가능. |
| 반복적 설계 | 한 번에 완벽한 설계는 불가능. "충분히 좋은(Good Enough)" 설계를 빠르게 → 구현하면서 피드백 → 개선. 빅 업프론트 디자인(BDUF)의 위험을 설명 가능. |
| 면접에서의 설계 프로세스 | 4단계 접근법: **1) 요구사항 정리**(5분, 질문으로 범위 확정) → **2) 대략적 설계**(10분, 핵심 컴포넌트 + API + 데이터 모델) → **3) 상세 설계**(10분, 병목 해결, 스케일링) → **4) 마무리**(5분, 트레이드오프 정리, 확장 가능성). |
| "정답은 없다" | 같은 요구사항에도 팀/상황에 따라 다른 아키텍처가 최선일 수 있음. "왜 이것을 선택했는가"를 논리적으로 설명하는 것이 중요. |

### Step 4. 요구사항 분석 — 기능/비기능 요구사항, 제약조건 식별

| 학습 항목 | 학습 목표 |
|----------|----------|
| 기능 요구사항 (Functional) | 시스템이 "무엇을 하는가". 유스케이스 목록, 핵심 기능 식별. 예: "수주 등록, 수주 조회, 수주 수정, 수주 취소". |
| 비기능 요구사항 (Non-Functional) | 시스템이 "얼마나 잘 하는가". 성능(응답 시간 < 200ms), 가용성(99.9%), 확장성(동시 사용자 1000명), 보안(개인정보 암호화), 데이터 보존(5년). |
| 제약조건 | 팀 규모(3명 vs 30명), 기술 스택(Java/Spring 필수), 예산(AWS 월 X만원), 기간(6개월), 기존 시스템 연동. |
| 핵심 질문법 | "사용자는 누구인가?", "핵심 기능은?", "DAU/트래픽 규모는?", "읽기/쓰기 비율은?", "데이터 보존 기간은?", "일관성 vs 가용성 중 무엇이 더 중요한가?", "단일 리전 vs 글로벌?". 핵심 질문을 던지고 범위를 확정하는 능력. |
| ERP 요구사항 예시 | 20만 줄 ERP의 요구사항: 20개 모듈(수주/구매/생산/재고/회계 등), 동시 사용자 200명, 트랜잭션 정합성 최우선, Oracle DB, 사내 서버(온프레미스 또는 AWS). |

### Step 5. 대략적 추정 — QPS, 저장소, 대역폭, 서버 수 계산

| 학습 항목 | 학습 목표 |
|----------|----------|
| 왜 추정이 필요한가 | "어떤 규모의 시스템인가"를 숫자로 파악해야 적절한 아키텍처를 선택 가능. 100 QPS와 100,000 QPS는 완전히 다른 설계. |
| QPS (Queries Per Second) | DAU × 1인당 요청 수 / 86,400초. 피크는 평균의 2~5배. 예: DAU 10만 × 50요청 / 86,400 ≈ 58 QPS, 피크 ≈ 300 QPS. |
| 저장소 추정 | 데이터 크기 × 건수 × 보존 기간. 예: 주문 1건 = 1KB, 일 10만 건, 5년 보존 = 1KB × 100,000 × 365 × 5 ≈ 180GB. |
| 2의 거듭제곱 감각 | 1KB(텍스트 1줄), 1MB(사진 1장), 1GB(영화 1편), 1TB(1,000GB). 1일 = 86,400초 ≈ 10만 초. 빠른 계산 감각을 갖추기. |
| ERP 추정 예시 | 동시 사용자 200명, 1인당 분당 5요청 = 1000 요청/분 ≈ 17 QPS. 피크 50 QPS. 이 규모에서는 단일 서버로도 충분함을 판단 가능. "ERP는 트래픽이 아니라 정합성이 핵심"임을 이해. |

### Step 6. 아키텍처 패턴 비교 — 모놀리식/모듈러 모놀리스/MSA

| 학습 항목 | 학습 목표 |
|----------|----------|
| (DDD 학습 Step 13, MSA 학습 Step 1~2와 연계) | 3가지 패턴을 이미 학습한 상태. 여기서는 **"20만 줄 프로젝트에 어떤 패턴을 선택하는가"**에 집중. |
| 20만 줄에 적합한 패턴 | 팀 3~5명 + 정합성 최우선(ERP) → **모듈러 모놀리스**가 최적. 모놀리식(경계 없음, 유지보수 어려움) < **모듈러 모놀리스**(Bounded Context별 패키지 격리) < MSA(인프라 비용 과다). |
| 모듈 분리 기준 | 비즈니스 도메인(수주/구매/생산/재고/회계)별로 모듈 분리. 모듈 간 통신은 공개 인터페이스만. 내부 직접 참조 금지. 패키지 구조 예시를 설계 가능. |
| 전환 경로 설계 | 모듈러 모놀리스에서 시작 → 트래픽/팀 규모 증가 시 → 특정 모듈만 MSA로 분리(Strangler Fig). 전환 시점 판단 기준을 설명 가능. |
| 레거시 현대화 전략 (심화) | 기존 20만 줄 모놀리스 ERP를 중단 없이 현대화하는 전략: **Strangler Fig 패턴**(프록시 배치 → 새 기능은 새 모듈/서비스 → 기존 기능 점진적 추출 → 모놀리스 축소). 결합도 낮은 기능(알림, 로깅)부터 분리 시작 → 핵심 도메인(수주, 회계)은 마지막. **DB 분리 전략**: 공유 DB → 뷰/동의어로 읽기 분리 → 이벤트 기반 데이터 동기화 → 완전 분리. 데이터 이관 시 정합성 보장(이중 쓰기 + 검증 배치). "새로 만드는 능력보다 기존 시스템을 안전하게 개선하는 능력"이 시니어의 핵심임을 설명 가능. |

### Step 7. 코드 아키텍처 비교 — 레이어드/헥사고날/클린

| 학습 항목 | 학습 목표 |
|----------|----------|
| (DDD 학습 Step 11~13과 연계) | 3가지 코드 아키텍처를 이미 학습한 상태. 여기서는 **20만 줄 프로젝트의 패키지 구조를 실제로 설계**하는 데 집중. |
| 모듈별 코드 아키텍처 | 핵심 도메인(수주, 회계) → 헥사고날/클린(비즈니스 로직 보호). 단순 도메인(코드 관리, 라벨 출력) → 레이어드(단순 CRUD). "모든 모듈에 같은 아키텍처를 적용할 필요 없다"는 판단을 설명 가능. |
| 패키지 구조 실전 예시 | 20만 줄 ERP의 패키지 구조를 설계 가능. 예: `com.company.erp.sm`(수주), `com.company.erp.pm`(구매), 각 모듈 내부에 domain/application/adapter/infra. |
| 모듈 간 의존성 규칙 | 허용: sm → co(기준정보 참조). 금지: sm → pm(수주가 구매를 직접 호출). 모듈 간 통신은 이벤트 또는 공개 인터페이스. 의존성 규칙 위반 감지(ArchUnit) 도구의 존재를 알고 있음. |

### Step 8. 통신 패턴 — 동기(REST) vs 비동기(이벤트) vs 혼합

| 학습 항목 | 학습 목표 |
|----------|----------|
| (MSA 학습 Step 3과 연계) | 동기/비동기 통신을 이미 학습한 상태. 여기서는 **"이 기능에 어떤 통신을 쓸 것인가"를 20만 줄 프로젝트에서 판단**하는 데 집중. |
| 판단 기준 | 즉시 응답 필요(조회, 유효성 검증) → 동기(메서드 호출 또는 REST). 결합도 감소 + 비동기 가능(알림, 로그, 통계) → 이벤트(Spring ApplicationEvent 또는 Kafka). |
| ERP 적용 | "수주 등록 시 재고 확인" → 동기(즉시 결과 필요). "수주 확정 후 알림 발송" → 비동기(이벤트). "수주 확정 후 매출 반영" → 이벤트(트랜잭션 커밋 후 @TransactionalEventListener). |
| 모듈러 모놀리스에서의 통신 | 같은 프로세스 내이므로 Kafka 불필요. Spring ApplicationEvent로 충분. 나중에 MSA로 분리 시 이벤트를 Kafka로 전환하면 됨. |

### Step 9. 데이터 아키텍처 — DB 선택, 스키마 설계, 캐시 전략

| 학습 항목 | 학습 목표 |
|----------|----------|
| DB 선택 | 20만 줄 ERP → RDBMS(Oracle/PostgreSQL) 기본. 검색 → Elasticsearch. 캐시 → Redis. 로그 → MongoDB 또는 Loki. 용도별 DB를 선택하는 판단 근거를 설명 가능. |
| 스키마 설계 원칙 | 정규화(3NF) 기본 → 성능 필요 시 비정규화. 공통 코드 테이블, 이력 테이블, 마스터-상세 구조. ERP 스키마 패턴을 설명 가능. |
| 캐시 전략 | 자주 조회되지만 변경 적은 데이터(코드, 거래처 목록) → Redis Cache Aside. TTL 설계. 캐시 무효화 전략(이벤트 기반)을 설명 가능. |
| 데이터 정합성 설계 | "수주 → 재고 차감 → 매출"이 하나의 트랜잭션인지, Saga인지 판단. ERP에서는 단일 DB 트랜잭션이 적합한 이유(모듈러 모놀리스)를 설명 가능. |
| 데이터 마이그레이션 | 기존 시스템에서 신규 시스템으로 데이터 이관 전략. ETL, 병행 운영, 검증. ERP 경험 연결. |
| 감사 로그 아키텍처 (ERP 심화) | "누가(who) 언제(when) 어떤 데이터를(what) 어떤 동작을(action) 했는가"를 불변으로 기록하는 설계. 설계 단계에서 감사 대상(금액 변경, 승인, 삭제)과 기록 방식(AOP 자동 기록, 별도 audit 테이블, Append-Only)을 결정. 이벤트 소싱(DDD 학습)과의 연결. ERP에서 "수주 금액을 누가 변경했는가?"를 설계 시점부터 보장. (보안 학습 Step 11과 연계) |
| 개인정보 분리/암호화 아키텍처 (ERP 심화) | 설계 단계에서 민감 데이터(주민번호, 계좌번호)의 저장 위치를 분리하는 아키텍처. 방안: ① 별도 테이블/스키마에 암호화 저장 + FK로 연결, ② 앱 레벨 AES-256 암호화 + 복호화 권한 분리, ③ 마스킹(화면 표시 시 일부 가림). "돈과 개인정보가 흐르는 시스템"에서 보안을 설계 시점부터 내재화하는 능력. (보안 학습 Step 11과 연계) |

### Step 10. 확장성 설계 — 수평 확장, 파티셔닝, 캐시, 큐

| 학습 항목 | 학습 목표 |
|----------|----------|
| (DDIA 학습 Step 14와 연계) | 확장성 패턴을 이미 학습한 상태. 여기서는 **20만 줄 프로젝트에 어디까지 확장성을 설계하는가**에 집중. |
| ERP는 확장성보다 정합성 | ERP 200명 동시 사용자 ≈ 17 QPS. 이 규모에서 샤딩/파티셔닝은 과도. 단일 DB + 커넥션 풀 튜닝 + 인덱스 최적화로 충분. |
| 과도한 확장성 설계의 위험 | "혹시 사용자가 100만이 될 수도 있으니까 MSA + 샤딩으로" → 현재 200명인데 불필요한 복잡성. **YAGNI(You Ain't Gonna Need It)** 원칙을 설명 가능. |
| 확장 지점 식별 | "지금은 불필요하지만 나중에 필요해질 수 있는 지점"을 설계 시 식별. 인터페이스를 두어 나중에 교체 가능하게(DIP). 하지만 구현은 지금 필요한 만큼만. |
| 진짜 확장이 필요한 경우 | ERP가 아닌 B2C 서비스(수만~수백만 사용자)라면: 읽기 확장(Read Replica, Redis 캐시), 쓰기 확장(파티셔닝), 비동기 처리(Kafka) 설계 판단. |

### Step 11. 가용성/장애 대응 설계 — 이중화, 페일오버, 서킷 브레이커

| 학습 항목 | 학습 목표 |
|----------|----------|
| (DDIA 학습 Step 15, MSA 학습 Step 10~11과 연계) | 장애 대응 패턴을 이미 학습한 상태. 여기서는 **20만 줄 프로젝트의 가용성 설계**에 집중. |
| ERP 가용성 요구 | 업무 시간(9~18시) 99.9% 가용성 = 연간 약 8시간 다운타임 허용. 24/7 서비스 대비 여유 있지만 업무 시간 중단은 매출 직결. |
| 이중화 설계 | WAS 2대 이상(Active-Active, 로드밸런서), DB Multi-AZ(Oracle Data Guard 또는 RDS Multi-AZ). 단일 장애점(SPOF) 제거. |
| 장애 대응 계획 | WAS 1대 다운 → LB가 트래픽 전환(자동). DB 마스터 다운 → Standby 승격(자동/수동). 외부 API 장애 → Circuit Breaker + Fallback. 각 시나리오별 대응을 설계 가능. |
| 배포 중 가용성 | Rolling Update(무중단 배포), Blue-Green(즉시 롤백), Graceful Shutdown(처리 중 요청 완료 후 종료). ERP 배포 전략을 설계 가능. |

### Step 12. 아키텍처 문서화 — ADR, C4 Model, 시퀀스 다이어그램

| 학습 항목 | 학습 목표 |
|----------|----------|
| 왜 문서화하는가 | "설계는 코드에 있다"는 일부만 맞음. 코드만으로 "왜 이 결정을 했는가"는 알 수 없음. 새 팀원이 합류하거나, 6개월 후 본인이 까먹었을 때 필요. |
| ADR (Architecture Decision Record) | 아키텍처 결정을 기록하는 경량 문서. 구조: **제목 → 상태(수락/거절) → 맥락(왜 이 결정이 필요했나) → 결정(무엇을 선택했나) → 결과(트레이드오프)**. ADR을 작성 가능. |
| ADR 예시 | "ADR-001: DB는 Oracle을 사용한다. 맥락: 팀이 Oracle 경험이 풍부하고, ERP는 복잡한 트랜잭션이 필요. 결정: Oracle 19c. 결과: 라이선스 비용 발생, MySQL 대비 운영 비용 높음, 하지만 복잡한 쿼리/튜닝 도구(AWR) 활용 가능." |
| C4 Model | 4단계 시스템 다이어그램. **Context**(시스템과 외부 사용자/시스템), **Container**(앱, DB, 메시지 브로커), **Component**(모듈/패키지), **Code**(클래스). 20만 줄 ERP의 Context/Container/Component 다이어그램을 그릴 수 있음. |
| 시퀀스 다이어그램 | 요청 흐름을 시간 순서로 표현. "수주 등록" API의 Controller → Service → Repository → DB 흐름을 그릴 수 있음. 복잡한 흐름(수주 → 재고 확인 → 이벤트 → 알림)을 시퀀스로 표현 가능. |
| 데이터 흐름도 | 시스템 간 데이터 이동을 표현. ERP ↔ WMS ↔ PDA ↔ 거래처 EDI 간 데이터 흐름을 그릴 수 있음. |
| 아키텍처 거버넌스 — ArchUnit (심화) | 설계 규칙을 문서로만 남기면 팀원이 어기는 것을 막을 수 없음. **ArchUnit**(Java 아키텍처 테스트 라이브러리)으로 규칙을 코드로 강제하는 방법을 설명 가능. 예: `noClasses().that().resideInAPackage("..sm..").should().dependOnClassesThat().resideInAPackage("..pm..")`(수주 모듈이 구매 모듈에 의존 금지). CI에서 ArchUnit 테스트 실패 → 빌드 실패로 자동 차단. "아키텍처는 문서가 아니라 코드로 지킨다"는 원칙을 설명 가능. |

### Step 13. 아키텍처 평가 — 트레이드오프 분석, 병목/SPOF 식별

| 학습 항목 | 학습 목표 |
|----------|----------|
| 트레이드오프 사고 | "왜 이 방식을 선택했는가? 대안은 무엇이고, 그 대안의 단점은?" 형태로 모든 설계 결정을 정당화 가능. "정답"이 아니라 "상황에 맞는 최선"임을 설명 가능. |
| 주요 트레이드오프 | 일관성 vs 가용성(CAP), 성능 vs 단순성, 결합도 vs 복잡도, 유연성 vs 오버엔지니어링, 비용 vs 기능. 각 축을 설명 가능. |
| 비용/운영 공수 트레이드오프 (심화) | 기술적 장단점만이 아니라 **인프라 비용**과 **운영 공수(Operational Overhead)**를 핵심 판단 축으로 포함. 예: "MSA가 기술적으로 우수하지만, 현재 팀 3명 + 트래픽 17 QPS에서는 서비스 20개 × 모니터링/배포/로깅 운영 비용이 개발 비용을 초과. 모듈러 모놀리스가 TCO(Total Cost of Ownership) 관점에서 최적." AWS 비용 추정(EC2, RDS, S3, 데이터 전송)을 아키텍처 결정에 포함시키는 습관. "기술적으로 좋다"와 "비즈니스적으로 합리적이다"는 다른 판단임을 설명 가능. |
| 병목 식별 | 설계를 보고 "트래픽이 몰리면 어디가 먼저 터지는가?"를 식별 가능. DB(커넥션 풀, 슬로 쿼리), 외부 API(타임아웃), 메모리(캐시 부족). |
| 단일 장애점 (SPOF) 식별 | "이 컴포넌트가 죽으면 전체 시스템이 멈추는가?"를 식별 가능. 이중화/페일오버/Circuit Breaker로 완화하는 방안 제시 가능. |
| 아키텍처 리뷰 프로세스 | 설계 문서를 팀에 공유 → 리뷰 회의 → 피드백 반영 → ADR 업데이트. "혼자 결정하지 않고 팀이 함께 결정하고 기록한다"는 원칙. |

### Step 15. 20만 줄 프로젝트 설계 실전 — ERP 규모 시스템 설계

| 학습 항목 | 학습 목표 |

| ERP 전체 요구사항 정리 | 20개 모듈(수주/구매/생산/재고/회계/기준정보/출고/매출/라벨/바코드...), 동시 사용자 200명, Oracle DB, 외부 연동(WMS, PDA, EDI). |

| 모듈 분리 설계 | Bounded Context별 패키지 분리. 모듈 간 의존성 규칙 정의. 공개 인터페이스 + 이벤트 통신 설계. |
| 핵심 도메인 설계 | 수주(SM) 모듈 상세: Aggregate(Order → OrderItem), Repository, Domain Service, Application Service, API. 헥사고날 구조 적용. |
| 트랜잭션 경계 설계 | "수주 등록"은 Order + OrderItem + 재고 예약이 하나의 트랜잭션. "수주 확정 후 매출 반영"은 이벤트 기반. 각 비즈니스 흐름의 트랜잭션 경계를 설계 가능. |
| 비기능 요구사항 설계 | 인증(JWT + Spring Security), 권한(역할 기반), 로깅(구조화 로그 + ELK), 모니터링(Actuator + Prometheus + Grafana), 배포(Docker + K8s). |
| ADR 5건 이상 작성 | DB 선택, 아키텍처 패턴 선택, 인증 방식, 캐시 전략, 모듈 간 통신 방식 등 핵심 결정을 ADR로 기록. |
