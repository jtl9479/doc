### Step 1. 웹 보안 개요 — 왜 보안이 중요한가, 공격자의 관점

| 학습 항목 | 학습 목표 |
|----------|----------|
| 왜 보안이 중요한가 | 보안 사고의 실제 피해(데이터 유출, 금전 손실, 법적 제재, 신뢰 상실)를 설명 가능. "보안은 나중에"가 위험한 이유(취약점은 배포 후 발견하면 수정 비용 급증)를 설명 가능. |
| 공격자의 관점 | 방어자는 모든 곳을 지켜야 하지만 공격자는 하나의 취약점만 찾으면 됨. 가장 약한 고리(사용자 입력, 인증, 설정 오류)를 노리는 관점을 이해. |
| 보안의 3요소 (CIA) | **기밀성**(Confidentiality: 비인가자 접근 차단), **무결성**(Integrity: 데이터 위/변조 방지), **가용성**(Availability: 서비스 지속 운영). 각각을 설명 가능. |
| 심층 방어 (Defense in Depth) | 하나의 방어 계층이 뚫려도 다음 계층이 막는 다중 방어 원칙. 네트워크(방화벽) + 애플리케이션(입력 검증) + 데이터(암호화) + 운영(모니터링)을 설명 가능. |
| 개발자의 보안 책임 | "보안팀이 할 일"이 아니라 "코드를 쓰는 사람이 1차 방어선"임을 이해. DevSecOps(보안이 내재된 개발)의 필요성을 설명 가능. |

### Step 2. HTTPS / TLS — 암호화 통신 원리

| 학습 항목 | 학습 목표 |
|----------|----------|
| HTTP vs HTTPS | HTTP: 평문 전송(도청 가능). HTTPS: TLS로 암호화(도청/위변조 방지). 왜 모든 통신이 HTTPS여야 하는지 설명 가능. |
| TLS (Transport Layer Security) | SSL의 후속. 서버와 클라이언트 간 암호화 통신을 수립하는 프로토콜. |
| TLS Handshake | 클라이언트 Hello → 서버 Hello + 인증서 전송 → 키 교환 → 대칭 키 생성 → 암호화 통신 시작. 전체 흐름을 개념 수준 설명 가능. |
| 대칭 키 vs 비대칭 키 | 대칭 키(AES: 빠름, 같은 키로 암/복호화), 비대칭 키(RSA: 느림, 공개 키/개인 키 쌍). TLS가 비대칭 키로 대칭 키를 교환한 후 대칭 키로 통신하는 이유(성능)를 설명 가능. |
| 인증서 (Certificate) | 서버의 공개 키 + 신원 정보를 CA(Certificate Authority)가 서명. 클라이언트가 "이 서버가 진짜인지" 검증하는 원리를 설명 가능. Let's Encrypt(무료 CA)의 존재를 알고 있음. |
| HSTS | HTTP Strict Transport Security. 브라우저가 해당 사이트에 HTTP 접근 시 자동으로 HTTPS로 전환하도록 강제하는 헤더. |

### Step 3. OWASP Top 10 — 웹 애플리케이션 10대 취약점 (1~5)

| 학습 항목 | 학습 목표 |
|----------|----------|
| OWASP이란 | Open Web Application Security Project. 웹 보안 취약점 Top 10을 주기적으로 발표하는 비영리 재단. |
| A01: Broken Access Control (접근 제어 실패) | 인가되지 않은 사용자가 다른 사용자의 데이터에 접근하거나 관리자 기능을 실행하는 취약점. 예: URL에 userId를 바꿔서 다른 사람의 주문 조회. 방어: 서버 측 인가 검증 필수, URL/파라미터 기반 접근 제어 금지, RBAC/ABAC 적용. |
| A02: Cryptographic Failures (암호화 실패) | 민감 데이터(비밀번호, 카드번호)를 평문 저장/전송하는 취약점. 방어: 비밀번호는 해시(BCrypt/Argon2) 저장, 전송은 TLS, 불필요한 민감 데이터 미저장. |
| A03: Injection (인젝션) | 사용자 입력이 쿼리/명령으로 직접 실행되는 취약점. **SQL Injection**: `' OR 1=1 --`로 인증 우회. **OS Command Injection**: 사용자 입력이 시스템 명령으로 실행. 방어: PreparedStatement(파라미터 바인딩), ORM 사용, 입력 검증(화이트리스트). ERP 개발에서 MyBatis `${}` vs `#{}` 차이를 설명 가능. |
| A04: Insecure Design (불안전한 설계) | 코드 버그가 아니라 **설계 자체**의 보안 결함. 예: 비밀번호 찾기에 무차별 대입(Brute Force) 방어 없음. 방어: 위협 모델링, 보안 설계 패턴(Rate Limiting, CAPTCHA). |
| A05: Security Misconfiguration (보안 설정 오류) | 기본 비밀번호 미변경, 불필요한 기능 활성화, 에러 메시지에 스택 트레이스 노출. 방어: 불필요한 기능 비활성화, 에러 메시지 최소화, 보안 헤더 설정. Spring Boot에서 `server.error.include-stacktrace=never` 설정의 이유를 설명 가능. |

### Step 4. OWASP Top 10 — 웹 애플리케이션 10대 취약점 (6~10)

| 학습 항목 | 학습 목표 |
|----------|----------|
| A06: Vulnerable Components (취약한 컴포넌트) | 알려진 취약점이 있는 라이브러리/프레임워크 사용. 예: Log4j 취약점(Log4Shell). 방어: 의존성 주기적 업데이트, 취약점 스캔(Dependabot, OWASP Dependency-Check, Trivy). |
| 공급망 보안 심화 (SCA + SBOM) | **SCA(Software Composition Analysis)**: 사용 중인 오픈소스 라이브러리의 취약점을 자동 스캔하는 도구/프로세스. CI 파이프라인에 SCA를 통합하여 취약한 의존성이 배포되지 않게 게이트키핑하는 방법을 설명 가능. **SBOM(Software Bill of Materials)**: 소프트웨어에 포함된 모든 컴포넌트/라이브러리 목록. Log4j 같은 대규모 취약점 발생 시 "우리 시스템에 해당 라이브러리가 있는가?"를 즉시 파악하는 도구. 미국 행정명령(Executive Order)으로 SBOM 제출이 의무화되는 추세임을 알고 있음. |
| A07: Authentication Failures (인증 실패) | 약한 비밀번호 허용, 무차별 대입 미방어, 세션 고정(Session Fixation). 방어: 강력한 비밀번호 정책, 로그인 시도 제한, MFA, 세션 ID 재생성. |
| A08: Data Integrity Failures (데이터 무결성 실패) | 신뢰할 수 없는 소스의 데이터/코드를 검증 없이 사용. 예: 안전하지 않은 역직렬화(Java Deserialization 공격). 방어: 서명 검증, 역직렬화 입력 검증, Jackson 대신 Java Serialization 사용 금지. |
| A09: Logging & Monitoring Failures (로깅/모니터링 실패) | 공격 시도를 로깅하지 않거나 모니터링하지 않아 침입을 감지 못 함. 방어: 인증 실패/접근 제어 실패 로깅, 이상 탐지 알림, 로그에 민감 정보(비밀번호, 토큰) 기록 금지. |
| A10: SSRF (Server-Side Request Forgery) | 서버가 공격자가 지정한 URL로 요청을 보내도록 유도. 내부 네트워크 자원에 접근하거나 메타데이터 서버(AWS 169.254.169.254) 정보를 탈취. 방어: URL 화이트리스트, 내부 IP 대역 차단, 메타데이터 접근 제한(IMDSv2). |

### Step 5. 인증 개요 — 인증 vs 인가, 세션 vs 토큰

| 학습 항목 | 학습 목표 |
|----------|----------|
| 인증 (Authentication) | "당신이 누구인가?" 신원 확인. 로그인(ID/PW, 소셜 로그인, 생체 인식). |
| 인가 (Authorization) | "당신이 무엇을 할 수 있는가?" 권한 확인. 인증된 사용자에 대한 접근 제어. 인증 후에 인가가 진행됨. |
| 세션 기반 인증 | 로그인 → 서버가 세션 생성(서버 메모리/DB에 저장) → 세션 ID를 쿠키로 클라이언트에 전달 → 매 요청 시 쿠키의 세션 ID로 인증. 장점(서버가 세션 제어 가능, 즉시 무효화)과 단점(서버 상태 유지, 수평 확장 시 세션 공유 필요)을 설명 가능. |
| 토큰 기반 인증 | 로그인 → 서버가 토큰(JWT) 발급 → 클라이언트가 토큰 저장 → 매 요청 시 Authorization 헤더에 토큰 포함 → 서버가 토큰 검증(서명 확인). 장점(서버 무상태, 수평 확장 용이)과 단점(토큰 탈취 시 즉시 무효화 어려움)을 설명 가능. |
| 세션 vs 토큰 선택 기준 | 전통적 웹앱(서버 렌더링) → 세션. SPA/모바일 + API 서버 → 토큰(JWT). MSA(여러 서비스에서 인증 공유) → 토큰. |

### Step 6. JWT — 구조, 동작, Access/Refresh Token

| 학습 항목 | 학습 목표 |
|----------|----------|
| JWT란 | JSON Web Token. 자가 포함형(Self-contained) 토큰. 토큰 자체에 사용자 정보가 포함되어 서버 조회 없이 검증 가능. |
| JWT 구조 | `Header.Payload.Signature` 3파트. **Header**: 알고리즘(HS256/RS256) + 타입(JWT). **Payload**: Claims(sub, exp, iat, iss, 커스텀 클레임). **Signature**: Header+Payload를 비밀 키로 서명. 각 파트를 설명 가능. |
| JWT 동작 흐름 | 로그인 → 서버가 JWT 생성(비밀 키로 서명) → 클라이언트에 반환 → 클라이언트가 저장(localStorage/HttpOnly 쿠키) → 매 요청 시 `Authorization: Bearer <token>` → 서버가 서명 검증 + 만료 확인. |
| Access Token + Refresh Token | Access Token: 짧은 만료(15분~1시간), API 접근에 사용. Refresh Token: 긴 만료(1주~1개월), Access Token 재발급에만 사용. 이중 토큰 전략으로 보안(짧은 Access)과 편의(긴 Refresh)를 균형 잡는 이유를 설명 가능. |
| JWT의 한계 | 한번 발급하면 만료 전까지 서버에서 무효화 어려움(무상태의 대가). 대응: ① 짧은 만료 + Refresh Token, ② 블랙리스트(Redis에 무효화된 토큰 저장, 무상태 원칙 일부 포기), ③ 토큰 버전(DB에 버전 관리). |
| RT Rotation (심화) | Refresh Token을 사용할 때마다 새 RT를 발급하고 이전 RT를 무효화하는 기법. 탈취된 RT가 재사용되면 즉시 감지(이미 사용된 RT 재사용 = 탈취 의심 → 전체 토큰 무효화)하는 원리를 설명 가능. |
| Redis 블랙리스트 트레이드오프 (심화) | 로그아웃 시 JWT를 Redis에 블랙리스트로 등록(TTL = JWT 남은 만료 시간). 매 요청마다 Redis 조회 필요 → **무상태(Stateless)의 장점을 일부 포기**하는 대가. "JWT인데 왜 서버 상태를 쓰는가?" → "완전한 무상태 vs 즉시 무효화" 트레이드오프를 비즈니스 요구(금융=즉시 무효화 필수, 일반=짧은 만료로 충분)에 맞게 판단 가능. Redis 블랙리스트의 성능 영향(O(1) 조회, AT 만료 시간만큼만 보관 → 메모리 부담 적음)을 설명 가능. |
| HS256 vs RS256 | HS256(대칭 키: 서명/검증 같은 키, 단일 서버에 적합). RS256(비대칭 키: 개인 키로 서명, 공개 키로 검증, MSA에 적합 — 인증 서버만 개인 키 보유, 각 서비스는 공개 키로 검증). 선택 기준을 설명 가능. |
| JWT 저장 위치 보안 | localStorage(XSS 취약), HttpOnly 쿠키(XSS 방어 + CSRF 필요), 메모리(가장 안전하지만 새로고침 시 사라짐)의 트레이드오프를 설명 가능. |

### Step 7. OAuth2 / OIDC — 소셜 로그인, 인가 서버

| 학습 항목 | 학습 목표 |
|----------|----------|
| OAuth2란 | 인가(Authorization) 프레임워크. "내 대신 이 앱이 내 Google 데이터에 접근해도 된다"를 승인하는 프로토콜. 비밀번호를 제3자에게 주지 않고 접근 권한을 위임하는 목적을 설명 가능. |
| OAuth2 핵심 역할 | Resource Owner(사용자), Client(내 앱), Authorization Server(Google/Kakao 인증 서버), Resource Server(Google/Kakao API 서버). 4가지 역할을 설명 가능. |
| Authorization Code Grant | 가장 안전한 표준 방식. 사용자 → 인증 서버 로그인 → Authorization Code 발급 → 내 서버가 Code + Client Secret으로 Access Token 교환. 코드가 클라이언트(브라우저)에 노출되지 않는 이유를 설명 가능. |
| PKCE (Proof Key for Code Exchange) | SPA/모바일에서 Client Secret을 안전하게 보관 못 하므로, Code Verifier/Challenge로 대체하는 확장. 최신 OAuth2 Best Practice. |
| OIDC (OpenID Connect) | OAuth2 위에 인증(Authentication) 레이어를 추가한 프로토콜. ID Token(JWT)으로 사용자 신원 확인. "OAuth2는 인가, OIDC는 인증"의 차이를 설명 가능. |
| 소셜 로그인 실전 | Google/Kakao 소셜 로그인 흐름(사용자 → Google 로그인 → Authorization Code → 내 서버에서 Access Token 교환 → 사용자 정보 조회 → 내 서비스 JWT 발급)을 설명 가능. |

### Step 8. 시크릿 관리 — 하드코딩 금지, Vault, AWS Secrets Manager

| 학습 항목 | 학습 목표 |
|----------|----------|
| 시크릿이란 | DB 비밀번호, API 키, 토큰 서명 키, 인증서 등 노출되면 안 되는 민감 정보. |
| 하드코딩의 위험 | 소스 코드에 비밀번호를 직접 입력 → Git에 커밋 → 레포지토리 공개 또는 퇴사자가 반출. GitHub에 AWS 키가 노출되어 수천만 원 과금된 실제 사례를 설명 가능. |
| 환경 변수 | 가장 기본적인 시크릿 분리. application.yml에서 `${DB_PASSWORD}`로 참조. 단점(환경 변수 관리 어려움, 로그에 노출 위험)을 설명 가능. |
| HashiCorp Vault | 시크릿 중앙 관리 도구. 동적 시크릿(DB 비밀번호를 일시적으로 생성/폐기), 시크릿 교체(Rotation), 감사 로그. 개념 수준 설명 가능. |
| AWS Secrets Manager | AWS 관리형 시크릿 저장소. 자동 교체(Rotation), IAM 기반 접근 제어, RDS 비밀번호 자동 교체 연동. 개념 수준 설명 가능. |
| AWS Parameter Store | Secrets Manager보다 단순/저렴. 일반 설정 + 암호화된 시크릿을 함께 관리. Secrets Manager와의 차이(자동 교체 유무, 비용)를 설명 가능. |
| Spring Boot 연동 | spring.config.import로 AWS Parameter Store/Secrets Manager에서 설정을 로딩하는 구조를 개념 수준 설명 가능. |
| .gitignore + .env | .env 파일에 시크릿 저장 + .gitignore에 등록하여 Git에 커밋 방지하는 기본 원칙. |

### Step 9. 인프라 보안 — Docker/K8s/클라우드 보안

| 학습 항목 | 학습 목표 |
|----------|----------|
| Docker 이미지 보안 | 비루트(non-root) 사용자로 컨테이너 실행해야 하는 이유를 설명 가능. Trivy 등으로 이미지 취약점(CVE) 스캔하는 방법을 설명 가능. 최소 베이스 이미지(distroless, alpine) 사용으로 공격 면적을 줄이는 원칙을 설명 가능. (Docker 학습 Step 4 보안과 연계) |
| K8s RBAC | ServiceAccount, Role, RoleBinding으로 Pod의 K8s API 접근 권한을 제어하는 원리를 설명 가능. 최소 권한 원칙(Least Privilege) 적용 이유를 설명 가능. (K8s 학습 Step 10 RBAC과 연계) |
| K8s 시크릿 관리 | K8s Secret이 Base64 인코딩이지 암호화가 아닌 이유를 설명 가능. etcd 암호화(Encryption at Rest), External Secrets Operator(AWS Secrets Manager 연동)로 보완하는 방법을 개념 수준 설명 가능. |
| 클라우드 IAM 최소 권한 | AWS IAM에서 와일드카드(*)를 쓰면 안 되는 이유. 필요한 Action + Resource만 허용하는 정책 작성 원칙을 설명 가능. (AWS 학습 Step 3 IAM과 연계) |
| 네트워크 보안 | K8s NetworkPolicy로 Pod 간 통신을 제한하는 개념. VPC 보안 그룹으로 포트/IP를 제한하는 원칙. "기본 거부(Default Deny) + 필요한 것만 허용"을 설명 가능. |

### Step 10. Spring Security 보안 설정 — CORS, CSRF, 헤더 보안

| 학습 항목 | 학습 목표 |
|----------|----------|
| CORS (Cross-Origin Resource Sharing) | 브라우저의 동일 출처 정책(Same-Origin Policy) 때문에 다른 도메인에서 API 호출이 차단되는 이유를 설명 가능. Preflight 요청(OPTIONS)이 발생하는 메커니즘을 설명 가능. Spring Security에서 CorsConfigurationSource로 허용 Origin/Method/Header를 설정하는 방법을 알고 있음. |
| CSRF (Cross-Site Request Forgery) | 사용자의 인증된 세션을 악용하여 공격자가 의도한 요청을 보내는 공격. 예: 사용자가 로그인한 상태에서 악성 사이트 방문 → 자동으로 송금 API 호출. 방어: CSRF 토큰. 세션 기반에서는 필수, JWT(Stateless)에서는 비활성화 가능한 이유를 설명 가능. |
| XSS (Cross-Site Scripting) 방어 | 사용자 입력에 `<script>` 태그를 주입하여 다른 사용자의 브라우저에서 실행. 방어: 출력 시 HTML 이스케이프, Content-Security-Policy 헤더, HttpOnly 쿠키(JS로 쿠키 접근 차단). |
| 보안 헤더 | X-Content-Type-Options(MIME 스니핑 방지), X-Frame-Options(클릭재킹 방지), Strict-Transport-Security(HSTS), Content-Security-Policy(XSS 방지). Spring Security가 기본 설정해주는 헤더들을 설명 가능. |
| Spring Security 연동 | SecurityFilterChain에서 CORS, CSRF, 헤더 보안을 설정하는 코드 패턴을 설명 가능. (학습_05 Spring Security Step 17~18과 연계) |

### Step 11. 보안 실전 — 코드 리뷰 + 데이터 보안 + 감사 로그

| 학습 항목 | 학습 목표 |
|----------|----------|
| SQL Injection 식별 | 코드에서 문자열 연결로 SQL을 만드는 패턴(`"SELECT * FROM users WHERE id = '" + userId + "'"`)을 발견하고 PreparedStatement로 개선 제안 가능. MyBatis `${}` 사용을 `#{}`로 교체 제안 가능. |
| XSS 식별 | 사용자 입력을 그대로 HTML에 출력하는 패턴을 발견하고 이스케이프 처리 제안 가능. |
| 시크릿 노출 식별 | 소스 코드/설정 파일에 비밀번호/API 키가 하드코딩된 패턴을 발견하고 환경 변수/Secrets Manager로 전환 제안 가능. |
| 인가 누락 식별 | API 엔드포인트에 인가 체크(@PreAuthorize, 서비스 레벨 권한 검증)가 없는 패턴을 발견 가능. |
| 로깅 취약점 | 로그에 비밀번호, 토큰, 개인정보가 기록되는 패턴을 발견하고 마스킹 제안 가능. |
| 보안 체크리스트 | ① 입력 검증(화이트리스트), ② 출력 이스케이프, ③ 파라미터 바인딩, ④ 인가 검증, ⑤ 시크릿 분리, ⑥ HTTPS 강제, ⑦ 보안 헤더, ⑧ 의존성 취약점 스캔. 8가지 항목을 코드 리뷰 시 점검 가능. |
| 개인정보 암호화 (ERP 심화) | DB 내 민감 데이터(주민번호, 계좌번호, 카드번호)의 컬럼 레벨 암호화 방식을 설명 가능. **애플리케이션 레벨 암호화**(AES-256으로 Java에서 암/복호화 후 DB에 저장) vs **DB 레벨 암호화**(Oracle TDE: Transparent Data Encryption)의 차이와 트레이드오프(검색 가능 여부, 성능, 키 관리)를 설명 가능. 개인정보보호법에 따른 암호화 의무 대상(고유식별정보, 비밀번호, 바이오정보)을 알고 있음. |
| 감사 로그 (Audit Log, ERP 심화) | "누가(who) 언제(when) 어떤 데이터를(what) 어떤 동작을(action) 했는가"를 불변(Immutable)으로 기록하는 설계. 감사 로그가 삭제/수정 불가능해야 하는 이유(법적 증거, 내부 감사)를 설명 가능. 구현 방식: ① AOP + 이벤트 기반 자동 기록, ② 별도 감사 테이블(audit_log), ③ Append-Only(UPDATE/DELETE 금지). ERP에서 "수주 금액을 누가 변경했는가?"를 추적하는 실무 시나리오에 연결 가능. 이벤트 소싱(DDD 학습 Step 14)과의 유사성을 설명 가능. |
