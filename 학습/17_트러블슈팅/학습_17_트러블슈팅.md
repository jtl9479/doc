## 1. 개요

**현재 수준**: ERP 운영 중 발생하는 에러를 로그로 확인하여 수정하는 수준. Thread Dump/Heap Dump 분석, 체계적 장애 대응 프로세스 경험 없음.
**학습 목표**: 프로덕션 장애 시 "감지 → 격리 → 진단 → 복구 → 회고"를 체계적으로 수행 가능. Thread/Heap Dump를 분석하여 원인을 진단 가능. 장애 보고서를 작성 가능.
**분기 배정**: 3분기 (2026.10 ~ 2026.12)

### Step 1. 트러블슈팅 개요 — 왜 트러블슈팅 역량이 중요한가

| 학습 항목 | 학습 목표 |
|----------|----------|
| 왜 중요한가 | "코드를 잘 짜는 것"과 "문제를 잘 찾는 것"은 다른 역량. 시니어가 주니어와 차별화되는 핵심이 트러블슈팅(문제 발생 시 빠르고 체계적으로 원인을 찾아 해결하는 능력)임을 이해. |
| 트러블슈팅 vs 디버깅 | 디버깅: IDE에서 브레이크포인트 걸고 코드 추적. 트러블슈팅: 프로덕션 환경에서 로그/메트릭/덤프만으로 원인을 추적. 프로덕션에서는 브레이크포인트를 걸 수 없음. |
| 시니어 면접에서의 트러블슈팅 | "프로덕션에서 장애가 발생하면 어떻게 대응하시겠습니까?", "응답이 갑자기 느려졌을 때 어디부터 확인합니까?", "OOM이 발생하면 어떻게 진단합니까?" — 실제 경험 기반 답변이 필요. |
| 트러블슈팅의 핵심 원칙 | ① 추측하지 말고 데이터(로그/메트릭/덤프)를 본다, ② 한 번에 하나씩 변경한다, ③ 재현 가능한 환경을 만든다, ④ 기록한다(나중에 같은 문제 재발 방지). |

### Step 2. 체계적 진단 프로세스 — 감지 → 격리 → 진단 → 복구 → 회고

| 학습 항목 | 학습 목표 |
|----------|----------|
| 1단계: 감지 (Detection) | 모니터링 알림(Grafana/CloudWatch), 사용자 신고, 헬스 체크 실패로 장애를 인지. "무엇이 이상한가"를 빠르게 파악하는 방법. |
| 2단계: 격리 (Isolation) | 장애 범위를 확인. 전체 시스템인가 특정 서비스/기능인가? 특정 사용자/데이터인가? 영향 범위를 좁혀서 피해를 최소화(예: Circuit Breaker 동작, 트래픽 전환). |
| 3단계: 진단 (Diagnosis) | 원인을 추적. 로그 확인 → 메트릭 확인 → 덤프 분석 → 코드 추적 순서. "최근에 무엇이 변경되었는가"(배포, 설정 변경, 트래픽 변화)를 최우선 확인. |
| 4단계: 복구 (Recovery) | 원인 해결 또는 임시 조치(롤백, 재시작, 스케일 아웃). 완전한 원인 해결이 오래 걸리면 임시 조치 먼저 → 서비스 복구 → 이후 근본 원인 해결. |
| 5단계: 회고 (Postmortem) | 장애 보고서 작성. 타임라인, 근본 원인, 영향 범위, 조치 내역, 재발 방지책. "누구의 잘못인가"가 아니라 "시스템/프로세스의 어떤 부분이 개선되어야 하는가"에 집중(Blameless Postmortem). |
| ERP 장애 시나리오 | "출고 화면이 갑자기 안 열린다" → 로그 확인(에러 메시지) → DB 확인(락 경합?) → 최근 배포 확인 → 원인 식별 → 해결 → 보고. 본인 경험과 연결. |

### Step 3. 로그 설계 — 구조화 로그, 로그 레벨, 추적 ID

| 학습 항목 | 학습 목표 |
|----------|----------|
| 왜 로그 설계가 중요한가 | 트러블슈팅의 1차 자료가 로그. 로그가 잘 설계되어 있지 않으면 장애 시 원인 추적 불가. "로그는 작성하는 시점이 아니라 읽는 시점에 가치가 결정된다". |
| 구조화 로그 (Structured Logging) | 텍스트 로그 vs JSON 구조화 로그. JSON이 검색/필터링/집계에 유리한 이유. Logback + logstash-logback-encoder로 JSON 로그를 설정하는 방법을 설명 가능. |
| 로그 레벨 전략 | **ERROR**(즉시 조치 필요, 알림 발송), **WARN**(잠재적 문제, 주시 필요), **INFO**(정상 흐름의 핵심 이벤트), **DEBUG**(개발 시 상세 추적), **TRACE**(가장 상세). 프로덕션에서 INFO 이상만 남기는 이유와, 장애 시 특정 패키지만 DEBUG로 동적 변경하는 방법(Actuator loggers 엔드포인트)을 설명 가능. |
| 추적 ID (Correlation ID) | 하나의 요청에 고유 ID(traceId)를 부여하여 여러 서비스/계층의 로그를 연결. MDC(Mapped Diagnostic Context)에 traceId를 넣는 방법. "이 에러가 어떤 요청에서 발생했는가"를 추적 가능. |
| 로그에 넣어야 할 것 / 넣으면 안 되는 것 | 넣어야 할 것: 요청 ID, 사용자 ID, 요청 URL, 응답 시간, 에러 메시지/스택트레이스. 넣으면 안 되는 것: 비밀번호, 토큰, 주민번호, 카드번호(마스킹 필수). |

### Step 4. 로그 기반 진단 — 로그에서 원인 찾기, 패턴 인식

| 학습 항목 | 학습 목표 |
|----------|----------|
| 에러 로그 읽기 | Java 스택트레이스를 읽고 "어디서(클래스:라인), 왜(예외 타입), 무엇이(메시지)" 발생했는지 즉시 파악 가능. Caused by 체인을 따라가 근본 원인을 찾는 방법. |
| 흔한 에러 패턴 | NullPointerException(null 체크 누락), ClassCastException(타입 불일치), SQLException(쿼리 오류/커넥션 부족), TimeoutException(외부 호출 지연), OutOfMemoryError(메모리 부족). 각각의 대응을 설명 가능. |
| 로그 타임라인 분석 | 장애 발생 시점 전후의 로그를 시간순으로 분석. "정상 → 경고 → 에러"의 전이 패턴을 식별하여 원인 시점을 특정. |
| 로그 검색 도구 | grep/awk(단일 서버), ELK/Loki(중앙 집중). traceId로 요청 흐름 전체를 추적하는 실습. |
| "최근에 무엇이 변경되었는가" | 장애 시 가장 먼저 확인할 것: 최근 배포, 설정 변경, 트래픽 변화, 외부 시스템 변경. 80%의 장애는 "최근 변경"이 원인. |

### Step 5. Thread Dump 분석 — 데드락, 스레드 고갈, 블로킹 진단

| 학습 항목 | 학습 목표 |
|----------|----------|
| Thread Dump란 | 특정 시점에 JVM의 모든 스레드 상태를 캡처한 스냅샷. "지금 이 순간 각 스레드가 무엇을 하고 있는가"를 보여줌. |
| Thread Dump 생성 방법 | `jstack <PID>`, `kill -3 <PID>`, VisualVM, Spring Boot Actuator `/actuator/threaddump`. 프로덕션에서 안전하게 덤프를 뜨는 방법. |
| 스레드 상태 읽기 | **RUNNABLE**(실행 중), **WAITING**(대기, notify 필요), **TIMED_WAITING**(시간 제한 대기, sleep/wait(timeout)), **BLOCKED**(모니터 락 대기). 각 상태의 의미와 정상/비정상 판단 기준. |
| 데드락 진단 | Thread Dump에서 "Found one Java-level deadlock" 메시지. 스레드 A가 락1 보유 + 락2 대기, 스레드 B가 락2 보유 + 락1 대기 패턴을 식별. 해결: 락 순서 통일, tryLock 타임아웃. |
| 스레드 고갈 진단 | 모든 스레드가 BLOCKED/WAITING 상태 → 새 요청 처리 불가. Tomcat 스레드 풀이 모두 소진된 상태. 원인: 외부 API 타임아웃 미설정, DB 커넥션 대기, 느린 동기 호출. |
| 블로킹 원인 추적 | BLOCKED 스레드의 "waiting to lock <주소>"에서 해당 락을 보유한 스레드를 찾아 "왜 오래 걸리는가"를 추적하는 방법. |
| Virtual Thread 진단 (Java 21+, 심화) | 기존 jstack으로는 가상 스레드가 수백만 개일 때 출력이 과도. `jcmd <PID> Thread.dump_to_file -format=json <file>`로 가상 스레드 포함 JSON 덤프 생성하는 방법. 가상 스레드가 synchronized 블록에서 **Pinning**(carrier thread에 고정)되어 처리량이 급락하는 현상을 덤프에서 식별하는 방법. `-Djdk.tracePinnedThreads=full` JVM 옵션으로 Pinning 발생 시 스택트레이스를 로그에 출력하는 설정. (Java 학습 Step 12 Virtual Thread와 연계) |
| 실습 | 의도적으로 데드락/스레드 고갈을 유발하는 코드 작성 → Thread Dump 생성 → 분석 → 원인 식별 연습. |

### Step 6. Heap Dump 분석 — 메모리 누수, OOM 진단

| 학습 항목 | 학습 목표 |
|----------|----------|
| Heap Dump란 | 특정 시점에 JVM 힙 메모리의 전체 스냅샷. "어떤 객체가 얼마나 메모리를 차지하고 있는가"를 보여줌. |
| Heap Dump 생성 방법 | `jmap -dump:format=b,file=heap.hprof <PID>`, `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path`(OOM 시 자동 생성). 프로덕션에서 OOM 자동 덤프 설정이 필수인 이유. |
| Eclipse MAT (Memory Analyzer Tool) | Heap Dump 분석 도구. **Leak Suspects Report**(자동 누수 의심 리포트), **Dominator Tree**(가장 큰 객체 트리), **Histogram**(클래스별 객체 수/크기). 각 뷰의 역할을 설명 가능. |
| 메모리 누수 패턴 | ① 컬렉션에 객체를 추가만 하고 제거 안 함(static List에 계속 add), ② 이벤트 리스너 등록 후 해제 안 함, ③ 캐시에 무한 적재(TTL/사이즈 제한 없음), ④ ThreadLocal 정리 안 함. 각 패턴을 식별 가능. |
| OOM 유형별 진단 | `java.lang.OutOfMemoryError: Java heap space`(힙 부족) → Heap Dump로 큰 객체 확인. `Metaspace`(클래스 메타 부족) → 클래스 로더 누수 의심. `unable to create native thread`(스레드 생성 실패) → 스레드 수 제한/메모리 부족. |
| 실습 | 의도적으로 메모리 누수를 유발하는 코드 작성 → OOM 발생 → Heap Dump 자동 생성 → MAT으로 분석 → 누수 객체 식별 연습. |

### Step 7. GC 로그 분석 — GC Pause, STW, 메모리 압박 진단

| 학습 항목 | 학습 목표 |
|----------|----------|
| GC 로그 활성화 | `-Xlog:gc*:file=gc.log:time,uptime,level,tags`(Java 9+), `-verbose:gc -Xloggc:gc.log`(Java 8). GC 로그를 항상 켜두는 것이 프로덕션 기본 설정인 이유(성능 영향 거의 없음)를 설명 가능. |
| GC 로그 읽기 | Minor GC(Young 영역), Major GC(Old 영역), Full GC(전체) 각 이벤트의 의미. Before/After 힙 사용량, GC Pause 시간을 읽을 수 있음. |
| 비정상 GC 패턴 | ① Full GC가 빈번(Old 영역 부족, 메모리 누수 의심), ② GC 후에도 힙이 줄지 않음(누수), ③ GC Pause가 수 초(STW로 응답 지연). 각 패턴의 원인과 대응. |
| GC 분석 도구 | GCViewer, GCEasy(온라인) 등으로 GC 로그를 시각화하여 패턴을 분석하는 방법을 알고 있음. |
| GC 튜닝 기본 | 힙 크기 조정(-Xms/-Xmx), GC 알고리즘 선택(G1/ZGC), MaxGCPauseMillis 목표 설정. (Java 학습 Step 13과 연계) |

### Step 8. Slow Response 진단 — APM, 병목 추적, 프로파일링

| 학습 항목 | 학습 목표 |
|----------|----------|
| "느려졌다"의 진단 순서 | ① 어디가 느린가? (Grafana HTTP 응답 시간 그래프 → 특정 API 식별) → ② 왜 느린가? (로그에서 해당 API의 처리 시간 분석) → ③ 어디서 시간을 쓰는가? (DB 쿼리? 외부 API? 비즈니스 로직?). |
| APM (Application Performance Monitoring) | 요청별 처리 시간을 자동 추적하는 도구. 각 단계(Controller → Service → Repository → 외부 호출)별 소요 시간을 분해하여 병목을 식별. 대표 도구: Pinpoint, Elastic APM, Datadog APM. 개념 수준 설명 가능. |
| Spring Boot에서의 추적 | Micrometer Timer로 메서드별 실행 시간 측정. `@Timed` 어노테이션. Spring Actuator `/actuator/metrics/http.server.requests`에서 요청별 P99 확인. |
| DB 병목 진단 | 슬로 쿼리 로그 확인 → 실행계획 분석 → 인덱스 확인. (DB 학습 Step 2, 8과 연계) |
| 외부 API 병목 | 타임아웃 설정 확인, 응답 시간 로깅, Circuit Breaker 상태 확인. |
| CPU 프로파일링 | async-profiler로 CPU 사용률이 높은 메서드를 식별하는 방법. Flame Graph 읽기. 개념 수준 설명 가능. |
| JFR + JMC (심화) | **JFR(Java Flight Recorder)**: JVM 내장 프로파일링 도구. 프로덕션 환경에서 **1% 미만 오버헤드**로 CPU/메모리/GC/I/O/스레드/락 등 세밀한 활동을 기록. `-XX:StartFlightRecording=duration=60s,filename=recording.jfr`로 60초간 기록하는 방법. 간헐적 성능 저하처럼 재현 어려운 문제에 "항상 켜놓고 사후 분석"하는 전략. **JMC(Java Mission Control)**: JFR 녹화를 시각화 분석하는 GUI 도구. CPU 핫 메서드, 메모리 할당 핫스팟, GC 패턴, 스레드 경합을 한눈에 파악. "원인을 알 수 없는 간헐적 성능 저하"를 프로덕션에서 안전하게 추적하는 시니어의 도구임을 설명 가능. |

### Step 9. DB 트러블슈팅 — 슬로 쿼리, 락 경합, 커넥션 고갈

| 학습 항목 | 학습 목표 |
|----------|----------|
| (DB 학습 Step 7~8과 연계, 여기서는 트러블슈팅 관점으로 정리) | |
| "화면이 멈췄다" → DB 락 의심 | V$LOCK/V$SESSION으로 블로커 식별 → 블로킹 SQL 확인 → 원인(긴 트랜잭션, 미커밋) 해결. |

### Step 10. 인프라 트러블슈팅 — CPU/메모리/디스크/네트워크

| 학습 항목 | 학습 목표 |
|----------|----------|
| CPU 사용률 높음 | top/htop으로 CPU 사용 프로세스 확인. Java 앱이면 → Thread Dump로 어떤 스레드가 CPU를 소비하는지 확인. 무한 루프, GC 과다, 정규식 ReDoS 등 의심. |
| 메모리 사용률 높음 | free -h로 메모리 확인. Java 앱이면 → JVM 힙(Heap Dump) + OS 네이티브 메모리 구분. 컨테이너에서 RSS > 메모리 Limit이면 OOMKilled. |
| 디스크 부족 | df -h로 확인. 로그 파일이 디스크를 가득 채운 경우(로그 Rotation 미설정). 임시 파일 누적. |
| 네트워크 문제 | ping/traceroute로 연결 확인. DNS 해석 실패(nslookup). 포트 차단(telnet host port). 타임아웃 빈발(네트워크 지연/패킷 유실). |
| Linux 진단 도구 (기본) | top(CPU/메모리), free(메모리), df(디스크), netstat/ss(네트워크 연결), iostat(디스크 I/O), vmstat(시스템 전반). 각 도구의 역할과 기본 사용법. |
| 하위 레벨 진단 도구 (심화) | **lsof**(List Open Files): 프로세스가 열고 있는 파일/소켓/파이프 목록. "Too many open files" 에러 시 어떤 프로세스가 파일 핸들을 소비하는지 식별. `lsof -p <PID>`, `lsof -i :8080`(특정 포트). **tcpdump/Wireshark**: 네트워크 패킷 캡처. 애플리케이션 로그에 아무것도 안 찍히는 "좀비 커넥션", TCP 핸드셰이크 실패, DNS 해석 지연을 패킷 레벨에서 진단. `tcpdump -i eth0 port 8080 -w capture.pcap`. **strace**: 프로세스의 시스템 콜을 추적. "프로세스가 뭘 하고 있는지 전혀 모르겠다"일 때 마지막 수단. `strace -p <PID> -e trace=network`(네트워크 관련 시스템 콜만). 각 도구가 "애플리케이션 로그로 안 보이는 문제"를 OS 레벨에서 진단하는 수단임을 설명 가능. |

### Step 11. 컨테이너/K8s 트러블슈팅 — CrashLoop, OOMKilled, Pod 장애

| 학습 항목 | 학습 목표 |
|----------|----------|
| (K8s 학습 Step 16과 연계, 여기서는 트러블슈팅 관점으로 심화) | |
| CrashLoopBackOff | 컨테이너 시작 → 즉시 종료 → 재시작 반복. 진단: kubectl logs --previous(이전 컨테이너 로그) → kubectl describe pod(이벤트) → 앱 에러/설정 오류/리소스 부족 확인. |
| OOMKilled | 컨테이너 메모리 Limit 초과. Exit Code 137. 진단: JVM 힙(-XX:MaxRAMPercentage) + 메모리 Limit 관계 확인. 힙 외 메모리(Metaspace, 스레드 스택, 네이티브)도 고려. |
| ImagePullBackOff | 이미지 Pull 실패. 이미지명 오타, 레지스트리 인증 실패, 네트워크 문제. |
| Pending | Pod가 스케줄링 안 됨. Node 리소스 부족, Taint/Toleration 불일치, PVC 바인딩 실패. |
| 진단 순서 정리 | kubectl get pods → 상태 확인 → kubectl describe pod → 이벤트 확인 → kubectl logs → 앱 로그 확인 → 리소스/설정/이미지 확인. |

### Step 12. 의도적 장애 주입 — 카오스 엔지니어링 기초

| 학습 항목 | 학습 목표 |
|----------|----------|
| 카오스 엔지니어링이란 | "운영 환경에서 장애를 의도적으로 발생시켜 시스템의 약점을 사전에 발견"하는 방법론. Netflix가 Chaos Monkey로 시작. |
| 왜 의도적 장애를 주입하는가 | 장애는 "발생할지 모르는 것"이 아니라 "반드시 발생하는 것". 사전에 발견하면 대응 준비 가능. "프로덕션에서 처음 겪는 장애"가 가장 위험. |
| Docker 환경에서의 장애 주입 | Kafka 브로커 컨테이너 중지(docker stop kafka) → 프로듀서/컨슈머 동작 확인. Redis 컨테이너 중지 → 캐시 미스 시 앱 동작 확인. DB 커넥션 수 제한 → 커넥션 풀 고갈 시뮬레이션. |
| 장애 주입 후 확인 항목 | ① 에러가 적절히 로깅되는가, ② 사용자에게 적절한 에러 메시지가 노출되는가, ③ Circuit Breaker가 동작하는가, ④ 장애 복구 후 정상 복귀되는가, ⑤ 데이터 정합성이 유지되는가. |
| 카오스 도구 | Chaos Monkey for Spring Boot, Litmus(K8s 카오스), Gremlin의 존재를 개념 수준 알고 있음. |

### Step 13. 장애 보고서 작성 — 포맷, 타임라인, 근본 원인, 재발 방지

| 학습 항목 | 학습 목표 |
|----------|----------|
| 왜 장애 보고서를 쓰는가 | 같은 장애 재발 방지, 팀 지식 공유, 프로세스 개선. "기억에 의존하면 같은 실수를 반복한다". |
| 장애 보고서 포맷 | **제목**(무엇이 발생했는가), **심각도**(Critical/Major/Minor), **영향 범위**(사용자 수, 기능), **타임라인**(감지 → 조치 → 복구 시간순 기록), **근본 원인**(Root Cause, "왜 5번" 기법으로 파고들기), **조치 내역**(임시 조치 + 근본 해결), **재발 방지책**(Action Items + 담당자 + 기한). |
| Blameless Postmortem | "누가 잘못했는가"가 아니라 "시스템/프로세스의 어떤 부분이 개선되어야 하는가"에 집중. 비난 문화에서는 팀원이 문제를 숨김 → 더 큰 장애로 이어짐. |
| "왜 5번" 기법 (5 Whys) | "서버가 다운됐다" → 왜? "메모리 부족" → 왜? "캐시에 무한 적재" → 왜? "TTL 미설정" → 왜? "코드 리뷰에서 놓침" → 왜? "캐시 설정 체크리스트가 없음" → **근본 원인: 캐시 설정 체크리스트 부재**. 표면 원인이 아닌 근본 원인을 찾는 방법. |
| 학습 중 장애 보고서 실전 | 학습 과정에서 발생하는 모든 에러(빌드 실패, 런타임 에러, 설정 오류)를 장애 보고서 형식으로 기록하는 습관. 3건 이상 작성 목표. |
| 런북 (Runbook) 작성 (심화) | 동일 장애 발생 시 **주니어도 대응할 수 있도록** 단계별 조치 가이드를 문서화. 구조: **증상**(어떤 알림이 오는가) → **확인 항목**(어떤 메트릭/로그를 보는가) → **조치 절차**(1단계: 재시작, 2단계: 스케일 아웃, 3단계: 에스컬레이션) → **에스컬레이션 기준**(언제 시니어/운영팀에 알리는가). 시니어는 혼자 문제를 해결하는 사람이 아니라 "팀과 시스템이 스스로 복구할 수 있는 구조"를 만드는 사람임을 설명 가능. |
| 자동 복구 (Auto-remediation) 개념 (심화) | 특정 메트릭 임계치 도달 시 자동 대응: **K8s HPA**(CPU > 80% → Pod 증가), **K8s Liveness Probe**(헬스 체크 실패 → 자동 재시작), **CloudWatch Alarm + Lambda**(알림 → 자동 스크립트 실행). "모든 장애에 사람이 개입할 필요 없다"는 원칙. 자동 복구 가능한 장애(일시적 과부하, OOM)와 불가능한 장애(데이터 손상, 버그)를 구분하는 판단 기준을 설명 가능. |

| 학습 항목 | 학습 목표 |
|----------|----------|

- [ ] "K8s Pod가 OOMKilled면?" → JVM 힙 + 컨테이너 Limit 관계 설명 가능
- [ ] "lsof/tcpdump/strace는 언제 쓰는가?" → 애플리케이션 로그로 안 보이는 OS 레벨 문제 진단 설명 가능

> 사용자가 "트러블슈팅 공부하자" 또는 "Step N 하자"라고 하면, 진행 상태를 확인하고 다음 미시작 Step부터 학습_템플릿.md 형식으로 진행합니다.
> 트러블슈팅은 **시나리오 기반 학습**이 핵심입니다. Claude가 "이런 장애가 발생했다" 시나리오를 제시 → 사용자가 진단 순서를 답변 → Claude가 피드백하는 방식으로 진행합니다.
