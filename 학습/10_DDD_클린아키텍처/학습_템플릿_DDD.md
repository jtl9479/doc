# DDD/클린 아키텍처 학습 템플릿

> 유형: **개념 + 도메인 모델링 + 설계 토론**
> 적용: 학습_10_DDD_클린아키텍처.md의 Step 1~16

## 공통 원칙

| 원칙 | 설명 |
|------|------|
| **왜 먼저** | "DDD 없이 개발하면 이런 문제(빈혈 모델, 거대 서비스, 도메인 오염)" |
| **비유 먼저** | DDD/아키텍처 개념을 일상 비유로 직관 잡기 |
| **트레이드오프** | DDD/헥사고날/클린 적용에도 비용이 있음. 과도한 적용 경계 |

### 비유 예시
```
Bounded Context = "부서. 같은 '주문'이라도 영업부(수주)와 물류부(출고)에서 의미가 다름"
Aggregate = "가족 단위 이사. 가족(Order+OrderItem)은 함께 움직이고, 이웃(Customer)은 주소(ID)만 알면 됨"
Entity vs VO = "주민번호가 있는 사람(Entity) vs 만원 지폐(VO). 사람은 ID로 구분, 만원은 다른 만원과 구분 불필요"
Repository = "도서관 사서. 책(Aggregate)을 찾아주고 보관. 어떤 서가에 있는지(DB)는 사서만 앎"
헥사고날 = "어댑터 멀티탭. 핵심(도메인)은 변하지 않고, 플러그(DB, API)만 교체"
클린 아키텍처 = "양파 껍질. 중심(Entity)은 바깥(프레임워크)을 모름. 바깥이 중심에 맞춤"
빈혈 모델 = "조수석에 앉아서 운전사에게 다 지시하는 사장(Service가 다 함, Entity는 멍 때림)"
풍부한 모델 = "직접 운전하는 사장(Entity가 비즈니스 로직 수행)"
```

### 트레이드오프 예시
```
DDD 적용: 도메인 표현력↑ 유지보수↑ ↔ 학습 곡선↑ 코드량↑ 단순 CRUD엔 과도
헥사고날: 외부 교체 용이↑ 테스트↑ ↔ 코드 구조 복잡↑ 인터페이스 많음
모듈러 모놀리스: 단순+정합성 ↔ 독립 배포/확장 불가
MSA: 독립 배포/확장 ↔ 분산 복잡성+운영 비용
이벤트 소싱: 완전한 이력↑ ↔ 복잡성↑ 스냅샷 필요, 스키마 진화 어려움
```

## 설명 흐름
1. **왜 써야 하는가**: "이것 없이 코드를 짜면 6개월 후 이렇게 망가진다"
2. **비유로 직관 잡기**: ERP 도메인으로 번역
3. **핵심 개념 + Bad/Good 코드** (빈혈 → 풍부, 레이어드 → 헥사고날)
4. **설계 토론**: "이 도메인을 어떻게 나눌 것인가?" → 사용자 참여 → 피드백
5. **트레이드오프**: "DDD를 적용하면 좋지만, 이 비용이 있다"
6. **오해하기 쉬운 부분**:
```
"DDD = Entity, VO, Repository 네이밍" → 전략 없는 전술은 무의미. Bounded Context가 먼저
"Aggregate를 크게 만들면 안전하다" → 크면 트랜잭션 경합 + 성능 저하. 작게 유지
"헥사고날 = 모든 프로젝트에 적용" → 단순 CRUD에는 레이어드가 더 효율적
"도메인 이벤트 = Kafka" → 모듈러 모놀리스에서는 Spring ApplicationEvent로 충분
"JPA Entity = DDD Entity" → JPA는 영속성 매핑, DDD Entity는 비즈니스 개념. 분리 가능
```
7. **확인 질문**: 사용자 답변 → 피드백
```
Step 5: "수주(SM)와 재고(IS)가 다른 Bounded Context인 이유는?"
Step 7: "이 Aggregate 경계를 왜 이렇게 잡았는가?"
Step 9: "이 로직은 Domain Service인가 Application Service인가?"
Step 11: "헥사고날 아키텍처에서 DB를 교체하면 어디를 수정하는가?"
Step 13: "이 프로젝트에 헥사고날이 필요한가, 레이어드로 충분한가?"
Step 16: "이 코드의 DDD 안티패턴은?"
```
8. **안티패턴 식별 연습**
9. **정리 + 다음 안내**

## Step별 특이사항
- 기초 Step(1~3): 레이어드의 한계를 먼저 체감 → DDD 필요성 유도
- 전략 Step(4~5): ERP 모듈 = Bounded Context. 서브도메인(Core/Supporting/Generic)
- 전술 Step(6~10): Bad/Good 코드 + ERP 예시 + Factory 패턴
- 아키텍처 Step(11~13): 패키지 구조 실전 + 모듈러 모놀리스 + ArchUnit
- 실전 Step(15): 전체 ERP를 DDD로 재설계하는 종합 연습
- 안티패턴 Step(16): "이 코드의 DDD 안티패턴은?" 식별 연습
