## 1. 개요

**현재 수준**: ERP 모놀리식 시스템 설계 경험. 분산 시스템·대규모 트래픽 설계 경험 없음.
**학습 목표**: 대규모 시스템 설계 면접에서 요구사항 분석 → 컴포넌트 설계 → 트레이드오프 판단을 30분 내 수행 가능. DDIA 핵심 개념을 자기 말로 설명 가능.
**분기 배정**: 1분기 시작 ~ 2분기 완료 (1분기 60h + 2분기 40h)

### Step 1. 데이터 모델 — 관계형, 문서형, 그래프

| 학습 항목 | 학습 목표 |
|----------|----------|
| 관계형 모델 | 테이블/행/조인 기반. 스키마 강제(Schema-on-Write). 정규화의 장점(중복 제거, 일관성)과 비정규화가 필요한 경우(성능)를 설명 가능. |
| 문서 모델 (Document) | JSON/BSON 기반. 스키마 유연(Schema-on-Read). 1:N 관계를 중첩 문서로 표현하는 장점(조인 불필요, 지역성)을 설명 가능. N:M 관계에 약한 이유를 설명 가능. |
| 그래프 모델 | 노드-엣지 구조. 다대다 관계가 복잡한 경우(소셜 네트워크, 추천) 적합한 이유를 설명 가능. |
| 관계형 vs 문서형 선택 기준 | 데이터 간 관계가 복잡하면 관계형, 문서 단위로 독립적이면 문서형이 유리한 판단 기준을 설명 가능. "어떤 DB를 쓸 것인가?"에 트레이드오프 기반으로 답변 가능. |

### Step 2. 스토리지 엔진 — B-Tree vs LSM-Tree

| 학습 항목 | 학습 목표 |
|----------|----------|
| B-Tree | 대부분의 RDBMS(Oracle, MySQL, PostgreSQL)가 사용. 읽기에 최적화. 페이지 단위 업데이트. Write Amplification(쓰기 증폭)이 발생하는 이유를 설명 가능. |
| LSM-Tree (Log-Structured Merge-Tree) | 쓰기에 최적화. 메모리(Memtable) → 디스크(SSTable) 구조. Compaction 과정을 설명 가능. Cassandra, RocksDB, LevelDB가 사용하는 이유를 설명 가능. |
| B-Tree vs LSM-Tree 선택 기준 | 읽기 많으면 B-Tree, 쓰기 많으면 LSM-Tree가 유리한 이유를 설명 가능. Space Amplification vs Write Amplification 트레이드오프를 설명 가능. |
| 행 지향 vs 열 지향 스토리지 | OLTP(행 지향, 개별 행 접근)와 OLAP(열 지향, 집계 쿼리)의 차이를 설명 가능. 열 지향이 분석 쿼리에 빠른 이유(컬럼 압축, 벡터 처리)를 설명 가능. |

### Step 3. 인코딩과 스키마 진화

| 학습 항목 | 학습 목표 |
|----------|----------|
| 인코딩 형식 비교 | JSON(사람이 읽기 쉬움, 크기 큼), Protocol Buffers(바이너리, 스키마 필수, 크기 작음), Avro(스키마 진화에 강점)의 차이를 설명 가능. |
| 스키마 진화 (Schema Evolution) | 전방 호환성(새 코드가 쓴 데이터를 구 코드가 읽음)과 후방 호환성(구 코드가 쓴 데이터를 새 코드가 읽음)의 차이를 설명 가능. |
| 서비스 간 통신에서의 인코딩 | REST(JSON) vs gRPC(Protocol Buffers) vs 메시지 큐(Avro/JSON)에서 인코딩 선택이 중요한 이유를 설명 가능. |

### Step 4. 복제 — 리더-팔로워, 다중 리더, 리더 없는 복제

| 학습 항목 | 학습 목표 |
|----------|----------|
| 복제의 목적 | 고가용성(한 노드 장애 시 다른 노드가 대체), 읽기 확장성(읽기 부하 분산), 지역성(사용자 가까운 곳에 데이터)을 설명 가능. |
| 리더-팔로워 복제 | 쓰기는 리더에만, 읽기는 팔로워에서 가능한 구조. 동기식 vs 비동기식 복제의 트레이드오프(일관성 vs 지연시간)를 설명 가능. |
| 복제 지연 문제 | "자기 쓰기 읽기(read-your-writes)" 일관성, "단조 읽기(monotonic reads)" 문제를 시나리오로 설명 가능. |
| 리더 장애 대응 (Failover) | 팔로워가 리더로 승격되는 과정. Split Brain(두 노드가 모두 리더라고 주장)의 위험과 방지를 설명 가능. |
| 다중 리더 복제 | 여러 데이터센터에서 각각 쓰기를 허용. 쓰기 충돌 해결 전략(최종 쓰기 승리 LWW, 병합, 사용자 해결)을 설명 가능. |
| 리더 없는 복제 | Dynamo 스타일. 읽기/쓰기 정족수(Quorum: W + R > N)의 의미를 설명 가능. Cassandra/DynamoDB가 사용하는 이유를 설명 가능. |

### Step 5. 파티셔닝 — 키 범위, 해시, 핫스팟, 리밸런싱

| 학습 항목 | 학습 목표 |
|----------|----------|
| 파티셔닝의 목적 | 단일 노드로 감당 못 하는 데이터/트래픽을 여러 노드로 분산하는 이유를 설명 가능. |
| 키 범위 파티셔닝 | 연속 키 기준 분할. 범위 쿼리에 유리. 핫스팟(특정 범위에 쓰기 집중)이 발생하는 사례를 설명 가능. |
| 해시 파티셔닝 | 해시 함수로 균등 분산. 핫스팟 방지. 범위 쿼리가 불가능한 단점을 설명 가능. |
| 핫스팟 문제 | 특정 키(예: 유명인 게시글)에 트래픽이 몰리는 현상. 파티셔닝으로도 해결 안 되는 이유와 대응(키 앞에 랜덤 접두사 추가 등)을 설명 가능. |
| 리밸런싱 | 노드 추가/제거 시 파티션을 재배치하는 과정. 고정 개수 파티셔닝 vs 동적 파티셔닝의 차이를 설명 가능. 리밸런싱 중 서비스 성능 저하(대량 데이터 이동, 네트워크/디스크 I/O 폭증)가 발생하는 이유를 설명 가능. |
| 일관된 해싱 (Consistent Hashing) | 해시 링(Hash Ring) 위에 노드와 키를 배치하는 구조를 그림으로 설명 가능. 노드 추가/제거 시 전체가 아닌 인접 구간의 키만 이동하는 이유를 설명 가능. 가상 노드(Virtual Node)로 불균등 분배를 해결하는 원리를 설명 가능. Cassandra, DynamoDB, Memcached 등에서 사용되는 이유를 알고 있음. |
| 리밸런싱의 실무적 고통 | "샤딩을 한다"는 것과 "샤딩 이후 노드를 확장한다"는 것이 전혀 다른 난이도임을 설명 가능. 데이터 마이그레이션 중 쓰기 충돌, 일시적 데이터 불일치, 성능 저하를 어떻게 관리하는지(점진적 이동, 이중 쓰기, 백그라운드 리밸런싱)를 설명 가능. |
| 세컨더리 인덱스와 파티셔닝 | 로컬 인덱스(각 파티션 독립) vs 글로벌 인덱스(전체 분산)의 트레이드오프를 설명 가능. |

### Step 6. 트랜잭션 — 분산 트랜잭션, 2PC, 합의

| 학습 항목 | 학습 목표 |
|----------|----------|
| 단일 노드 트랜잭션 | ACID 복습 (학습_02에서 상세). 여기서는 분산 환경과의 차이에 집중. |
| 분산 트랜잭션의 어려움 | 네트워크 지연, 부분 실패(일부 노드만 커밋)가 단일 노드 트랜잭션과 근본적으로 다른 이유를 설명 가능. |
| 2PC (Two-Phase Commit) | 코디네이터가 Prepare → Commit/Abort를 조율하는 과정을 설명 가능. 코디네이터 장애 시 참여자가 블로킹되는 문제(In-Doubt 상태)를 설명 가능. |
| 2PC의 한계 | 성능 저하(동기식 대기), 코디네이터 단일 장애점, 실무에서 기피하는 이유를 설명 가능. |
| Saga 패턴 (2PC 대안) | 각 서비스가 로컬 트랜잭션 + 보상 트랜잭션으로 처리. MSA 학습과 연계. "2PC 대신 Saga를 쓰는 이유"를 설명 가능. |

### Step 7. 분산 시스템의 어려움 — 네트워크, 시계, 프로세스 장애

| 학습 항목 | 학습 목표 |
|----------|----------|
| 비신뢰 네트워크 | 분산 시스템에서 네트워크는 "보내면 도착한다"는 보장이 없음을 이해. 메시지 유실, 지연, 순서 역전, 중복 전송이 발생하는 이유를 설명 가능. "요청을 보냈는데 응답이 안 오면, 상대가 죽은 건가 네트워크가 끊긴 건가?" 판별 불가능한 문제를 설명 가능. |
| 타임아웃의 딜레마 | 타임아웃을 짧게 잡으면 살아있는 노드를 죽었다고 오판(false positive), 길게 잡으면 죽은 노드를 늦게 감지. 적정 타임아웃이 존재하지 않는 이유(네트워크 지연은 상한이 없음)를 설명 가능. |
| 비신뢰 시계 (Clock Skew) | 각 노드의 시계가 다를 수 있는 이유(NTP 동기화 한계, 드리프트)를 설명 가능. "이벤트 A가 B보다 먼저 발생했는가?"를 시계만으로 판단하면 안 되는 이유를 설명 가능. Last Write Wins(LWW)에서 시계 불일치가 데이터 손실로 이어지는 시나리오를 설명 가능. |
| 논리적 시계 | 물리적 시계 대신 Lamport Timestamp, Vector Clock으로 이벤트 순서를 추적하는 개념을 설명 가능. |
| 프로세스 일시 정지 | GC Pause로 인해 프로세스가 수 초간 멈출 수 있는 문제를 설명 가능. "리더라고 믿고 있었는데 사실 GC 동안 리더 자격을 잃은 상태"인 시나리오를 설명 가능. Fencing Token으로 방지하는 패턴을 설명 가능. |
| 비잔틴 장애 | 노드가 "거짓말"하는 경우(악의적 또는 버그). 대부분의 시스템은 비잔틴 장애를 고려하지 않는 이유(비용 대비 확률 낮음, 블록체인은 예외)를 설명 가능. |
| 이 챕터의 핵심 교훈 | "분산 시스템에서는 무엇이든 잘못될 수 있다. 네트워크가 끊길 수 있고, 시계가 틀릴 수 있고, 프로세스가 멈출 수 있다. 이걸 전제로 시스템을 설계해야 한다."를 자기 말로 설명 가능. |

### Step 8. 일관성과 합의 — 선형성, 인과성, Raft/Paxos

| 학습 항목 | 학습 목표 |
|----------|----------|
| 선형성 (Linearizability) | "최신 값을 항상 읽는다"의 의미. 선형성이 보장되면 마치 복제본이 1개인 것처럼 동작함을 설명 가능. 선형성이 성능을 떨어뜨리는 이유를 설명 가능. |
| 인과적 일관성 (Causal Consistency) | "원인이 결과보다 먼저"만 보장. 선형성보다 약하지만 성능이 좋은 이유를 설명 가능. |
| 합의 (Consensus) | 여러 노드가 하나의 값에 동의하는 문제. 리더 선출, 원자적 커밋이 합의 문제인 이유를 설명 가능. |
| Raft 알고리즘 | 리더 선출 → 로그 복제 → 안전성의 흐름을 개념 수준으로 설명 가능. etcd, Consul이 Raft를 사용하는 이유를 알고 있음. |
| Paxos | Raft보다 먼저 나온 합의 알고리즘. 이해하기 어렵지만 이론적 기반이라는 것을 알고 있음. 깊이 학습은 불필요. |
| FLP 불가능 정리 | 비동기 네트워크에서 하나의 노드라도 장애가 있으면 합의가 보장되지 않는다는 이론적 한계를 개념 수준 설명 가능. |

### Step 9. CAP 정리와 일관성 모델

| 학습 항목 | 학습 목표 |
|----------|----------|
| CAP 정리 | Consistency(일관성), Availability(가용성), Partition Tolerance(분단 내성) 중 네트워크 분단 시 C와 A 중 하나를 선택해야 하는 이유를 설명 가능. |
| CP vs AP | CP 시스템(일관성 우선, 분단 시 일부 요청 거부. 예: ZooKeeper, etcd)과 AP 시스템(가용성 우선, 분단 시에도 응답. 예: Cassandra, DynamoDB)의 차이를 설명 가능. |
| CAP의 한계 | CAP 정리가 지나치게 단순화된 모델인 이유(네트워크 분단이 아닌 평상시에도 일관성-지연시간 트레이드오프 존재)를 설명 가능. PACELC 모델(분단 시 A/C 선택 + 평상시 Latency/Consistency 선택)을 개념 수준 설명 가능. |
| 일관성 모델 비교 | Strong Consistency(선형성, 항상 최신), Eventual Consistency(결국 일치, 일시적 불일치 허용), Causal Consistency(인과 순서 보장)를 비교 설명 가능. |
| 실제 시스템에 대입 | Kafka(파티션 내 순서 보장, 파티션 간은 보장 안 함), Redis(기본 AP, Cluster 모드에서 일관성 주의), Cassandra(W+R>N으로 튜닝 가능)에 CAP/일관성 모델을 대입하여 설명 가능. |
| Eventual Consistency의 사용자 경험 문제 | "방금 올린 글이 안 보임", "방금 주문했는데 주문 목록에 없음" 등 최종 일관성으로 인해 사용자가 겪는 기이한 현상을 시나리오로 설명 가능. |
| 애플리케이션 레벨 보정 패턴 | **Read-your-writes**: 자기가 쓴 데이터는 리더에서 읽어 즉시 반영하는 패턴을 설명 가능. **낙관적 UI 업데이트**: 서버 응답 전에 클라이언트가 먼저 UI를 업데이트하고 실패 시 롤백하는 패턴을 설명 가능. **폴링/이벤트 기반 갱신**: 일정 시간 후 재조회 또는 WebSocket으로 변경 알림을 받는 패턴을 설명 가능. |
| 비즈니스 관점 판단 | "이 기능에서 강한 일관성이 정말 필요한가, 아니면 최종 일관성 + UI 보정으로 충분한가?"를 업무 요구사항에 맞게 판단 가능. 기술적 한계를 비즈니스적으로 풀어내는 설계 사고를 설명 가능. |

### Step 10. 배치 처리 — MapReduce, 데이터플로 엔진

| 학습 항목 | 학습 목표 |
|----------|----------|
| 배치 처리란 | 대량 데이터를 한꺼번에 처리하는 방식. 실시간이 아닌 지연 처리(분~시간 단위)임을 이해. |
| MapReduce | Map(입력을 키-값으로 변환) → Shuffle(같은 키끼리 그룹핑) → Reduce(그룹별 집계)의 흐름을 설명 가능. Hadoop이 MapReduce를 사용하는 이유를 설명 가능. |
| MapReduce의 한계 | 중간 결과를 디스크에 쓰는 오버헤드, 복잡한 파이프라인 작성의 어려움을 설명 가능. |
| 데이터플로 엔진 | Spark, Flink 등이 MapReduce를 개선한 방식(메모리 처리, DAG 기반 파이프라인)을 개념 수준 설명 가능. |

### Step 11. 스트림 처리 — 이벤트 소싱, CDC, 스트림 조인

| 학습 항목 | 학습 목표 |
|----------|----------|
| 스트림 처리란 | 데이터가 도착하는 즉시 처리하는 방식. 배치 처리와의 차이(지연시간, 처리 단위)를 설명 가능. |
| 메시지 브로커와 이벤트 로그 | RabbitMQ(전통적 메시지 큐, 소비 후 삭제)와 Kafka(이벤트 로그, 재생 가능)의 근본적 차이를 설명 가능. |
| CDC (Change Data Capture) | DB 변경 사항을 실시간으로 캡처하여 다른 시스템에 전파하는 패턴. Debezium 등의 도구 존재를 알고 있음. 활용 사례(검색 인덱스 동기화, 캐시 무효화, 데이터 웨어하우스 적재)를 설명 가능. |
| 이벤트 소싱 (Event Sourcing) | 현재 상태가 아닌 이벤트(변경 이력)를 저장하는 패턴. 장점(완전한 이력, 시간 여행 쿼리)과 단점(복잡성, 스냅샷 필요)을 설명 가능. CQRS와의 관계를 설명 가능. |
| 스트림 조인 | 스트림-스트림 조인(윈도우 기반), 스트림-테이블 조인(DB 조회), 테이블-테이블 조인(CDC 기반)의 차이를 개념 수준 설명 가능. |
| 배치 vs 스트림 통합 | Lambda Architecture(배치 + 스트림 이중 처리)와 Kappa Architecture(스트림만으로 처리)의 차이를 설명 가능. |

### Step 12. 시스템 설계 프레임워크 — 설계 면접 접근법

| 학습 항목 | 학습 목표 |
|----------|----------|
| 4단계 접근법 | **1) 요구사항 정리**(기능/비기능/제약조건) → **2) 대략적 설계**(핵심 컴포넌트, API, 데이터 모델) → **3) 상세 설계**(병목 해결, 스케일링) → **4) 마무리**(트레이드오프 정리, 개선점) 순서로 진행 가능. |
| 요구사항 질문법 | "사용자 수는?", "읽기/쓰기 비율은?", "데이터 보존 기간은?", "일관성 vs 가용성 중 무엇이 더 중요한가?" 등 핵심 질문을 던질 수 있음. |
| 대략적 추정 (Back-of-the-envelope) | DAU, QPS, 저장소 용량, 네트워크 대역폭을 간단히 추정하는 방법. 2의 거듭제곱 + 단위 변환(1일 = 86,400초 ≈ 10만) 감각을 갖추고 있음. |
| 트레이드오프 사고 | "왜 이 방식을 선택했는가? 대안은 무엇이고, 그 대안의 단점은?" 형태로 설계 결정을 정당화 가능. |

### Step 13. 시스템 설계 연습 — URL 단축기, 채팅, 뉴스피드 등

| 학습 항목 | 학습 목표 |
|----------|----------|
| URL 단축기 | 해시 생성(Base62), 충돌 해결, 리다이렉션(301 vs 302), 캐시(읽기 Heavy) 설계를 30분 내 구조도로 그릴 수 있음. |
| 채팅 시스템 | WebSocket, 메시지 저장(NoSQL vs RDBMS), 읽음 표시, 그룹 채팅 설계 포인트를 설명 가능. |
| 뉴스피드 | Fan-out on Write(쓰기 시 팔로워 전파) vs Fan-out on Read(읽기 시 조합)의 트레이드오프를 설명 가능. |
| 알림 시스템 | Push/Pull 방식, 대기열, 중복 제거, 실패 재시도 설계를 설명 가능. |
| 검색 시스템 | 역인덱스(Inverted Index), 파티셔닝(문서 기반 vs 용어 기반), 랭킹의 기본 개념을 설명 가능. |
| 주문/결제 시스템 | 멱등성(Idempotency), 상태 머신, 보상 트랜잭션, 이벤트 기반 설계를 설명 가능. |
| **ERP 경험 연결 — 돈과 정합성 설계 (본인 차별점)** | ERP에서 다루던 **복식 부기(차변/대변 균형) 원칙**을 분산 시스템 정합성 설계에 연결 가능. "모든 금액 이동은 반드시 차변과 대변이 균형을 이뤄야 한다" → 분산 환경에서 이를 보장하려면 멱등성(같은 요청 2번 보내도 1번만 반영) + 보상 트랜잭션(실패 시 역분개) + 이벤트 소싱(거래 이력 완전 보존)이 필수인 이유를 설명 가능. "수주 → 출고 → 매출 → 회계 전표" 흐름이 분산 시스템에서 Saga 패턴(각 단계 로컬 트랜잭션 + 실패 시 보상)과 동일한 구조임을 설명 가능. 면접에서 "주문/결제 시스템을 설계하라"에 대해 본인 ERP 도메인 경험을 녹여 독보적으로 답변 가능. |

### Step 14. 확장성 패턴 — 수평/수직 확장, 캐시, 로드밸런싱, CDN

| 학습 항목 | 학습 목표 |
|----------|----------|
| 수직 확장 vs 수평 확장 | Scale Up(더 큰 서버)과 Scale Out(더 많은 서버)의 차이. 수직 확장의 한계(물리적 상한, 단일 장애점)를 설명 가능. |
| 로드 밸런서 | L4(TCP 레벨) vs L7(HTTP 레벨) 차이. 라운드 로빈, 가중치, 최소 연결 등 알고리즘을 설명 가능. |
| 캐시 전략 | Cache Aside, Read Through, Write Through, Write Behind의 차이를 설명 가능. 캐시 무효화 전략(TTL, 이벤트 기반)을 설명 가능. 캐시 스탬피드/썬더링 허드를 설명 가능. |
| CDN | 정적 콘텐츠를 사용자 가까운 엣지 서버에 배치하는 이유. Push vs Pull CDN의 차이를 설명 가능. |
| DB 읽기 확장 | 읽기 복제본(Read Replica)으로 읽기 부하 분산하는 패턴. 복제 지연(Replication Lag)으로 인한 문제와 대응을 설명 가능. |
| DB 쓰기 확장 | 파티셔닝/샤딩으로 쓰기 부하 분산. 샤딩 키 설계의 중요성과 잘못된 샤딩의 위험(핫스팟, 리밸런싱 비용)을 설명 가능. |

### Step 15. 장애 대응 설계 — 장애 감지, 페일오버, 서킷 브레이커

| 학습 항목 | 학습 목표 |
|----------|----------|
| 장애의 종류 | 크래시 장애(프로세스 죽음), 비잔틴 장애(잘못된 응답), 네트워크 지연/분단의 차이를 설명 가능. |
| 장애 감지 | Heartbeat, Health Check, Timeout 기반 감지. 타임아웃을 너무 짧게/길게 잡을 때의 트레이드오프를 설명 가능. |
| 페일오버 (Failover) | Active-Passive(대기 서버가 인수), Active-Active(양쪽 모두 처리)의 차이를 설명 가능. 자동 페일오버의 위험(Split Brain)을 설명 가능. |
| 서킷 브레이커 (Circuit Breaker) | Closed → Open → Half-Open 상태 전이를 설명 가능. 장애 전파(Cascading Failure) 방지 목적을 설명 가능. Resilience4j 등 구현체 존재를 알고 있음. |
| 멱등성 (Idempotency) | 네트워크 재시도 시 중복 처리를 방지하는 설계. 멱등키(Idempotency Key) 패턴을 설명 가능. |
| Rate Limiting | 과도한 요청을 제한하는 목적(DDoS 방어, 서비스 보호). Token Bucket, Sliding Window 알고리즘을 개념 수준 설명 가능. |
| Graceful Degradation | 전체 시스템이 아닌 일부 기능만 제한하여 핵심 서비스를 유지하는 전략을 설명 가능. |

## 3. 자가 검증

### DDIA 이론
- [ ] "관계형 vs 문서형 DB 선택 기준" 트레이드오프 기반 설명 가능
- [ ] "B-Tree와 LSM-Tree의 차이" → 읽기/쓰기 최적화 관점에서 설명 가능
- [ ] "리더-팔로워 복제에서 리더가 장애나면?" → Failover 과정 + Split Brain 위험 설명 가능
- [ ] "파티셔닝에서 핫스팟이란?" → 원인 + 해결 방안 설명 가능
- [ ] "Consistent Hashing이란?" → 해시 링 + 가상 노드 + 노드 추가 시 최소 데이터 이동 설명 가능
- [ ] "샤딩 이후 노드를 추가하면 어떤 문제가 발생하는가?" → 리밸런싱 부하 + 관리 전략 설명 가능
- [ ] "2PC의 문제점과 대안" → 블로킹, 코디네이터 SPOF, Saga 패턴 설명 가능
- [ ] "분산 시스템에서 어떤 문제가 발생할 수 있는가?" → 네트워크 유실/지연, 시계 불일치, 프로세스 일시 정지 3가지 설명 가능
- [ ] "시계만으로 이벤트 순서를 판단하면 안 되는 이유" → Clock Skew + LWW 데이터 손실 시나리오 설명 가능
- [ ] "Fencing Token이란?" → GC Pause 시 리더 자격 상실 문제 방지 설명 가능
- [ ] "CAP 정리를 설명하라" → C/A/P 정의 + CP/AP 시스템 예시 + CAP의 한계(PACELC) 설명 가능
- [ ] "Eventual Consistency란?" → Strong과의 차이, 허용 가능한 시나리오 설명 가능
- [ ] "최종 일관성을 택했을 때 사용자가 겪는 문제와 보정 방법" → Read-your-writes, 낙관적 UI, 폴링/WebSocket 설명 가능
- [ ] CAP을 Kafka, Redis, Cassandra에 각각 대입하여 설명 가능
- [ ] "CDC란?" → 활용 사례 3가지 설명 가능
- [ ] "이벤트 소싱이란?" → 장단점 + CQRS 관계 설명 가능

### 시스템 설계 실전
- [ ] "URL 단축기를 설계하라" → 30분 내 구조도 + 트레이드오프 설명 가능
- [ ] "1억 건 데이터의 검색 시스템을 설계하라" → 역인덱스 + 파티셔닝 + 랭킹 설명 가능
- [ ] "채팅 시스템을 설계하라" → WebSocket + 메시지 저장 + 읽음 표시 설명 가능
- [ ] "주문/결제 시스템을 설계하라" → 멱등성 + 상태 머신 + 보상 트랜잭션 설명 가능
- [ ] "ERP의 복식 부기 원칙이 분산 시스템 설계와 어떻게 연결되는가?" → 차변/대변 균형 = 멱등성 + 보상 트랜잭션 + 이벤트 소싱 설명 가능
- [ ] "수주→출고→매출→회계 흐름을 분산 시스템으로 설계하라" → Saga 패턴 + 보상 로직 설명 가능
- [ ] 4단계 접근법(요구사항 → 대략적 설계 → 상세 설계 → 마무리)으로 체계적으로 진행 가능

### 확장성 + 장애 대응
- [ ] "수직 확장 vs 수평 확장" → 각각의 장단점 + 한계 설명 가능
- [ ] "캐시 스탬피드란?" → 원인 + 대응 설명 가능
- [ ] "서킷 브레이커 동작 원리" → Closed/Open/Half-Open 상태 전이 설명 가능
- [ ] "멱등성이란?" → 왜 필요하고 어떻게 구현하는가 설명 가능
- [ ] "Graceful Degradation이란?" → 구체적 사례 설명 가능
