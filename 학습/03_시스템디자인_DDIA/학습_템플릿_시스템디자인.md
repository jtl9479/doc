# 시스템 디자인 학습 템플릿

> 유형: **개념 설명 + 설계 연습**
> 적용: 학습_03_시스템디자인_DDIA.md의 Step 1~15

## 공통 원칙

| 원칙 | 설명 |
|------|------|
| **왜 먼저** | "이 개념이 없으면 분산 시스템에서 이런 장애가 발생한다" |
| **비유 먼저** | 복잡한 분산 개념을 일상 비유로 직관 잡기 |
| **트레이드오프** | 시스템 디자인의 본질 = 트레이드오프. 모든 선택에 "얻는 것 vs 잃는 것" 명시 |

### 비유 예시
```
데이터 모델 (관계형 vs 문서형) = "엑셀(관계형: 행/열 고정, 시트 간 VLOOKUP) vs 서류 폴더(문서형: 폴더마다 다른 양식, 관련 서류를 한 폴더에)"
B-Tree = "사전. 'ㄱ→가→감' 순서로 좁혀감. 페이지를 넘기며 찾음(읽기 최적화)"
LSM-Tree = "메모장에 적고 나중에 정리. 일단 빠르게 적고(Memtable), 나중에 정리해서 보관(SSTable Compaction). 쓰기 최적화"
인코딩 = "편지 봉투. JSON = 큰 봉투에 이름표까지 적음(읽기 쉬움, 큼). Protobuf = 작은 봉투에 번호표만(작고 빠름, 사람이 못 읽음)"
복제 = "중요 서류를 복사해서 여러 금고에 보관. 하나가 불타도 다른 곳에 남아있음"
리더-팔로워 = "사장(리더)이 결재하고, 비서(팔로워)가 복사본 보관. 사장 부재 시 비서가 승격"
Split Brain = "부서가 둘로 나뉘어 각각 '내가 사장'이라고 주장. 명령 충돌 → 혼란"
파티셔닝 = "도서관 책을 층별로 나눔. 1층(A~M), 2층(N~Z). 한 층에서만 찾으면 됨"
핫스팟 = "도서관에서 해리포터만 모든 학생이 빌림 → 해리포터가 있는 층만 붐빔"
Consistent Hashing = "원형 테이블에 앉은 사람들. 새 사람이 오면 옆 사람 접시만 옮기면 됨(전체 재배치 X)"
2PC = "결혼식 서약. '네' 할 건지 양쪽에 물어보고(Prepare), 둘 다 '네'면 진행(Commit). 한쪽이 도망가면(코디네이터 장애) 하객(참여자)이 멈춤"
분산 시스템의 어려움 = "해외 원격 근무. 메일이 늦게 도착하고(네트워크 지연), 시차가 있고(시계 불일치), 상대가 자는지 퇴사했는지 모름(프로세스 장애)"
합의 (Raft) = "반장 선거. 후보가 과반수 투표를 받으면 당선(리더 선출). 반장이 전학 가면 재선거"
CAP = "택배: 빠르게(가용성) vs 정확하게(일관성). 도로가 끊기면(분단) 둘 중 하나만"
Eventual Consistency = "은행 ATM. 입금 직후 다른 ATM에서 안 보일 수 있음. 하지만 '결국'은 반영됨"
배치 처리 = "빨래 모아서 한 번에 세탁기 돌리기. 한 벌씩 손빨래(실시간)보다 효율적이지만 기다려야 함"
스트림 처리 = "공장 컨베이어 벨트. 부품(이벤트)이 도착하는 즉시 조립(처리)"
로드밸런서 = "은행 번호표 기계. 빈 창구로 자동 안내"
CDN = "편의점 체인. 본사 창고(원본 서버)에서 가져오지 않고 가까운 편의점(엣지 서버)에서 바로 구매"
서킷 브레이커 = "전기 차단기. 과전류(장애 전파) 감지하면 회로 차단. 복구되면 다시 연결"
```

### 트레이드오프 예시
```
관계형 vs 문서형: 관계형(조인 강력, 정합성) ↔ 문서형(유연한 스키마, 조인 약함)
B-Tree vs LSM-Tree: B-Tree(읽기↑) ↔ LSM-Tree(쓰기↑, 공간 효율↑, Compaction 비용)
JSON vs Protobuf: JSON(가독성↑) ↔ Protobuf(크기↓ 속도↑, 사람이 못 읽음)
동기 복제 vs 비동기 복제: 동기(일관성↑) ↔ 비동기(지연↓ 가용성↑, 데이터 유실 가능)
파티셔닝: 확장성↑ ↔ 조인 어려움, 핫스팟 위험, 리밸런싱 비용
2PC vs Saga: 2PC(강한 일관성) ↔ Saga(성능↑ 가용성↑, 보상 트랜잭션 복잡)
강한 일관성 vs 최종 일관성: 정확성↑ ↔ 지연↑ 가용성↓
배치 vs 스트림: 배치(처리량↑ 비용↓) ↔ 스트림(지연↓ 실시간, 복잡↑)
캐시: 응답 속도↑ ↔ 데이터 불일치, 캐시 관리 복잡성
수평 확장 vs 수직 확장: 수평(무한 확장) ↔ 수직(단순, 물리적 한계)
```

## 설명 흐름

### DDIA 이론 Step (1~11)

1. **왜 알아야 하는가**: "이 개념 없이 분산 시스템을 만들면 이런 장애가 발생"
2. **비유로 직관 잡기**: 위 비유 활용
3. **핵심 개념 설명**: 다이어그램(텍스트) + 구조/흐름
4. **실제 시스템 대입**: "Kafka/Redis/Cassandra에서 이것이 이렇게 적용"
5. **트레이드오프 토론**: "A vs B 중 어떤 상황에서 무엇을 선택?" → 사용자에게 묻고 피드백
6. **오해하기 쉬운 부분**: "~라고 생각하기 쉬운데, 사실은 ~"
```
"CAP에서 3개 중 2개를 고른다" → P는 선택이 아니라 현실. 분단 시 C와 A 중 선택
"Eventual Consistency = 데이터가 틀려도 된다" → 아님. '결국' 일치. 일시적 불일치 허용
"복제하면 데이터가 안전하다" → 비동기 복제는 리더 장애 시 유실 가능
"파티셔닝하면 항상 빨라진다" → 핫스팟 키면 한 파티션에 몰려서 오히려 느려질 수 있음
```
7. **확인 질문 (1~2개)**: 학습 목표 수준으로 질문 → 사용자 답변 → 피드백
```
Step 1: "이 데이터에 관계형 vs 문서형 중 무엇을 쓸 것인가? 근거는?"
Step 4: "리더가 죽고 팔로워가 승격되면 어떤 문제가 발생할 수 있는가?"
Step 5: "파티션 수를 나중에 바꾸면 왜 어려운가?"
Step 7: "타임아웃이 발생했을 때 상대 서버가 죽은 건지 느린 건지 어떻게 아는가?"
Step 9: "Kafka는 CP인가 AP인가? 근거는?"
Step 11: "CDC란? 활용 사례 3가지는?"
```
8. **정리 + 다음 안내**

### 설계 실전 Step (12~15)

1. **요구사항 제시**: Claude가 시스템 요구사항 제시 (기능/비기능/제약조건)
2. **사용자 설계**: 사용자가 답변 (**정답을 먼저 주지 않음**)
3. **리뷰 + 트레이드오프 토론**: "왜 이 방식? 대안은? 비용은? 병목은?"
4. **확인 질문**: "이 설계의 SPOF는?", "트래픽 10배면 어디가 먼저 터지는가?", "비용을 줄이려면?"
5. **모범 답안 + ADR 작성**: 핵심 결정 3가지를 ADR로

## Step별 특이사항

### DDIA Part 1 (Step 1~3)
- Step 1 (데이터 모델): "이 데이터에 관계형 vs 문서형 중 무엇을 쓸 것인가?" 판단 연습. 엑셀 vs 서류 폴더 비유
- Step 2 (스토리지 엔진): B-Tree(사전) vs LSM-Tree(메모장→정리) 비유. "Oracle은 B-Tree, Cassandra는 LSM-Tree인 이유". 행 지향 vs 열 지향도 비유("출석부 전체 행 vs 성적표 한 과목 열만")
- Step 3 (인코딩): 편지 봉투 비유. 스키마 진화(전방/후방 호환성)는 "옛날 편지를 새 양식으로 읽기/새 편지를 옛날 양식으로 읽기"

### DDIA Part 2 (Step 4~9)
- Step 4 (복제): 금고 복사 비유. 리더-팔로워(사장-비서) + Split Brain(사장 2명 충돌). "동기 vs 비동기 복제" 트레이드오프 필수
- Step 5 (파티셔닝): 도서관 층별 분류 + 핫스팟(해리포터) + Consistent Hashing(원형 테이블). 리밸런싱의 실무적 고통("샤딩 후 노드 추가하면?")
- Step 6 (분산 트랜잭션): 결혼식 서약(2PC) 비유. "코디네이터가 쓰러지면?" 시나리오. 2PC vs Saga 트레이드오프
- Step 7 (분산 어려움): 해외 원격 근무 비유 (메일 지연/시차/상대 부재). Clock Skew, Fencing Token. "분산은 무엇이든 잘못될 수 있다"
- Step 8 (합의): 반장 선거(Raft) 비유. 선형성 vs 인과적 일관성 트레이드오프
- Step 9 (CAP): 택배 비유. CP/AP 시스템을 Kafka/Redis/Cassandra에 대입. **Eventual Consistency의 사용자 경험 보정**(Read-your-writes, 낙관적 UI) → "기술 한계를 비즈니스에서 어떻게 풀어내는가"

### DDIA Part 3 (Step 10~11)
- Step 10 (배치): 빨래 모아서 세탁기 비유. MapReduce의 한계 → Spark/Flink
- Step 11 (스트림): 컨베이어 벨트 비유. CDC, 이벤트 소싱, Lambda/Kappa Architecture. Kafka 학습과 직접 연계

### 설계 실전 (Step 12~15)
- Step 12 (설계 프레임워크): 면접 4단계 접근법(요구사항 5분 → 대략적 설계 10분 → 상세 10분 → 마무리 5분). Back-of-the-envelope 추정(QPS, 저장소)
- Step 13 (설계 연습): **사용자가 먼저 설계 → Claude가 리뷰**. 매 연습마다 ADR 작성. ERP 도메인(주문/결제) 시 본인 경험(복식 부기 + 멱등성 + Saga) 활용 유도
- Step 14 (확장성): 로드밸런서(번호표 기계) + CDN(편의점 체인) 비유. "20만 줄 ERP에서 확장이 정말 필요한가?" → YAGNI 판단. 수평 vs 수직 트레이드오프
- Step 15 (장애 대응): 서킷 브레이커(전기 차단기) 비유. 멱등성, Rate Limiting, Graceful Degradation. "이 시스템의 SPOF는 어디인가?" 식별 연습
