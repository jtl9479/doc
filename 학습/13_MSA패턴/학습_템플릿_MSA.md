# MSA 패턴 학습 템플릿

> 유형: **개념 + 패턴 비교 + 설계 토론**
> 적용: 학습_13_MSA패턴.md의 Step 1~16

## 공통 원칙

| 원칙 | 설명 |
|------|------|
| **왜 먼저** | "모놀리스의 이런 한계를 MSA가 이렇게 해결 (하지만 새로운 문제도 발생)" |
| **비유 먼저** | MSA 패턴을 일상 비유로 직관 잡기 |
| **트레이드오프** | MSA의 본질 = 트레이드오프. "무조건 MSA가 좋다" 절대 금지 |

### 비유 예시
```
모놀리스 = "1인 식당. 주문/요리/서빙 혼자. 빠르고 단순하지만 손님 많아지면 한계"
MSA = "전문 식당 거리. 초밥집/피자집/카페 각각 독립. 각자 메뉴 특화. 단, 주문 연계(통신)가 복잡"
Saga = "이사 체크리스트. 전입신고 → 인터넷 설치 → 가스 개통. 가스 개통 실패하면 → 인터넷 해지(보상) → 전입 취소(보상)"
Circuit Breaker = "전기 차단기. 과전류(장애 전파) 감지하면 회로 차단(요청 차단). 전기 복구되면 다시 연결"
Outbox = "보내는 편지함. 편지(이벤트)를 우편함(Outbox 테이블)에 넣고 트랜잭션으로 확정 → 우체부(별도 프로세스)가 수거하여 발송(Kafka)"
API Gateway = "호텔 컨시어지. 손님(클라이언트)이 뭘 원하든 컨시어지에게만 말하면 됨. 내부 연결은 컨시어지가 처리"
Strangler Fig = "오래된 건물 리모델링. 한 번에 철거하지 않고, 한 층씩 새로 지으면서 기존 건물을 서서히 대체"
```

### 트레이드오프 예시
```
MSA 자체: 독립 배포/확장 ↔ 분산 복잡성, 운영 비용 3배↑, 디버깅 어려움
Saga (Choreography): 결합도↓ ↔ 전체 흐름 파악 어려움
Saga (Orchestration): 흐름 명확 ↔ Orchestrator가 SPOF/병목
동기 통신: 구현 단순 ↔ 결합도↑ 장애 전파
비동기 통신: 결합도↓ ↔ 최종 일관성, 디버깅 어려움
CQRS: 읽기/쓰기 최적화 ↔ 복잡성↑ 최종 일관성
데이터 복사: 조회 빠름 ↔ 정합성 관리 필요
API 조인: 항상 최신 ↔ 지연↑ 장애 영향
```

## 설명 흐름
1. **왜 써야 하는가 (+ 왜 안 써도 되는가)**: MSA는 항상 정답이 아님
2. **비유로 직관 잡기**
3. **핵심 개념 + 다이어그램**
4. **패턴 비교** (A vs B 표): 항상 대안과 함께
5. **"이 상황에서 어떤 패턴?" 판단 연습** → 사용자 참여 → 트레이드오프 토론
6. **오해하기 쉬운 부분**:
```
"MSA가 항상 좋다" → 팀 3명 + 트래픽 17 QPS에 MSA는 오버엔지니어링
"서비스를 잘게 나눌수록 좋다" → Nano Service = 운영 비용 폭증. 비즈니스 단위로 나눔
"서비스 간 DB를 공유해도 된다" → 공유 DB = 독립성 상실. Database per Service 원칙
"Saga = 분산 트랜잭션의 완벽한 대안" → 보상 트랜잭션이 항상 가능하지 않음(이미 발송된 이메일)
"API Gateway에 비즈니스 로직을 넣어도 된다" → Gateway는 라우팅/인증만. 로직 넣으면 관심사 혼재
"Circuit Breaker만 있으면 장애 전파 방지" → Retry + Timeout + Bulkhead 조합 필요
```
7. **ERP 연결**: "ERP에 MSA가 정말 필요한가?" 비판적 관점
8. **확인 질문**: 사용자 답변 → 피드백
```
Step 2: "MSA가 필요한 경우와 불필요한 경우의 판단 기준은?"
Step 3: "동기 vs 비동기 통신 선택 기준은?"
Step 6: "Saga Choreography vs Orchestration 차이와 선택 기준은?"
Step 7: "Outbox 패턴이란? 이중 쓰기 문제를 어떻게 해결하는가?"
Step 10: "Circuit Breaker의 Closed→Open→Half-Open 상태 전이를 설명해보세요"
Step 14: "분산 모놀리스란? 어떻게 식별하는가?"
Step 15: "Strangler Fig 패턴으로 레거시를 어떻게 전환하는가?"
```
9. **정리 + 다음 안내**

## Step별 특이사항
- 기초 Step(1~2): "MSA가 필요한가?" 판단이 핵심. ERP에는 모듈러 모놀리스 권장
- 통신 Step(3~5): K8s Service = 서비스 디스커버리, Ingress = API Gateway 연결
- Saga Step(6): ERP 시나리오(수주→재고→출고) + 보상 트랜잭션
- 장애 대응 Step(10~11): Circuit Breaker + Retry + Timeout 조합
- Strangler Fig Step(15): "기존 시스템을 어떻게 안전하게 전환?"
- 안티패턴 Step(14): "이 설계의 문제점은?" 식별 연습
