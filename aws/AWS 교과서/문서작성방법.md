# AWS 교과서 정리 — 문서 작성 방법

Claude는 이 폴더(`aws/AWS 교과서/`)를 작업하기 전에 이 파일을 먼저 읽는다.

---

## 0. 목적 — 이 노트는 학습용이다

**레퍼런스 문서가 아니다.** 나중에 찾아보려고 만드는 자료가 아니라, **읽으면서 이해하고 머리에 남기려고** 만드는 자료다.

아래 모든 규칙은 이 목적에서 나온다.

| 규칙 | 학습용이기 때문에 |
|------|-----------------|
| 사용자가 직접 쓴다 | **쓰면서 배운다.** 대신 써 주면 학습이 사라진다 |
| 보완이 책보다 길면 안 된다 | 길면 안 읽는다. **안 읽는 노트는 학습 실패** |
| 금액·개수를 안 적는다 | 외울 필요가 없다. **조회하면 되는 건 학습 대상이 아니다** |
| "왜 이 개념이 있는가"를 반드시 쓴다 | 이유를 모르면 **암기만 남고 응용이 안 된다** |
| 묻지 않은 걸 안 넣는다 | 지금 궁금한 것에 답해야 **머리에 붙는다** |
| 요금·기본값은 확인한다 | **틀린 걸 외우면 안 되니까.** 수치를 적으려는 게 아니다 |

### 판단이 애매할 때

> **"이게 이해를 돕는가, 아니면 그냥 정보인가?"**
>
> 정보면 뺀다. 나중에 필요하면 그때 검색하면 된다.
> 지금 필요한 건 **"아, 그래서 이렇게 되는 거구나"** 하나뿐이다.

## 1. 역할 분담

| 주체 | 하는 일 |
|------|--------|
| **사용자** | 책을 읽고 **원문 요약을 직접 작성**한다. 모르는 부분은 그 자리에 질문을 적어 둔다. |
| **Claude** | 오타·사실 오류를 교정하고, 질문에 답하고, 꼭 필요한 내용만 보완한다. **원문을 대신 써 주지 않는다.** |

사용자가 쓴 문장은 **가능한 한 그대로 둔다.** 고치는 것은 오타, 명백한 사실 오류, 문체 통일뿐이다.

---

## 2. 파일 규칙

```
aws/AWS 교과서/
├── 문서작성방법.md          ← 이 파일
├── 1.AWS란.MD
├── 2.AWS컴퓨팅 서비스.MD
└── N.장제목.MD
```

- 파일명 = `장번호.장제목.MD`
- 인코딩 UTF-8(BOM 없음), 줄바꿈 CRLF
- 한 장 = 한 파일

---

## 3. 문서 구조

```markdown
# 장 제목                     ← 장 번호 없이 제목만 (예: "AWS란")

## N.1 절 제목
### N.1.1 항 제목

[책 원문 요약 — 코드블록 또는 일반 문단]

#### 소제목                   ← 보완 내용은 h4로
> **Q.** 사용자가 적은 질문    ← 질문이 있던 자리
[답변]

### ⚠️ N.1 오해               ← 절 끝. 3~4개 불릿, 한 줄씩
```

- 절(`N.1`)이 끝날 때마다 `⚠️ 오해` 블록으로 마무리한다
- 장 전체 요약이나 자가 점검 체크리스트는 두지 않는다 (분량만 늘고 결국 안 읽게 됨)

---

## 4. 표기 규칙

| 대상 | 표기 |
|------|------|
| **책 원문 요약** | 코드블록 또는 일반 문단 — 사용자가 쓴 그대로 |
| **사용자 질문** | 해당 소제목 아래 `> **Q.** 질문 내용` 한 줄 |
| **보완 설명** | 일반 문단, 표, 인용구(`>`) |
| **중요 경고** | `> ⚠️ 내용` |
| **시점 의존적 수치** | 원문 뒤에 `← 책 집필 시점 기준` + 확인처 링크 |

책 원문과 보완 내용은 **코드블록 여부로 구분**된다. 별도 마커(`📌 보완` 등)는 쓰지 않는다.

## 5. 보완 분량 기준 ★

**보완이 책 원문보다 길어지면 안 된다.** 노트의 주인은 책이다.

| 항목 | 기준 |
|------|------|
| 질문 1개당 답변 | **3~10줄** |
| 표 | 정말 비교가 필요할 때만, 소제목당 **1개** |
| 표의 열 개수 | **3~5열**. 그 이상은 정보가 아니라 장식 |
| 사례 | 대표 **1~2개**. 나열하지 않는다 |
| 절당 오해 포인트 | **3~4개**, 각 한 줄 |

### 넣을 것 / 뺄 것

| ✅ 넣는다 | ❌ 뺀다 |
|----------|--------|
| 질문에 대한 직접적인 답 | 묻지 않은 주변 지식 |
| 지금 장에서 이미 다룬 개념으로 하는 설명 | **아직 안 배운 개념을 끌어와 하는 설명** |
| **책 서술이 오해를 유발하는 지점** (예: "프라이빗 = 온프레미스") | 흥미롭지만 시험·실무에 안 걸리는 배경 지식 |
| 뒤 장 전체가 의존하는 개념 (리전/AZ, S3·EBS·EFS) | 창업 배경, 역사, 어원 나열 |
| 실무에서 바로 걸리는 함정 (Lambda 15분, EBS 과금) | 같은 내용의 다른 표현 반복 |
| 판단을 바꾸는 수치 | **금액·개수·세부 한도** (아래 참고) |

### 수치를 적는 기준

**기준은 하나 — 그 수치를 몰라서 판단이 달라지는가.**

| ✅ 적는다 (방향) | ❌ 안 적는다 (수치) |
|----------------|------------------|
| "15분 넘으면 Lambda를 못 쓴다" → 서비스 선택이 바뀜 | Lambda 메모리 128MB~10GB |
| "중지해도 EBS는 돈이 나간다" → 설계·정리 습관이 바뀜 | IP당 $0.005/시간, 프리 티어 750시간 |
| "루트 볼륨은 종료 시 삭제된다" → 데이터를 잃음 | `DeleteOnTermination` 기본값 5가지 경우의 수 |
| "리전은 여러 개고 골라야 한다" | 리전 37개, AZ 117개, 인스턴스 유형 500개 |

**금액·개수는 바뀌고, 외워도 쓸모가 없고, 실무에서는 그때 조회한다.** 필요한 것은 "얼마"가 아니라 **"나가느냐 아니냐 / 되느냐 안 되느냐"** 다.

책에 적힌 수치는 사용자가 쓴 그대로 두되, 정확도가 필요한 자리면 확인처 링크만 남긴다.

## 6. 요약이 부실할 때 (질문이 없어도 손볼 것)

사용자가 질문을 적지 않았더라도, 요약 자체가 부실하면 보완한다. 단 **사용자가 쓴 문장은 고치지 않고, 아래에 별도로 붙인다.**

### 전제 1 — 기억으로 쓰면 안 되는 것이 있다

| 유형 | 예 | 처리 |
|------|-----|------|
| **개념·구조·동작 원리** | 보안 그룹은 상태 저장, 인스턴스 상태 전이, 책임 공유 모델 | 안정적이라 기억으로 써도 됨 |
| **요금·기본값·정책** | 퍼블릭 IPv4 과금, `DeleteOnTermination` 기본값 | **바뀐다. 확인하거나 단정하지 말 것** |

실제로 "Elastic IP는 미연결 시에만 과금"이라고 적었다가 틀렸다. 2024년 2월에 정책이 바뀌어 **연결 여부와 무관하게 과금**된다.
다만 확인했더라도 **금액·개수는 노트에 옮기지 않는다**(5장 '수치를 적는 기준' 참고). 확인은 *방향을 틀리지 않기 위해* 하는 것이지 수치를 적기 위한 것이 아니다.

### 전제 2 — Claude는 책을 보지 못한다

> "책에 있는데 빠뜨렸다"는 **판단할 수 없다.**
> 가능한 것은 **"이 주제라면 보통 이것도 다룬다"는 제안**뿐이다.
> 따라서 단정하지 말고 `책에 있다면 확인 필요` 형태로 적는다.

### 부실 유형과 처리

| 유형 | 상태 | 처리 |
|------|------|------|
| **① 누락** | 이 주제의 핵심이 안 적혀 있음 | `> ❓ 확인 필요:` 로 무엇이 빠진 것 같은지 + 왜 중요한지 **2~3줄** |
| **② 오해** | 적혀 있으나 내용이 틀렸거나 오해를 부름 | `> ⚠️` 로 정확한 내용 제시. **원문은 그대로 두고** 아래에 붙임 |
| **③ 불완전** | 적혀 있으나 그것만으로는 이해가 안 됨 | 정의·예시를 **3~5줄** 보완 |
| **④ 단순 나열** | 용어만 나열되고 차이·기준이 없음 | 비교표 **1개** 또는 판단 기준 한 줄 |

### 예시

```markdown
* AWS 스토리지
​```
Amazon S3, EFS, EBS 등이 있으며 데이터를 저장할 수 있다.
​```

> ⚠️ 셋의 차이가 이 절의 핵심인데 나열만 되어 있다.
> 통째로 올리고 내리기 → S3 / 서버 1대의 디스크 → EBS / 여러 서버 공유 → EFS
```

### 하지 않는 것

- 사용자 문장을 **다시 써 주지 않는다.** 부족하면 지적하되 채워 넣는 건 사용자 몫이다
- 책에 없을 수도 있는 내용을 **"책에 나온다"는 듯이 적지 않는다**
- 한 절에서 지적은 **2~3개까지.** 전부 지적하면 요약을 다시 쓰라는 말과 같다

## 7. 답변 작성 규칙

### 용어 질문 — "OO가 무엇인가"

반드시 이 순서로 쓴다.

```
1. 한 줄 정의      — 그게 무엇인지. 전문 용어를 다른 전문 용어로 바꾸지 말 것
2. 구체적 예시     — 사용자 업무(ERP) 기준이면 더 좋다
3. 왜 이 개념이 있는가   ← 가장 중요. 없으면 암기만 남는다
4. (필요하면) 분류·응용
```

> **나쁜 예**
> "워크로드는 비즈니스 가치를 내는 리소스와 코드의 집합이다."
> → AWS 문서 표현을 옮긴 것일 뿐 정의가 아니다. 응용(분류표)부터 쓰는 것은 더 나쁘다.
>
> **좋은 예**
> "워크로드는 시스템이 처리해야 하는 '일' 그 자체다. work(일) + load(짐).
> 예: '매월 25일 급여를 계산해 명세서를 발송한다'가 하나의 워크로드다.
> 클라우드는 Auto Scaling으로 서버 수가 계속 변해 장비로 셀 수 없으니, 단위가 장비에서 일로 옮겨갔다."

### 그 외 질문 유형

| 질문 유형 | 서술 순서 |
|----------|----------|
| **비교** ("A와 B 차이") | 비유 → 비교표 → 판단 기준 한 줄 |
| **사용 시점** ("언제 쓰나") | 조건 → 예시 → 판단 순서 |
| **목록** ("무엇이 있나") | 표 1개 + 선택 기준 |

> ⚠️ **가장 자주 하는 실수 — 다음 단계까지 끌어오기**
> 질문에 답한 뒤 "이것도 알면 좋은데" 하며 **응용·분류·선택 기준**을 덧붙이는 것.
> 예: "워크로드가 무엇인가"에 답하면서 인스턴스 패밀리(`t`,`c`,`r`)와 과금 모델 분류표를 붙임
> → 아직 배우지 않은 개념으로 설명하는 셈이라 이해를 돕지 않는다.
> **그 내용이 실제로 등장하는 장·절에 넣는다.** 지금 필요한 건 질문에 대한 답 하나뿐이다.

## 8. 교정 강도

사용자가 요청할 때 지정한다. 기본은 **교정**.

| 요청 | 범위 |
|------|------|
| **"사실만 봐줘"** | 오타·사실 오류만. 문장은 그대로 |
| **"교정해줘"** (기본) | 사실 + 질문 답변 + 필요한 보완 + 구조 정리 |
| **"보강해줘"** | 위 전부 + 비유·트레이드오프·오해 포인트 추가 |

---

## 9. 작업 절차

1. 사용자가 해당 장을 작성하고 **저장**한다
2. Claude가 파일을 읽고 **작업 전 백업**을 스크래치패드에 복사한다
3. 교정·보완을 반영한다
4. 무엇을 왜 고쳤는지 채팅으로 요약 보고한다

> ⚠️ **저장 충돌 주의**
> 사용자가 편집기에 파일을 열어 둔 상태에서 Claude가 파일을 수정하면, 이후 편집기 버퍼를 저장할 때 **Claude의 수정분이 통째로 덮어써진다.**
> Claude 작업 후에는 **편집기 탭을 닫았다 다시 열고** 이어서 작성할 것.

> ⚠️ **파일 생성 시 주의**
> `문서작성방법.md`가 디렉터리로 잘못 생성된 적이 있다. 새 파일은 편집기에서 만들거나, 만든 뒤 파일인지 확인할 것.

## 10. 반영 전 확인

- [ ] 보완 분량이 책 원문 분량을 넘지 않는가
- [ ] 묻지 않은 내용을 넣지 않았는가
- [ ] 용어 정의를 다른 전문 용어로 돌려막지 않았는가
- [ ] "왜 이 개념이 있는가"가 들어 있는가
- [ ] 표가 소제목당 1개를 넘지 않는가
- [ ] 사용자가 쓴 문장을 임의로 바꾸지 않았는가
- [ ] 시점 의존적 수치에 "책 집필 시점 기준"을 붙였는가
