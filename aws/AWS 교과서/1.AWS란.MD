# AWS란

## 1.1 클라우드 컴퓨팅

### 1.1.1 클라우드 컴퓨팅이란

IT 자원을 구축하는 전통적인 방법 온프레미스 방법은 자체적인 공간과 자원을 이용하여
사용자가 직접 구축 및 운용하는 방식을 의미한다. 해당 방식은 사용자가 모든 것을 수행해야 하기 때문에
부담이 클 수밖에 없으며, 비용 또한 만만치 않다. 이러한 문제점을 고려하여 효율적인 IT 자원을 구축하는 방법인 클라우드 구축 방법이 떠오르고 있다.

클라우드 컴퓨팅은 인터넷을 통해 요구가 있을 때 즉시(온디맨드) IT 자원을 제공하며, 사용한 만큼
비용을 지불하는 서비스이다. 클라우드 단어 의미와 연결하여 생각하면, 인터넷 구간 어딘가에 구름 형태로 쌓여 실제 물리적인 자원은 보이지 않지만 IT 자원을 원하는 대로 가져다 사용할 수 있는 컴퓨팅 서비스를 의미한다.

> 📌 **보완: 온프레미스 vs 클라우드 — 비용 구조의 차이**
>
> 책에서 "비용이 만만치 않다"고 한 부분의 핵심은 **금액의 크기가 아니라 지출의 성격**이다.
>
> | 구분 | 온프레미스 | 클라우드 |
> |------|-----------|---------|
> | 지출 성격 | **CapEx** (자본 지출) — 선투자 후 감가상각 | **OpEx** (운영 지출) — 매달 사용량만큼 |
> | 자원 확보 시간 | 견적 → 결재 → 발주 → 납품 → 설치 = **수 주 ~ 수 개월** | 콘솔 클릭 = **수 분** |
> | 용량 산정 | 피크 기준으로 **과다 구성**해야 안전 | 실사용 기준, 부족하면 즉시 확장 |
> | 미사용 시 | 놀아도 감가상각·전기·상면 비용 발생 | 삭제하면 과금 중단 |
> | 실패 비용 | 잘못 산 서버는 되돌릴 수 없음 | 지우면 끝 → **시도 비용이 낮음** |
>
> "클라우드는 싸다"가 아니라 **"실패를 싸게 만든다"** 가 본질에 가깝다.

> 📌 **보완: 클라우드의 5대 특성 (NIST 정의)**
>
> 미국 표준기술연구소(NIST)가 정의한, 무엇을 클라우드라고 부를 수 있는지의 기준. 개념 정리와 면접에서 자주 인용된다.
>
> | 특성 | 의미 |
> |------|------|
> | 온디맨드 셀프서비스 | 사람(영업·운영자)을 거치지 않고 사용자가 직접 자원을 할당 |
> | 광범위한 네트워크 접근 | 인터넷을 통해 어떤 기기로든 접근 가능 |
> | 자원 풀링 (Resource Pooling) | 공급자가 자원을 모아두고 다수 사용자에게 나눠 씀 (멀티테넌시) |
> | 신속한 탄력성 (Rapid Elasticity) | 수요에 따라 빠르게 확장·축소 |
> | 측정 가능한 서비스 | 사용량이 계측되어 과금·모니터링의 근거가 됨 |

### 1.1.2 클라우드 컴퓨팅 이점

* 민첩성
```
클라우드를 통해 광범위한 기술에 쉽게 접근할 수 있어 거의 모든 것을 빠르고 혁신적으로 구축할 수 있다.
```
* 탄력성
```
기존 온프레미스 환경처럼 향후 비즈니스 확장을 고려한 IT자원을 사전에 과하게 구성할 필요가 없다.
필요한 만큼만 자원을 할당받아 사용하면 된다.

비즈니스 요구가 가변적인 상황에서 자원을 손쉽게 확장하거나 축소하여 탄력적으로 운영이 가능하다.
```
* 비용 절감
```
클라우드 컴퓨팅은 Pay Per Use로, IT자원을 사용한 만큼 비용을 지불한다.
```

> 📌 **보완: AWS가 공식적으로 말하는 6가지 이점**
>
> 책은 3가지로 압축했지만, AWS 공식 문서와 자격증 시험에서 쓰는 목록은 6가지다. 위 3개를 포함해 아래와 같이 정리된다.
>
> | 이점 | 설명 |
> |------|------|
> | **선행 비용을 가변 비용으로** | 데이터센터·서버를 사기 전에 투자할 필요 없이, 사용한 만큼만 지불 |
> | **규모의 경제로 인한 비용 절감** | 수많은 고객의 사용량이 모이므로 AWS의 구매 단가가 낮고, 그 절감이 요금 인하로 전가됨 |
> | **용량 추정 불필요** | "3년 뒤 트래픽이 얼마일까"를 맞힐 필요가 없음 (온프레미스 실패의 단골 원인) |
> | **속도 및 민첩성** | 자원 확보가 수 주 → 수 분 (책의 '민첩성') |
> | **데이터센터 운영·유지 비용 제거** | 상면·전력·냉각·경비·하드웨어 교체 인력이 불필요 → 인력을 비즈니스 로직에 투입 |
> | **몇 분 만에 전 세계 배포** | 리전을 선택하기만 하면 해외 사용자 근처에 인프라 배치 가능 |
>
> **트레이드오프도 같이 기억할 것:**
> ```
> 이점                ↔  대가
> 즉시 확장           ↔  방치하면 비용도 즉시 증가 (비용 거버넌스 필요)
> 관리 위임           ↔  벤더 종속(Lock-in), 내부 동작 통제 불가
> 운영 인력 감소      ↔  IAM·네트워크·비용 관리라는 새 역량이 필요
> 사용한 만큼 지불    ↔  24시간 일정 부하는 온프레미스가 더 쌀 수 있음
> ```

> 📌 **보완: 책임 공유 모델 (Shared Responsibility Model)**
>
> 클라우드로 옮긴다고 보안 책임이 사라지지 않는다. AWS 학습 전체를 관통하는 개념이라 여기서 잡고 가는 것이 좋다.
>
> | 주체 | 책임 범위 | 표현 |
> |------|----------|------|
> | **AWS** | 데이터센터 물리 보안, 전력·냉각, 하드웨어, 네트워크 인프라, 가상화 계층 | 클라우드 **의** 보안 (Security **of** the Cloud) |
> | **사용자** | OS 패치, 애플리케이션, IAM 권한 설정, 보안 그룹 규칙, 데이터 암호화 | 클라우드 **에서의** 보안 (Security **in** the Cloud) |
>
> 서비스 유형에 따라 경계가 이동한다. **IaaS는 사용자 책임이 크고, SaaS로 갈수록 공급자 책임이 커진다.** (1.1.3과 연결)

### 1.1.3 클라우드 컴퓨팅 서비스 유형

클라우드 사용자가 어느 영역까지 관리하는지, 반대로 클라우드 공급자가 어느 영역까지 관리하는지에 따라 유형을 분류한다.

* IaaS (Infrastructure as a Service)
```
인프라를 제공하는 클라우드 서비스 유형을 의미한다.
인프라에는 서버, 네트워크, 스토리지 등 하드웨어 영역과 가상화 기능이 해당된다.

클라우드 공급자는 인프라 영역을 관리하고 서비스 제공
클라우드 사용자는 나머지 영역(os, 미들웨어, 런타임, 데이터, 애플리케이션)을 직접 관리하는 구조
```
* PaaS (Platform as a Service)
```
플랫폼 형태로 제공되는 클라우드 서비스 유형을 의미한다.
클라우드 공급자가 자체적으로 구축한 플랫폼을 제공하며, 클라우드 사용자는 별도의 플랫폼을 구축하지 않고 애플리케이션을 개발 및 관리만 한다.

클라우드 사용자는 애플리케이션 영역(데이터, 애플리케이션)만 담당하고
클라우드 공급자가 나머지 영역(하드웨어, 가상화, 운영체제, 미들웨어, 런타임)을 관리 및 제공한다
```
* SaaS (Software as a Service)
```
소프트웨어 영역까지 클라우드 공급자가 관리 및 제공하는 유형을 의미한다.

클라우드 사용자는 별도의 애플리케이션을 설치하거나 운영할 필요 없이 클라우드 서비스를 제공받는다.

클라우드 공급자가 모든 것을 제공한다.
클라우드 사용자는 서비스만을 받는다.
```

**질문 :**
서버/스토리지/네트워킹, 가상화, 운영체제, 미들웨어, 런타임, 데이터, 애플리케이션
각각 단어가 무엇인지 간단한 설명 및 iaas, paas, saas 예를 보여달라.

#### (1) 7개 계층 용어 설명

아래는 "웹 애플리케이션 한 대를 돌리기 위해 아래에서부터 쌓아 올려야 하는 것들"이다. 순서 자체에 의미가 있다.

| # | 계층 | 한 줄 설명 | 온프레미스에서 담당하는 사람 |
|---|------|-----------|--------------------------|
| 1 | **서버 / 스토리지 / 네트워킹** | 실제 쇳덩이. CPU·메모리가 달린 장비(서버), 데이터를 담는 디스크(스토리지), 장비들을 연결하는 스위치·라우터·회선(네트워킹) | 인프라팀 / 전산실 |
| 2 | **가상화 (Virtualization)** | 물리 서버 1대를 논리적인 여러 대(VM)로 쪼개는 기술. 하이퍼바이저(VMware ESXi, KVM, Xen)가 담당 | 인프라팀 |
| 3 | **운영체제 (OS)** | VM 위에서 하드웨어를 관리하고 프로그램을 실행시키는 소프트웨어. Linux(Amazon Linux, Ubuntu), Windows Server | 시스템 엔지니어 |
| 4 | **미들웨어 (Middleware)** | OS와 애플리케이션 **사이**에서 공통 기능을 제공하는 소프트웨어. WAS(Tomcat, WebLogic), DBMS(Oracle, MySQL), 메시지 큐(Kafka) | 시스템 엔지니어 / DBA |
| 5 | **런타임 (Runtime)** | 작성한 코드가 실제로 실행되는 환경. JVM(JRE), Node.js, Python 인터프리터 | 개발자 |
| 6 | **데이터 (Data)** | 애플리케이션이 다루는 실제 내용물. DB 레코드, 업로드 파일, 로그 | 개발자 / 현업 |
| 7 | **애플리케이션 (Application)** | 비즈니스 로직 그 자체. ERP 소스 코드, 주문 처리 로직 | 개발자 |

> **미들웨어와 런타임이 가장 헷갈린다:**
> - **런타임** = "내 코드를 돌려주는 엔진". JVM이 없으면 class 파일은 실행 자체가 안 된다.
> - **미들웨어** = "내 코드가 **가져다 쓰는** 공통 인프라 소프트웨어". Tomcat은 HTTP 요청을 받아 서블릿으로 넘겨주고, Oracle은 데이터를 저장해 준다.
> - Tomcat은 JVM 위에서 돈다. 즉 **런타임 위에 미들웨어가 얹히는 구조**여서 자료마다 4번과 5번의 순서가 뒤바뀌기도 한다. 순서 암기보다 **역할 구분**이 중요하다.

#### (3) 유형별 실제 서비스 예시

| 유형 | AWS | 타 벤더 / 일반 | 내가 하는 일 | 내가 못 하는 일 |
|------|-----|---------------|-------------|----------------|
| **IaaS** | **EC2**(가상 서버), **S3**(스토리지), **VPC**(네트워크), EBS | Azure VM, GCP Compute Engine, 네이버 클라우드 서버 | OS 설치·패치, Tomcat 설치, 방화벽 설정, 배포 | 물리 서버 교체, 하이퍼바이저 조작 |
| **PaaS** | **Elastic Beanstalk**, **RDS**(관리형 DB), **Lambda**, **ECS Fargate**, App Runner | Heroku, Google App Engine, Azure App Service | 코드 작성, 설정값 지정, 배포 | OS 로그인·패치, DB 엔진 파일 직접 수정(파라미터 그룹으로만 조정) |
| **SaaS** | **Amazon WorkMail**, **Amazon Chime**, QuickSight | Gmail, Slack, Notion, Salesforce, Microsoft 365 | 계정 만들고 쓰기, 데이터 입력 | 기능 추가, 버전 선택, 인프라 접근 |

> **비유 — 피자로 이해하기 (Pizza as a Service)**
> ```
> 온프레미스 : 밀가루 반죽부터 오븐까지 전부 집에서  → 완전 통제, 완전 노동
> IaaS       : 밀키트 구입 → 오븐(하드웨어)은 빌려 쓰고, 굽는 건 내가
> PaaS       : 배달 주문   → 집(플랫폼)에서 먹기만. 음료·식탁은 내 것
> SaaS       : 식당에서 사 먹기 → 아무것도 준비 안 함. 메뉴에 없는 건 못 먹음
> ```

> **트레이드오프:**
> ```
> IaaS → 통제권 최대  ↔ 관리 부담 최대, 대신 이식성 좋음(다른 클라우드로 옮기기 쉬움)
> PaaS → 생산성 높음  ↔ 공급자가 정한 방식 강제, 종속성 중간~높음
> SaaS → 관리 부담 0  ↔ 통제권 0, 커스터마이징 불가, 종속성 최대
> ```
> **Spring Boot 앱을 올린다면:** EC2에 직접 설치(IaaS) → ECS/EKS → Fargate → Lambda(서버리스) 순으로 **관리 부담이 줄고 제약이 늘어난다.** 이 축이 앞으로 배울 컴퓨팅 서비스 선택의 기준이 된다.

### 1.1.4 클라우드 구축 모델
클라우드 서비스를 위한 자원의 소유권, 위치, 주체에 따라 퍼블릭 클라우드, 프라이빗 클라우드, 하이브리드 클라우드 구축 모델로 분류된다.

* 퍼블릭 클라우드 구축 모델(public cloud)
```
사용자가 클라우드 자원을 소유하지 않으며, 자체적인 공간에 위치하지 않고 클라우드 공급자가 서비스를 제공하는 환경이다.

퍼블릭 클라우드는 서비스의 주체가 클라우드 공급자이다. 대표적인 퍼블릭 클라우드 공급자는 아마존 웹 서비스, 구글 클라우드 플랫폼, 마이크로소프트 애저 등이 있다.

퍼블릭 클라우드는 온디맨드 형태로 사용자 요구에 따라 클라우드 공급자에게서 IT 자원을 할당받아 확장성이 우수하다.
```

* 프라이빗 클라우드 구축 모델
```
프라이빗 클라우드(private cloud)는 사용자 전용 클라우드 환경으로, 자원 소유권은 사용자한테 있고 프라이빗 클라우드는 온프레미스 환경에 구축되어 서비스를 받는 환경이다.

프라이빗 클라우드는 서비스 주체가 사용자이다.
프라이빗 클라우드는 온프레미스 환경에 구축되어 보안이 우수하지만, 퍼블릭 클라우드보다 서비스 확장성은 떨어진다.
```
* 하이브리드 클라우드 구축 모델
```
하이브리드 클라우드(hybrid cloud)는 다수의 클라우드 시스템이 혼합되어 있는 형태로 클라우드 시스템이 서로 연결된 모델이다.
```

> 📌 **보완 1: 프라이빗 클라우드 ≠ 온프레미스**
>
> 책의 "온프레미스 환경에 구축되어"라는 서술 때문에 둘을 같은 말로 오해하기 쉬운데, **다르다.**
>
> | 구분 | 온프레미스 (전통적) | 프라이빗 클라우드 |
> |------|-------------------|------------------|
> | 자원 할당 | 담당자에게 요청 → 수동 구성 (수 일 ~ 수 주) | 포털에서 셀프서비스로 즉시 (수 분) |
> | 가상화·자동화 | 없거나 부분적 | 필수 (가상화 + 오케스트레이션 + 사용량 계측) |
> | 과금 | 없음 (부서 공용) | 부서별 사용량 측정 (Chargeback / Showback) |
> | 대표 스택 | 물리 서버 + 수동 운영 | OpenStack, VMware Cloud Foundation |
>
> 즉 **프라이빗 클라우드는 "우리만 쓰는 클라우드"라는 운영 방식**을 말하고, 온프레미스는 **자원이 놓인 위치**를 말하는 단어다.
> 프라이빗 클라우드를 외부 사업자의 데이터센터에 우리 전용으로 두는 형태(호스티드 프라이빗)도 있으므로, "프라이빗 = 반드시 사내 위치"도 정확한 표현은 아니다.

> 📌 **보완 2: 하이브리드 클라우드 vs 멀티 클라우드**
>
> 책의 하이브리드 설명이 짧아서 멀티 클라우드와 섞이기 쉽다.
>
> | 구분 | 정의 | 예 |
> |------|------|-----|
> | **하이브리드 클라우드** | **퍼블릭 + 프라이빗(또는 온프레미스)** 을 연결해 하나처럼 운영 | 사내 DB는 온프레미스, 웹 프런트는 AWS. 전용선(Direct Connect)이나 VPN으로 연결 |
> | **멀티 클라우드** | **서로 다른 퍼블릭 클라우드 2개 이상**을 함께 사용 | 컴퓨팅은 AWS, 데이터 분석은 GCP, 협업 도구는 Azure |
>
> 둘은 배타적이지 않고 동시에 성립할 수 있다.

**클라우드 구축 모델 3종 요약**

| 모델 | 자원 소유권 | 위치 | 서비스 주체 | 확장성 | 초기 비용 | 보안·규제 통제 |
|------|-----------|------|-----------|--------|----------|--------------|
| 퍼블릭 | 공급자 | 공급자 데이터센터 | 공급자 | ★★★ | 없음 | 낮음 (책임 공유) |
| 프라이빗 | 사용자 | 자체 데이터센터(또는 전용 공간) | 사용자 | ★ | 큼 | 높음 |
| 하이브리드 | 혼합 | 혼합 | 혼합 | ★★ | 중간 | 중간 (분리 설계 가능) |

**질문** 각 구축모델 별 언제 사용해야하며, 예시를 들어달라

**답변 :**

#### (1) 퍼블릭 클라우드 — 언제 쓰나

| 조건 | 이유 |
|------|------|
| 트래픽 변동이 크다 | 탄력성이 가장 큰 무기. 피크만큼 사두는 낭비를 제거 |
| 초기 자본이 없다 / 빠르게 검증해야 한다 | 선투자 0, 실패해도 지우면 끝 |
| 글로벌 서비스가 필요하다 | 리전 선택만으로 해외 인프라 확보 |
| 관리 인력이 부족하다 | 관리형 서비스(RDS 등)로 운영 인력을 대체 |
| 신기술(AI, 빅데이터)을 빠르게 써야 한다 | 매니지드 서비스로 즉시 사용 |

**예시**
- **스타트업 서비스**: 사용자 수를 예측할 수 없음 → 전부 AWS
- **이커머스 이벤트**: 블랙프라이데이·명절에만 트래픽 10배 → Auto Scaling
- **게임 런칭**: 흥행 여부를 모름. 대박이면 확장, 부진하면 축소
- **넷플릭스**: 자체 데이터센터를 완전히 버리고 AWS로 전면 이전한 대표 사례

#### (2) 프라이빗 클라우드 — 언제 쓰나

| 조건 | 이유 |
|------|------|
| 법·규제상 데이터 외부 반출 금지 | 금융·의료·공공. 물리적 위치를 증명해야 하는 경우 |
| 부하가 일정하고 예측 가능 + 장기 운영 | 3년 이상 24시간 일정 부하면 **자체 보유가 더 저렴**할 수 있음 |
| 극단적으로 낮은 지연시간이 필요 | 공장 설비 제어, 초단타 매매(HFT) |
| 이미 대규모 인프라 투자가 끝나 있다 | 감가상각이 남은 자산을 버릴 이유가 없음 |
| 하드웨어·커널 수준 커스터마이징 필요 | 퍼블릭에서는 불가능한 영역 |

**예시**
- **은행 계정계(코어뱅킹)**: 망분리 규제, 무중단 요구 → 사내 프라이빗 클라우드
- **병원 EMR(전자의무기록)**: 환자 개인정보 보호 요구로 통제 필요
- **국방·공공 기밀 시스템**: 물리적 망 분리 의무
- **제조 공장 MES**: 라인 설비와의 지연시간 문제로 현장에 위치

#### (3) 하이브리드 클라우드 — 언제 쓰나

| 조건 | 이유 |
|------|------|
| 민감 데이터는 내부, 나머지는 외부 | 규제와 확장성을 동시에 만족 |
| 평소 부하는 내부, 피크만 외부로 | **클라우드 버스팅(Cloud Bursting)** |
| 단계적 클라우드 전환 중 | 한 번에 다 옮길 수 없으므로 과도기가 필수 |
| 재해 복구(DR) 사이트가 필요 | 평소엔 최소 자원만, 장애 시 퍼블릭에서 확장 |
| 레거시를 옮길 수 없다 | 메인프레임·특수 라이선스는 이전 불가 |

**예시**
- **대형 유통사**: 고객 개인정보 DB는 사내, 웹·앱 프런트와 프로모션 페이지는 AWS
- **수강신청·성적 조회 시스템**: 평소엔 내부 서버, 오픈 당일만 퍼블릭으로 확장(버스팅)
- **제조 대기업**: 공장 MES는 온프레미스, 데이터 분석·AI 학습은 AWS로 전송
- **DR 구성**: 주 센터는 사내, 재해 시 AWS 리전에서 복구

> **선택 판단 순서 (실무 기준)**
> ```
> 1. 법·규제가 외부 저장을 막는가?
>      ├ 예     → 프라이빗 (일부만 못 나가면 하이브리드)
>      └ 아니오 ↓
> 2. 부하가 24시간 일정하고 3년 이상 유지되는가?
>      ├ 예     → 비용 비교 필수 (프라이빗이 유리할 수 있음)
>      └ 아니오 ↓
> 3. 퍼블릭 클라우드
> ```

## ⚠️ 1.1 오해하기 쉬운 부분

| 오해 | 실제 |
|------|------|
| "클라우드는 항상 싸다" | **아니다.** 변동성이 클 때 싸다. 24시간 일정 부하를 온디맨드로 3년 돌리면 자체 보유보다 비쌀 수 있다. 예약 인스턴스·미사용 리소스 정리 같은 **비용 거버넌스가 없으면 오히려 비싸진다.** |
| "클라우드로 가면 관리할 게 없다" | 서버 관리가 **IAM 권한·네트워크(VPC)·비용 관리로 형태만 바뀐다.** 관리 총량이 0이 되지는 않는다. |
| "클라우드는 무조건 안전하다 / 위험하다" | 책임 공유 모델의 문제다. 물리·인프라 보안은 AWS가 대부분의 조직보다 잘한다. 반면 유출 사고의 대다수는 **사용자의 설정 실수**(S3 퍼블릭 공개, 과도한 IAM 권한)에서 나온다. |
| "프라이빗 클라우드 = 온프레미스" | 다르다. 온프레미스는 **위치**, 프라이빗 클라우드는 **운영 방식**(셀프서비스·자동화·계측)을 가리킨다. |
| "하이브리드 = 멀티 클라우드" | 하이브리드는 **퍼블릭 + 프라이빗**, 멀티 클라우드는 **퍼블릭 여러 개**다. |
| "PaaS를 쓰면 무조건 편하다" | 편한 대신 **공급자가 정한 방식만** 가능하다. 커스텀 JVM 옵션, 특정 라이브러리, 15분 넘는 작업 등에서 막힐 수 있다. |
| "SaaS는 데이터까지 공급자 책임" | 인프라는 공급자 책임이지만, **어떤 데이터를 넣고 누구에게 권한을 주는지는 사용자 책임**이다. |

## ✅ 1.1 자가 점검

- [ ] 온프레미스와 클라우드의 차이를 **CapEx/OpEx, 리드타임, 용량 산정** 세 가지 축으로 설명할 수 있다
- [ ] 7개 계층(서버 ~ 애플리케이션)을 아래에서 위로 순서대로 말할 수 있다
- [ ] 미들웨어와 런타임의 차이를 예를 들어 설명할 수 있다
- [ ] IaaS / PaaS / SaaS의 **관리 경계선**을 표 없이 그릴 수 있다
- [ ] 각 유형별 AWS 서비스를 2개 이상 댈 수 있다
- [ ] "통제권 ↔ 관리 부담" 트레이드오프를 한 문장으로 설명할 수 있다
- [ ] 퍼블릭 / 프라이빗 / 하이브리드를 **소유권·위치·주체** 기준으로 구분할 수 있다
- [ ] 하이브리드와 멀티 클라우드의 차이를 설명할 수 있다
- [ ] 책임 공유 모델에서 "S3 버킷 공개로 인한 유출"이 누구 책임인지 답할 수 있다
- [ ] 우리 회사 ERP가 어떤 구축 모델에 적합한지 근거를 들어 설명할 수 있다

## 1.2 AWS 서비스

### 1.2.1 AWS 소개
```
AWS는 아마존의 자회사로 다양한 퍼블릭 클라우드 컴퓨팅 서비스를 제공한다.
직접 장비를 구매하거나 임대하지 않고 필요한 만큼 자원을 공급하는 클라우드 컴퓨팅 서비스를 제공한다.
AWS는 37개의 리전과 117개의 가용 영역을 운영한다.  ← 책 집필 시점 기준
```

> ⚠️ **수치 주의:** 리전·가용 영역 개수는 **매년 늘어나는 값**이라 인용할 때 반드시 "○○년 기준"을 붙여야 한다.
> 최신 수치는 [AWS 글로벌 인프라 페이지](https://aws.amazon.com/ko/about-aws/global-infrastructure/)에서 확인. 면접에서는 정확한 숫자보다 **"30개 이상의 리전, 리전당 보통 3개 이상의 AZ"** 라는 구조를 아는 것이 중요하다.

> 📌 **보완: 리전 / 가용 영역 / 엣지 로케이션 — 3계층 구조**
>
> 책에 숫자만 나와 있어서 개념이 안 잡힌다. AWS 글로벌 인프라는 3층으로 되어 있다.
>
> | 계층 | 정의 | 규모 | 왜 있는가 |
> |------|------|------|----------|
> | **리전 (Region)** | 지리적으로 분리된 독립 구역. 서울 = `ap-northeast-2` | 전 세계 30개 이상 | 사용자와 가까운 곳에 배치(지연시간), 데이터 주권·규제 대응 |
> | **가용 영역 (AZ, Availability Zone)** | 리전 내부의 물리적으로 분리된 데이터센터 묶음. 서울은 4개(`2a`,`2b`,`2c`,`2d`) | 리전당 보통 3개 이상 | **한 건물이 불타도 서비스가 살아남게** (고가용성) |
> | **엣지 로케이션 (Edge Location)** | 캐시 전용 소규모 거점. CloudFront가 사용 | 전 세계 수백 개 | 정적 콘텐츠를 사용자 코앞에서 전달(CDN) |
>
> **비유:**
> ```
> 리전       = 도시 (서울, 도쿄, 버지니아)
> AZ         = 그 도시 안의 서로 떨어진 물류창고들 (한 곳이 정전돼도 나머지가 살아있음)
> 엣지 로케이션 = 동네 편의점 (본 창고까지 안 가도 자주 찾는 물건을 바로 꺼내 줌)
> ```
>
> **왜 중요한가:** AZ를 이해해야 뒤에 나오는 **Multi-AZ(RDS), ELB, Auto Scaling**이 왜 필요한지가 이해된다.
> AZ끼리는 물리적으로 떨어져 있으면서도 **저지연 전용 회선으로 연결**되어 있어, 여러 AZ에 걸쳐 배포해도 성능 손해가 거의 없다. 이것이 "AWS에서는 무조건 2개 이상 AZ에 배포하라"의 근거다.

> 📌 **보완: AWS의 시작 (맥락)**
>
> AWS는 2006년 **S3**와 **EC2**를 출시하며 시작했다. 아마존이 자사 쇼핑몰 운영을 위해 만든 대규모 인프라 운영 노하우를 외부에 판매한 것이 출발점이다.
> → **퍼블릭 클라우드 시장을 사실상 처음 연 사업자**라서 서비스 수·레퍼런스·커뮤니티가 가장 많다. 1.1.4에서 본 "퍼블릭 클라우드 대표 공급자"라는 위치의 배경이다.

### 1.2.2 AWS 서비스 라인업
```
해당 책에서는 23개의 범주 중에서 컴퓨팅, 네트워킹, 스토리지, 데이터베이스, 보안자격 5개에 대해 알려준다.
```

> 📌 **보완: 5개 범주를 왜 이 순서로 배우는가**
>
> 순서가 임의가 아니라 **서버 한 대를 서비스로 만드는 순서**다.
> ```
> 보안·자격증명(IAM)  ← 누가 만들 수 있는지부터 정하고
>        ↓
> 네트워킹(VPC)       ← 서버를 놓을 땅과 길을 만들고
>        ↓
> 컴퓨팅(EC2)         ← 그 위에 서버를 올리고
>        ↓
> 스토리지(EBS/S3)    ← 데이터를 담을 곳을 붙이고
>        ↓
> 데이터베이스(RDS)   ← 정형 데이터를 관리한다
> ```
> 책은 컴퓨팅부터 소개하지만, **실제 구축 순서는 IAM → VPC → EC2**다. (학습 가이드의 Step 3·4가 IAM·VPC인 이유)

* 컴퓨팅
```
AWS 컴퓨팅은 퍼블릭 클라우드의 서버 자원에 대해 가상 머신을 생성하고, 비용 및 용량을 관리할 수 있는 서비스들로 구성되어 있다.

대표적 서비스로 Amazon Elastic Compute Cloud(Amazon EC2)가 있으며 해당 서비스 덕분에
클라우드에서 안전하고 크기 조정이 가능한(resizable) 컴퓨팅 자원을 제공받을 수 있다. 2장, 9장에서 설명한다.
```
* AWS 네트워킹 및 콘텐츠 전송
```
AWS 네트워킹 및 콘텐츠 전송은 퍼블릭 클라우드에 생성한 다양한 자원이 통신할 수 있도록 지원하는 네트워크 서비스들로 구성되어 있다.

대표적 서비스로 Amazon Virtual Private Cloud(VPC), Amazon CloudFront, Amazon Route 53 등이 있으며 해당 서비스로 생성된 클라우드 자원의 통신 환경을 구성할 수 있다.

3장 AWS 네트워킹 서비스, 4장 부하 분산 서비스, 7장 AWS 고급 네트워킹 서비스에서 설명한다.
```

* AWS 스토리지
```
AWS 스토리지는 퍼블릭 클라우드에 안정적이고 확장성이 높은 스토리지 서비스들로 구성되어 있다.

Amazon Simple Storage Service(S3), Amazon Elastic File System(EFS), Amazon Elastic Block Store(EBS) 등이 있으며 해당 서비스에서 클라우드에서 빠르고 안정적으로 데이터를 저장할 수 있다.
```

* AWS 데이터베이스
```
AWS 데이터베이스는 데이터베이스 목적과 용도에 따라 퍼블릭 클라우드에서 다양한 데이터베이스 엔진을 제공하는 완전 관리형 서비스이다. 대표적으로는 Amazon Relational Database Service(RDS) 등이 있으며 DB 유형에 따라 선택해서 사용할 수 있다. 6장 AWS 데이터베이스 서비스에서 설명한다.
```

* AWS 보안 자격 증명 및 규격 준수
```
AWS 보안 자격 증명 및 규격 준수는 퍼블릭 클라우드 자원과 사용자 자격 증명 및 접근 관리, 데이터·네트워크·애플리케이션 보호와 위협 탐지 및 모니터링을 위한 서비스로 구성되어 있다.
대표적으로는 AWS Identity & Access Management(IAM)가 있으며 8장 AWS IAM 서비스에서 설명한다.
```

> 📌 **보완: `Amazon OOO` vs `AWS OOO` — 접두어에 규칙이 있다**
>
> 위 본문에서 IAM만 **AWS** Identity & Access Management인 것이 우연이 아니다.
>
> | 접두어 | 의미 | 예 |
> |--------|------|-----|
> | **Amazon** | 독립적으로 쓰는 **완결된 서비스** 자체 | Amazon EC2, Amazon S3, Amazon RDS, Amazon VPC, Amazon CloudFront, Amazon Route 53 |
> | **AWS** | 다른 서비스를 **보조·관리·연결**하는 도구 | AWS IAM, AWS Lambda, AWS CloudFormation, AWS CLI, AWS Config |
>
> 절대적인 규칙은 아니고 예외도 있지만, **"혼자서도 쓸모가 있으면 Amazon, 다른 서비스를 거들면 AWS"** 로 기억하면 시험·문서 읽기에서 헷갈리지 않는다.

> 📌 **보완: 5개 범주 = 온프레미스의 무엇을 대체하는가**
>
> 사내 ERP 환경에 대응시켜 보면 범주의 정체가 한 번에 잡힌다.
>
> | 범주 | 온프레미스에서는 | AWS 대표 서비스 | 누가 하던 일인가 |
> |------|-----------------|----------------|----------------|
> | **컴퓨팅** | 서버 구매 → 랙 장착 → OS 설치 | EC2, Lambda, ECS/EKS | 인프라팀 |
> | **네트워킹** | 스위치·라우터·L4 장비·방화벽 정책 | VPC, ELB, Route 53, CloudFront | 네트워크팀 |
> | **스토리지** | NAS·SAN·백업 테이프 | S3, EBS, EFS | 인프라팀 |
> | **데이터베이스** | Oracle 설치·패치·백업·이중화 | RDS, Aurora, DynamoDB | DBA |
> | **보안·자격 증명** | AD/LDAP 계정, 서버 접근 권한 대장 | IAM, KMS, GuardDuty | 보안팀 |
>
> **"클라우드로 가면 이 다섯 팀의 일이 콘솔 화면과 JSON 정책으로 바뀐다"** 가 이 절의 요지다.

> 📌 **보완: 스토리지 3형제 — S3 vs EBS vs EFS (가장 많이 나오는 비교)**
>
> 책은 세 개를 나열만 하는데, **셋의 차이가 시험·면접·실무 모두에서 핵심**이다.
>
> | 구분 | **S3** | **EBS** | **EFS** |
> |------|--------|---------|---------|
> | 유형 | 객체 스토리지 | 블록 스토리지 | 파일 스토리지 |
> | 비유 | **창고** (물건을 통째로 넣고 뺌) | **노트북에 꽂은 SSD** | **팀 공유 네트워크 드라이브** |
> | 접근 방법 | HTTP API (REST) | EC2에 장착 후 OS가 디스크로 인식 | 여러 EC2가 동시에 마운트(NFS) |
> | 동시 연결 | 무제한 (인터넷 어디서나) | **원칙적으로 EC2 1대** | **여러 대 동시 가능** |
> | 부분 수정 | 불가 — 통째로 덮어씀 | 가능 (일반 디스크처럼) | 가능 |
> | 용량 | 무제한 (자동 확장) | 생성 시 지정 (수동 확장) | 자동 확장 |
> | 주 용도 | 이미지·첨부파일·로그·백업·정적 웹 | OS 디스크, DB 데이터 파일 | 여러 서버가 공유하는 파일 |
> | 상대 비용 | 가장 저렴 | 중간 | 가장 비쌈 |
>
> **판단 기준 한 줄:**
> ```
> 파일을 통째로 올리고 내리기만 한다        → S3
> 서버 한 대가 디스크처럼 읽고 써야 한다     → EBS
> 여러 서버가 같은 파일을 동시에 봐야 한다   → EFS
> ```
> **ERP에 대입하면:** OS와 Oracle 데이터 파일은 EBS, 전자결재 첨부파일·스캔 이미지는 S3, 여러 WAS가 공유하는 업로드 디렉터리는 EFS.

**답변 :**

#### (1) 컴퓨팅 — 언제 쓰나

| 상황 | 선택 | 이유 |
|------|------|------|
| 기존 온프레미스 서버를 그대로 옮기고 싶다 | **EC2** | OS부터 내가 통제 → 기존 구성을 거의 그대로 이전(Lift & Shift) |
| Spring Boot 앱을 24시간 돌린다 | **EC2 / ECS** | 상시 구동 + 상태 유지에 적합 |
| 파일 업로드 시 썸네일만 만들면 된다 | **Lambda** | 이벤트 발생 시에만 실행, 평소 비용 0 |
| 컨테이너로 배포하는데 서버 관리는 싫다 | **ECS Fargate** | 인스턴스 관리 없이 컨테이너만 신경 씀 |
| 야간 배치를 매일 1시간 돌린다 | **EC2 Spot / AWS Batch** | 중단돼도 재실행 가능 → 최대 90% 저렴 |

**예시**: 사내 ERP를 AWS로 옮긴다면 → WAS 서버는 **EC2**, 월말 정산 배치는 **Spot 인스턴스**, 첨부파일 바이러스 검사는 **Lambda**.

#### (2) 네트워킹 및 콘텐츠 전송 — 언제 쓰나

| 상황 | 선택 | 이유 |
|------|------|------|
| 서버들을 외부와 격리된 사설망에 두고 싶다 | **VPC** | AWS 안에 우리 전용 네트워크를 만듦 (모든 구축의 출발점) |
| 트래픽이 늘어 서버 여러 대에 분산해야 한다 | **ELB (ALB/NLB)** | L7/L4 부하 분산 + 헬스 체크 |
| `erp.company.com` 도메인을 연결하고 싶다 | **Route 53** | DNS 등록·라우팅, 장애 조치(Failover) |
| 해외 지사에서 접속이 느리다 | **CloudFront** | 전 세계 엣지에서 캐싱 → 지연시간 감소 |
| 사내망과 AWS를 안전하게 연결해야 한다 | **Direct Connect / Site-to-Site VPN** | 하이브리드 구성의 연결 고리 |

**예시**: 사내 ERP + AWS 하이브리드 → 사내망과 **VPN**으로 연결, 웹 계층 앞에 **ALB**, 정적 자원(이미지·JS)은 **CloudFront**.

#### (3) 스토리지 — 언제 쓰나

| 상황 | 선택 | 이유 |
|------|------|------|
| EC2에 OS와 DB 데이터를 저장 | **EBS** | 서버 전용 디스크 |
| 전자결재 첨부파일·스캔 이미지 보관 | **S3** | 무제한·저렴·URL로 바로 접근 |
| WAS 3대가 같은 업로드 폴더를 공유 | **EFS** | 다중 마운트 가능 |
| 법정 보존 7년짜리 회계 증빙 | **S3 Glacier / Deep Archive** | 꺼낼 일 거의 없음 → 최저 비용 |
| 정적 웹페이지(사내 공지 사이트) 호스팅 | **S3 정적 호스팅 + CloudFront** | 서버 없이 웹사이트 운영 |

#### (4) 데이터베이스 — 언제 쓰나

| 상황 | 선택 | 이유 |
|------|------|------|
| 기존 Oracle/MySQL ERP DB를 옮긴다 | **RDS** | 백업·패치·이중화를 AWS가 대행 |
| DB 성능을 더 원하고 MySQL 호환이면 된다 | **Aurora** | MySQL/PostgreSQL 호환 + 성능·가용성 강화 |
| 세션·조회 결과를 캐싱해 응답을 줄인다 | **ElastiCache (Redis)** | 인메모리 캐시 |
| 로그·이벤트처럼 스키마가 유연한 대용량 | **DynamoDB** | NoSQL, 무제한 확장 |
| DB 엔진을 커널 수준까지 튜닝해야 한다 | **EC2에 직접 설치** | RDS는 OS 접근이 막혀 있음 |

> **RDS를 못 쓰는 경우가 실무에서 꽤 있다.** OS 접근 불가, 특정 플러그인 미지원, 라이선스 문제 등. 그때는 EC2에 직접 설치하고 백업·이중화를 직접 구성한다. **"관리를 위임한 대가로 통제권을 잃는다"** 는 1.1.3의 트레이드오프가 그대로 반복된다.

#### (5) 보안 자격 증명 및 규격 준수 — 언제 쓰나

| 상황 | 선택 | 이유 |
|------|------|------|
| 팀원별로 접근 가능한 자원을 나눈다 | **IAM 사용자·그룹·정책** | 최소 권한 원칙 적용 |
| EC2가 S3에 접근해야 한다 | **IAM 역할(Role)** | **액세스 키를 코드에 넣지 않고** 임시 자격 증명 사용 |
| DB 비밀번호를 소스에 안 넣고 싶다 | **Secrets Manager / Parameter Store** | 자격 증명 분리 저장·자동 교체 |
| 저장 데이터를 암호화해야 한다 | **KMS** | 키 관리 + S3·EBS·RDS 암호화 연동 |
| 누가 무엇을 했는지 감사 로그가 필요하다 | **CloudTrail** | 모든 API 호출 기록 (규제 대응 필수) |
| 비정상 접근을 탐지하고 싶다 | **GuardDuty** | 위협 탐지 |

> **가장 중요한 한 줄:** **액세스 키를 코드·깃허브에 올리지 말 것.** EC2·Lambda에는 반드시 **IAM 역할**을 붙인다. AWS 사고 사례의 상당수가 깃허브에 올라간 액세스 키로 인한 것이다.

## ⚠️ 1.2 오해하기 쉬운 부분

| 오해 | 실제 |
|------|------|
| "리전 = 데이터센터 1개" | 리전은 **여러 AZ의 묶음**이고, AZ 하나가 다시 **데이터센터 여러 개**다. |
| "AZ에 나눠 배포하면 느려진다" | AZ 간은 전용 저지연 회선으로 연결되어 있다. **나누지 않는 쪽이 훨씬 위험하다.** |
| "리전은 아무거나 골라도 된다" | 리전마다 **가격·제공 서비스·지연시간**이 다르다. 국내 서비스는 보통 서울(`ap-northeast-2`). |
| "S3도 디스크니까 EC2에 마운트해서 쓰면 된다" | S3는 **객체 스토리지**라 일반 파일시스템처럼 부분 수정이 안 된다. 디스크가 필요하면 EBS, 공유 파일시스템이 필요하면 EFS. |
| "EC2를 정지(Stop)하면 비용이 0" | 인스턴스 요금은 멈추지만 **EBS 볼륨·Elastic IP 요금은 계속 나간다.** |
| "RDS는 DB 서버에 접속해서 뭐든 할 수 있다" | **OS 접근이 불가능**하다. 설정은 파라미터 그룹으로만 바꾼다. |
| "IAM은 유료 서비스" | **IAM 자체는 무료**다. (요금은 IAM으로 접근한 서비스에서 발생) |
| "서비스가 200개가 넘으니 다 알아야 한다" | 실무에서 쓰는 핵심은 **20개 남짓**이다. EC2·VPC·S3·RDS·IAM 다섯이 8할. |
