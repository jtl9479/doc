# Redis 학습 템플릿

> 유형: **개념 + 명령어 실습 + 설계 패턴**
> 적용: 학습_08_Redis.md의 Step 1~16

## 공통 원칙

| 원칙 | 설명 |
|------|------|
| **왜 먼저** | "DB만 쓰면 이런 성능 문제. Redis를 쓰면 이렇게 해결" |
| **비유 먼저** | 캐시/분산 락 개념을 일상 비유로 직관 잡기 |
| **트레이드오프** | 캐시의 모든 전략에 "얻는 것 vs 잃는 것" 명시 |
| **버전 차이** | Redis 6+(ACL, Client-side Caching), 7+(Functions) 언급 |

### 비유 예시
```
Redis = "포스트잇 메모판. 자주 찾는 정보를 메모판(메모리)에 적어두고 바로 확인. 서랍(DB) 뒤질 필요 없음"
캐시 = "냉장고. 자주 먹는 재료를 냉장고에 넣어두면 매번 마트(DB)에 안 가도 됨"
Cache Aside = "냉장고에 없으면 마트 가서 사오고, 냉장고에도 넣어둠"
캐시 스탬피드 = "냉장고가 비었는데 가족 5명이 동시에 마트로 달려감. 1명만 가면 되는데"
분산 락 = "화장실 잠금. 열쇠(SETNX)로 잠그고, 볼일 끝나면 열쇠 반납(DEL). 30초 자동 해제(TTL)는 안에서 쓰러질 경우 대비"
Pub/Sub = "교내 방송. 방송(Publish)하면 듣고 있는 사람(Subscribe)만 들음. 안 듣고 있었으면 못 들음(영속성 없음)"
Sentinel = "병원 모니터. 환자(Master) 상태를 감시하다 위급하면 대기 의사(Slave)를 투입"
```

### 트레이드오프 예시
```
캐시 도입: 조회 속도↑ ↔ 데이터 불일치 가능, 캐시 관리 복잡성
TTL 짧게: 데이터 신선도↑ ↔ Cache Miss↑ DB 부하↑
TTL 길게: Cache Hit↑ ↔ Stale 데이터 위험
분산 락(Redis): 빠름, DB 부하 없음 ↔ 단일 Redis 장애 시 락 실패
분산 락(DB): 정합성 확실 ↔ DB 부하↑ 동시성↓
RDB 영속성: 복구 빠름 ↔ 마지막 스냅샷 이후 유실
AOF 영속성: 유실 최소 ↔ 파일 큼, 복구 느림
```

## 설명 흐름
1. **왜 써야 하는가**: "이걸 안 쓰면/모르면 이런 성능 문제/장애"
2. **비유로 직관 잡기**
3. **핵심 개념 설명**
4. **redis-cli 명령어 예제** + Spring Data Redis 코드
5. **설계 패턴 + 트레이드오프**: "어떤 캐시 전략을 선택하고, 그 비용은?"
6. **장애 시나리오**: "Redis가 죽으면?" "메모리 가득 차면?"
7. **오해하기 쉬운 부분 + 버전 차이**:
```
"Redis는 캐시 전용이다" → 세션, 분산 락, 메시지 큐, 리더보드 등 다목적
"싱글 스레드라 느리다" → IO 멀티플렉싱 + 인메모리라 초당 10만+ 처리
"KEYS * 써도 된다" → O(n) 블로킹 → 프로덕션 전체 멈춤. SCAN으로 대체
"Redlock이 최선이다" → Martin Kleppmann 비판 존재. 실무에서 단일 Redis + Redisson이 더 일반적
"Secret이 Base64라 안전하다" → Base64는 인코딩이지 암호화가 아님
Redis 6+: ACL(사용자별 권한), Client-side Caching(로컬 캐시 + 무효화)
Redis 7+: Functions(Lua Script 대체)
```
8. **확인 질문**: 사용자 답변 → 피드백
```

```
