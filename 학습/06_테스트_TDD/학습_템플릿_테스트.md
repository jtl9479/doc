# 테스트/TDD 학습 템플릿

> 유형: **개념 설명 + TDD 실습**
> 적용: 학습_06_테스트_TDD.md의 Step 1~14

## 공통 원칙

| 원칙 | 설명 |
|------|------|
| **왜 먼저** | "테스트를 안 짜면/잘못 짜면 이런 일이 발생한다" |
| **비유 먼저** | 테스트 개념을 일상 비유로 직관 잡기 |
| **트레이드오프** | 테스트에도 비용이 있음. "모든 것을 테스트하면 좋지만 현실적 비용" |

### 비유 예시
```
단위 테스트 = "부품 검사. 엔진, 바퀴, 브레이크를 각각 검사"
통합 테스트 = "완성차 시운전. 부품이 합쳐졌을 때 제대로 동작하는지"
E2E 테스트 = "고객이 직접 시승. 실제 도로에서 운전해봄"
테스트 피라미드 = "부품 검사(많이) > 시운전(적당히) > 시승(최소). 위로 갈수록 비싸고 느림"
JUnit = "시험지 틀. 문제(테스트 메서드)를 적고, 정답(Assertion)을 채점"
@BeforeEach = "시험 전 연필/지우개 준비. 매 시험마다 새로 준비"
@ParameterizedTest = "같은 문제를 여러 학생(입력)에게 돌림. 반복 코드 제거"
@Nested = "시험지를 단원별로 묶기. '1단원: 더하기' 안에 문제 3개"
Stub = "녹음된 안내 멘트. '1번 누르면 A, 2번 누르면 B' 정해진 응답만"
Mock = "감시 카메라. 누가 언제 몇 번 왔는지 기록(verify). 행위 검증"
Spy = "위장 잠입. 진짜 직원처럼 일하면서 일부만 조작"
Fake = "모형 비행기. 진짜처럼 생겼지만 날지는 못함(InMemory DB)"
테스트 가능한 설계 = "조립식 가구. 부품(의존성)을 교체할 수 있게 설계 → 테스트 시 가짜 부품(Mock)으로 교체"
테스트 불가능한 설계 = "접착제로 붙인 가구. 부품 교체 불가 → 가짜로 교체 불가 → 테스트 불가"
FIRST = "좋은 시험의 조건. Fast(빨리), Independent(독립), Repeatable(반복 가능), Self-validating(자동 채점), Timely(적시)"
TDD = "시험 문제를 먼저 만들고(Red), 답안을 쓰고(Green), 답안을 깔끔하게 정리(Refactor)"
@SpringBootTest = "전체 시운전. 모든 부품(빈) 장착 후 테스트. 느리지만 실제에 가까움"
MockMvc = "시뮬레이터. 실제 서버 안 띄우고 HTTP 요청/응답 검증"
@WebMvcTest = "엔진(Controller)만 검사. 바퀴(Service)는 가짜"
TestContainers = "이동식 검사실. 실제 장비(DB/Redis) 가져와서 검사. 정확하지만 준비 오래 걸림"
H2 = "모형 검사실. 빠르지만 실제 장비와 동작이 약간 다를 수 있음"
특성화 테스트 = "현장 사진. 현재 상태를 그대로 찍어두고, 나중에 리팩토링 후 사진이 달라졌는지 비교"
```

### 트레이드오프 예시
```
Mock 사용: 빠름+격리 ↔ 실제 동작과 괴리, Mock 과다 시 깨지기 쉬움
Stub(상태 검증) vs Mock(행위 검증): Stub(결과 중심, 안정) ↔ Mock(호출 검증, 구현 변경에 민감)
TestContainers vs H2: TestContainers(정확, 실제 DB) ↔ H2(빠름, 동작 차이 가능)
@SpringBootTest vs @WebMvcTest: 전체(정확, 느림) ↔ 슬라이스(빠름, 다른 계층 Mock 필요)
TDD: 설계 개선+회귀 방지 ↔ 초기 속도 느림, 탐색적 코드에 부적합
높은 커버리지: 안전감↑ ↔ 의미 없는 테스트 양산, 유지보수 비용↑
@MockBean: 편리 ↔ Context 캐싱 깨짐 → 전체 테스트 느려짐
단위 테스트만: 빠름 ↔ 통합 문제 못 잡음
통합 테스트만: 실제 동작 검증 ↔ 느림, 불안정, 원인 특정 어려움
```

## 설명 흐름

### 개념 Step (1~8)
1. **왜 써야 하는가**: "이걸 안 하면/모르면 이런 버그가 프로덕션에 나감"
2. **비유로 직관 잡기**: 위 비유 활용
3. **핵심 개념 + 코드 예제 + 트레이드오프**
4. **오해하기 쉬운 부분**:
```
"커버리지 100% = 버그 없음" → 커버리지는 호출 여부만. Assertion 밀도가 핵심
"Mock을 많이 쓰면 좋다" → Mock 과다 = SRP 위반 신호. 행위 검증 과다 = 깨지기 쉬운 테스트
"TDD는 모든 코드에 적용해야 한다" → 탐색적 코드, UI, 프로토타입에는 부적합
"통합 테스트가 단위 테스트보다 좋다" → 느리고 불안정. 테스트 피라미드(단위 많이, 통합 적당히)
"@MockBean을 많이 쓰면 편하다" → Context 캐싱 깨져서 전체 테스트 느려짐
"테스트는 구현 세부사항을 검증해야 한다" → 행위(결과)를 검증. 구현 검증은 깨지기 쉬운 테스트
"Fake는 Mock보다 열등하다" → Fake(InMemory DB)가 Mock보다 실제에 가까울 수 있음
```
5. **확인 질문**: 사용자 답변 → 피드백
```
Step 1: "테스트 피라미드란? 왜 단위 테스트를 가장 많이 짜야 하는가?"
Step 2: "JUnit 5에서 @BeforeEach와 @BeforeAll의 차이는?"
Step 3: "@ParameterizedTest는 언제 쓰는가?"
Step 4: "Stub과 Mock의 차이는? 상태 검증 vs 행위 검증"
Step 5: "Mockito when/thenReturn과 verify의 역할 차이는?"
Step 6: "ArgumentCaptor는 언제 쓰는가?"
Step 7: "이 코드는 왜 테스트하기 어려운가? 어떻게 리팩토링하는가?"
Step 8: "FIRST 원칙 5가지는? '구현이 아닌 행위를 테스트'하라는 이유는?"
Step 9: "TDD의 Red-Green-Refactor를 설명해보세요"
Step 11: "@WebMvcTest vs @SpringBootTest 차이와 선택 기준은?"
Step 12: "TestContainers vs H2 트레이드오프는?"
Step 13: "테스트 커버리지 100%가 목표가 아닌 이유는? Mutation Testing이란?"
Step 14: "레거시 코드에 테스트를 추가하는 전략은? 특성화 테스트란?"
```
6. **정리 + 다음 안내**

### TDD Step (9~10): **Claude가 정답을 먼저 주지 않음**
1. **요구사항 제시**
2. **Red**: 사용자가 테스트 먼저 작성
3. **테스트 리뷰** (경계값 누락? Given-When-Then?)
4. **Green**: 사용자가 구현
5. **Refactor**: 리팩토링 제안 + 트레이드오프
6. **오해 확인**: "TDD에서 흔히 실수하는 부분" 짚기
7. **다음 요구사항 추가** (사이클 반복)

## Step별 특이사항

### 기초 (Step 1)
- Step 1 (왜 테스트): 부품 검사/시운전/시승 비유. 테스트 피라미드. "테스트 안 짜면 이런 일이" 실무 사례

### JUnit (Step 2~3)
- Step 2 (JUnit 기본): 시험지 틀 비유. @Test, @BeforeEach, Assertions, AssertJ. "AssertJ가 왜 JUnit Assertions보다 좋은가"
- Step 3 (JUnit 심화): @ParameterizedTest(같은 문제 여러 학생), @Nested(단원별 묶기). BDD 스타일 구성

### 테스트 더블 (Step 4~6)
- Step 4 (테스트 더블): **Stub(녹음 안내) vs Mock(감시 카메라) vs Spy(위장 잠입) vs Fake(모형) 비유가 핵심**. 상태 검증 vs 행위 검증 구분
- Step 5 (Mockito 기본): when/thenReturn + verify 코드 예제. any() matcher 규칙
- Step 6 (Mockito 심화): ArgumentCaptor(인자 캡처), BDD style(given-when-then), @Spy. "Mockito로 static 메서드 Mock이 어려운 이유"

### 테스트 원칙 (Step 7~8)
- Step 7 (테스트 가능한 설계): 조립식 가구(교체 가능) vs 접착제 가구(교체 불가) 비유. **"Mock이 5개 이상 → SRP 위반 신호"**. DIP로 테스트 가능하게 리팩토링
- Step 8 (좋은 테스트): FIRST 원칙(좋은 시험 조건). 테스트 냄새. "구현이 아닌 행위를 테스트". AAA/Given-When-Then 구조. Context Caching 최적화

### TDD (Step 9~10)
- Step 9 (TDD 이론): 시험 문제 먼저 만들기 비유. Red→Green→Refactor 사이클. TDD의 이점/한계
- Step 10 (TDD 실전): **Claude가 정답 먼저 주지 않음**. ERP 시나리오(금액 계산, 재고 차감)로 TDD. 점진적 일반화(Triangulation). 경계값 테스트

### Spring 테스트 (Step 11~12)
- Step 11 (Spring 테스트): 전체 시운전(@SpringBootTest) vs 엔진만(@WebMvcTest) 비유. MockMvc(시뮬레이터). **@MockBean이 Context 캐싱을 깨뜨리는 이유 + 대응(공통 설정 통합)**
- Step 12 (TestContainers): 이동식 검사실(TestContainers) vs 모형 검사실(H2) 비유. CI/CD 연동(Docker-in-Docker)

### 전략/실전 (Step 13~14)
- Step 13 (테스트 전략): "어디를 테스트? 어디까지?". 비용-효과 판단. 팀 비율(7:2:1). **Mutation Testing**(커버리지의 한계 보완)
- Step 14 (레거시): 현장 사진(특성화 테스트) 비유. 이음새(Seam) 찾기. "버그 수정 시 먼저 테스트 작성 → 수정 → 통과" 패턴. ERP 레거시 경험 연결

## 학습 방식 원칙
- TDD Step은 **Claude가 정답을 먼저 주지 않음**. 사용자가 먼저 작성 → 리뷰
- ERP 도메인 활용: 금액 계산, 재고 차감, 할인 정책 등으로 TDD 연습
- 코드 예제는 항상 **테스트 코드 + 프로덕션 코드** 쌍으로 제시
- "이 코드는 왜 테스트하기 어려운가?" → 사용자가 식별하게 하고 피드백
