## 2.1 AWS 컴퓨팅 서비스

### 2.1.1 컴퓨팅 정의

> **Q.** 컴퓨팅 정의 설명 필요

**컴퓨팅(Computing)은 데이터를 처리하는 연산 능력 자체**를 말한다. 구체적으로는 **CPU와 메모리**가 하는 "계산하고 판단하는 일"이다.

IT 인프라의 세 축 중 하나다.

| 축 | 하는 일 | AWS |
|----|--------|-----|
| **컴퓨팅** | 연산 — "생각한다" | EC2, Lambda, ECS |
| **스토리지** | 보관 — "기억한다" | S3, EBS, EFS |
| **네트워킹** | 전달 — "말한다" | VPC, ELB, Route 53 |

온프레미스에서는 연산 능력을 확보하려면 **서버라는 장비를 사야** 했다. 클라우드는 이 관계를 끊고 연산 능력을 **장비가 아니라 서비스로** 빌려 쓴다. Lambda처럼 서버가 아예 보이지 않는 형태도 포함되기 때문에 "서버 임대"가 아니라 **컴퓨팅 서비스**라고 부른다.

추상화 수준에 따라 **가상 머신(EC2) → 컨테이너(ECS/EKS) → 서버리스(Lambda)** 로 나뉘며, 아래로 갈수록 관리 부담이 줄고 제약이 늘어난다.

#### 워크로드 (Workload)

> **Q.** 워크로드 용어 설명

**워크로드는 시스템이 처리해야 하는 '일' 그 자체다.** 영어 그대로 work(일) + load(짐), 즉 **시스템에 지워진 일거리**를 말한다.

예를 들어 *"매월 25일에 급여를 계산해서 명세서를 발송한다"* — 이것이 하나의 워크로드다. 그리고 이 일을 해내기 위해 WAS 2대, Oracle DB, 배치 서버, 파일 스토리지가 동원되는데, **그 자원 묶음까지 합쳐서** 워크로드라고 부른다.

> **왜 '서버'가 아니라 '워크로드'로 세는가**
> 온프레미스에서는 "급여 서버 2대"처럼 **장비 단위**로 셌다. 클라우드는 Auto Scaling으로 서버 수가 2대 → 8대 → 3대로 계속 변하기 때문에 장비로 셀 수가 없다. 변하지 않는 것은 **"무슨 일을 하는가"** 뿐이다.
> 그래서 설계·관리·과금의 단위가 **장비에서 일(워크로드)로 옮겨갔다.** AWS 문서가 "서버"라는 말 대신 "워크로드"를 쓰는 이유다.

문맥에 따라 일의 *양*을 가리키기도 한다. "월말에는 워크로드가 5배로 늘어난다"처럼 쓰면 부하량을 뜻한다.

### 2.1.2 AWS 컴퓨팅 서비스
```
AWS 컴퓨팅 서비스는 퍼블릭 클라우드에서 컴퓨팅 자원을 활용하여 다양한 워크로드를 수행할 수 있는 서비스이다.

컴퓨팅 자원을 사용한 만큼의 비용만 지불하면 수 분 내로 가상의 서버 자원을 생성하고 관리할 수 있다.

AWS는 다양한 형식의 컴퓨팅 서비스를 제공한다
```
* **EC2(Elastic Compute Cloud)** : 클라우드 환경에서 서버 자원을 인스턴스라는 가상 머신 형태로 제공하는 가장 기본적인 AWS 컴퓨팅 서비스
* **Lambda** : 서버리스 컴퓨팅 서비스로 별도의 서버 설정이 없는 환경을 제공하여 코드만 실행해 주는 서비스
* **Lightsail** : 독립적인 환경을 제공, 최소한의 설정만으로도 손쉽게 사용 가능한 컴퓨팅 서비스

#### 3종 비교

> **Q.** 각 AWS 컴퓨팅 주요 서비스 비교 및 설명

```
EC2       = 렌터카     — 차만 빌려줌. 기름·정비는 내가. 시간당 과금
Lightsail = 패키지여행 — 차·숙소·일정 한 세트. 정해진 코스지만 편하고 월 정액
Lambda    = 택시       — 탈 때만 부르고 탄 만큼만. 단, 15분 넘는 장거리는 거부
```

| | **EC2** | **Lightsail** | **Lambda** |
|---|---|---|---|
| 유형 | IaaS | IaaS (패키지형) | 서버리스(FaaS) |
| **과금** | 초/시간 단위 | **월 정액** | 실행 횟수 × 시간 × 메모리 (유휴 시 0원) |
| OS 접근 | 완전 (SSH) | 가능 | 불가 |
| **실행 시간** | 무제한 | 무제한 | **최대 15분** |
| 상태 유지 | 가능 | 가능 | **불가 (무상태)** |
| 확장 | Auto Scaling 구성 | 수동(플랜 변경) | 자동 |
| 적합 | 상시 구동, 기존 서버 이전 | 소규모·단순·비용 예측 | 이벤트 기반, 짧은 작업 |

**EC2** — OS부터 전부 내 통제라 온프레미스 서버를 그대로 옮기기(Lift & Shift)에 가장 적합. 대신 OS 패치·보안·확장이 전부 사용자 책임. VPC·보안그룹·EBS·ELB·IAM 역할이 전부 EC2를 통해 맞물리므로 **가장 먼저 깊게 배워야 한다.**

**Lambda** — 이벤트(S3 업로드, API 요청, 스케줄)가 있을 때만 실행. 제약 3가지가 핵심이다.
```
15분 제한   → 긴 배치·스트리밍 불가
무상태      → 메모리에 세션 보관 불가 (DynamoDB·Redis 필요)
콜드 스타트 → 한동안 호출 없으면 첫 요청이 느림
```
> ⚠️ **Java는 JVM 기동 때문에 콜드 스타트가 특히 길다.** 대응: Provisioned Concurrency, SnapStart, GraalVM Native Image. 면접 단골.

**Lightsail** — EC2 + 스토리지 + 고정 IP + 전송량을 월 정액 한 세트로 판매. WordPress 같은 블루프린트를 클릭 배포. 대신 세밀한 제어가 안 되고 다른 VPC 자원과 붙이려면 피어링이 필요해, 규모가 커지면 EC2로 이관하게 된다.

> **책에 없는 나머지**: ECS(컨테이너) · EKS(관리형 K8s) · Fargate(서버 없이 컨테이너) · Elastic Beanstalk(코드만 올리면 자동 구성) · AWS Batch · App Runner.
> ```
> EC2 → Beanstalk → ECS/EKS → Fargate → App Runner → Lambda
> 통제권 큼 ─────────────────────────────→ 관리 부담 적음
> ```

#### 선택 판단

```
15분 내에 끝나고 이벤트 기반인가?  → Lambda
컨테이너로 배포하는가?             → ECS/EKS (서버 관리 싫으면 Fargate)
작고 단순하고 비용 예측이 중요한가? → Lightsail
그 외                              → EC2
```

ERP에 대입하면 — WAS 상시 구동은 **EC2 + 예약 인스턴스**, 월말 정산 배치는 **Spot / Batch**, 첨부파일 검사는 **Lambda**, 30분짜리 야간 리포트는 **15분 제한 때문에 Lambda 불가**.

### ⚠️ 2.1 오해

- **"서버리스 = 서버가 없다"** → 서버는 있다. AWS가 관리해서 안 보일 뿐.
- **"Lambda가 항상 싸다"** → 호출이 잦고 상시 구동에 가까우면 EC2보다 비싸진다. 유휴 시간이 길 때 이득.
- **"EC2 정지하면 비용 0"** → 인스턴스 요금만 멈춘다. EBS·Elastic IP는 계속 과금.
- **"워크로드 = 서버"** → 서버 여러 대 + DB + 코드를 묶은 **시스템 단위**다.

## 2.2 Amazon EC2
Amazon EC2(Amazon Elastic Compute Cloud)는 AWS의 퍼블릭 클라우드 환경에서 확장 가능한 컴퓨팅 자원을 제공하여 가상의 서버를 운영할 수 있는 서비스이다.

### 2.2.1 Amazon EC2 인스턴스
Amazon EC2 인스턴스는 가상의 컴퓨팅 환경으로 CPU, 메모리, 스토리지, 네트워킹 용량을 결정하는 다양한 인스턴스 유형을 제공한다. 즉 클라우드 환경에서 필요한 만큼 컴퓨팅 자원을 사용하고, 사용이 끝나면 자원을 반납하는 형태로 임의로 구성된 가상 서버를 인스턴스라고 한다.

#### 인스턴스 유형

EC2는 500개가 넘는 인스턴스 유형을 제공하여 사용자 목적과 비즈니스 환경에 맞게 최적화된 선택을 할 수 있다.

인스턴스 유형은 크게 범용, 컴퓨팅 최적화, 메모리 최적화, 가속 컴퓨팅, 스토리지 최적화, HPC 최적화로 분류한다. 각 인스턴스 유형별로 명칭을 부여해서 CPU, 메모리, 네트워크 등 자원을 정의한다.

> **명칭 규칙** — `m5.large` = **패밀리(m)** + **세대(5)** + **크기(large)**. 숫자가 클수록 최신 세대다.
>
> | 분류 | 패밀리 | 쓰는 곳 |
> |------|-------|--------|
> | 범용 | `t`, `m` | 웹 서버, WAS, 개발 서버 |
> | 컴퓨팅 최적화 | `c` | 배치 연산, 인코딩 |
> | 메모리 최적화 | `r`, `x` | 대용량 DB, 캐시 |
> | 스토리지 최적화 | `i`, `d` | 데이터 웨어하우스, 로그 |
> | 가속 컴퓨팅 | `g`, `p` | AI 학습·추론, 렌더링 |
> | HPC 최적화 | `hpc` | 시뮬레이션, 과학 연산 |

#### 인스턴스 상태
인스턴스 상태는 일반적으로 일곱 가지로 분류할 수 있으며, 어떤 행위에 최종적으로 도달하는 상태와 진행 과정에 따른 상태로 나눌 수 있다.

최종적으로 도달하는 상태는 실행 중, 중지됨, 종료됨 상태이며, 진행 과정에 따른 상태는 대기 중, 중지 중, 재부팅, 종료 중 상태이다.

1. 최초 인스턴스를 시작하는 행위 : 대기 중 → 실행 중
2. 실행 중인 인스턴스를 중지하는 행위 : 실행 중 → 중지 중 → 중지됨 (인스턴스 종료가 아닌 일시적 중지 상태로 다시 시작 가능)
3. 중지된 인스턴스를 시작하는 행위 : 중지됨 → 대기 중 → 실행 중
4. 중지된 인스턴스를 종료하는 행위 : 중지됨 → 종료 중 → 종료됨 (인스턴스 영구 삭제)
5. 실행 중인 인스턴스를 종료하는 행위 : 실행 중 → 종료 중 → 종료됨 (인스턴스 영구 삭제)

> **Q.** 인스턴스 수명주기 그림으로 그려달라

```
                    ┌─────────── 재부팅(rebooting) ───────────┐
                    │                                         │
                    ↓                                         │
  [시작]  →  대기 중  →  ●실행 중  ────────────────────────────┘
           (pending)   (running)
                           │  │
              중지 ────────┘  └──────── 종료
                │                         │
                ↓                         ↓
            중지 중                     종료 중
          (stopping)              (shutting-down)
                │                         │
                ↓                         ↓
            ●중지됨  ── 종료 ──────→   ●종료됨
           (stopped)                 (terminated)
                │                    ※ 되돌릴 수 없음
                └── 시작 → 대기 중 ──→ 실행 중

  ● = 최종 도달 상태 (실행 중 / 중지됨 / 종료됨)
```

> **Q.** 중지됨, 종료됨의 차이

| | **중지됨 (stopped)** | **종료됨 (terminated)** |
|---|---|---|
| 되돌리기 | **가능** — 다시 시작 | **불가** — 영구 삭제 |
| 인스턴스 요금 | 청구 안 됨 | 청구 안 됨 |
| **EBS 루트 볼륨** | 유지 | **기본적으로 삭제** |
| 인스턴스 스토어 | **데이터 소멸** | 데이터 소멸 |
| 퍼블릭 IP | **반납됨** (재시작 시 새 IP) | 반납됨 |
| 프라이빗 IP·인스턴스 ID | 유지 | 소멸 |

> ⚠️ **중지해도 비용이 0이 되지는 않는다.** 인스턴스 요금은 멈추지만 **EBS 볼륨 요금은 계속 청구**된다. 보유 중인 Elastic IP도 마찬가지다.

### 2.2.2 AMI(Amazon Machine Image)

AMI는 인스턴스를 시작할 때 필요한 정보를 제공하는 것으로 운영체제와 소프트웨어를 적절히 구성한 상태로 제공되는 템플릿이다.

인스턴스를 생성할 때는 AMI를 지정해야 하며, 하나의 AMI로 동일한 구성의 여러 인스턴스를 손쉽게 생성할 수 있다. 이런 AMI는 사용자 정의 AMI를 생성하여 활용할 수 있고, AWS Marketplace에서 제공하는 서드 파티용 AMI를 선택하거나 AWS 자체적으로 정의된 기본 AMI를 선택할 수 있다.

> **Q.** 사용자 정의 AMI 생성 및 배포 과정 설명

```
1. 기준 인스턴스 준비   기본 AMI로 EC2 생성 → OS 패치, JDK·Tomcat 설치, 설정 완료
2. 이미지 생성          콘솔에서 [이미지 생성] → 내부적으로 EBS 스냅샷을 떠서 AMI 등록
3. 배포                 이 AMI로 인스턴스를 몇 대든 동일하게 생성
```

**왜 쓰는가** — 서버를 늘릴 때마다 설치를 반복하지 않기 위해서다. Auto Scaling이 새 인스턴스를 띄울 때도 이 AMI를 쓰므로, **확장의 전제 조건**이 된다.

> ⚠️ AMI는 **만든 리전에만 존재**한다. 다른 리전에서 쓰려면 복사(Copy AMI)해야 한다.
> 이미지 생성 시 인스턴스가 재부팅되므로(기본 동작), 운영 중인 서버에서는 주의한다.


### 2.2.3 Amazon EC2 스토리지

AMI를 활용하여 Amazon EC2 인스턴스 환경을 설정했다면 다음으로 어떤 저장소를 사용할지 결정해야 한다.
EC2 인스턴스가 사용하는 데이터를 저장하는 공간으로, 서버 자원에서 발생되는 다양한 데이터를 보관하려면 필수적으로 존재해야 하는 요소이다.

스토리지 유형은 기본적으로 인스턴스 스토어와 Amazon EBS(Elastic Block Store)로 나뉜다.

#### 인스턴스 스토어
인스턴스에 바로 붙어 있는 저장소로, EC2 인스턴스를 생성하면 기본적으로 존재하는 스토리지이다.
일부 인스턴스 유형은 인스턴스 스토어를 지원하지 않는다.
인스턴스와 직접 붙어 있는 구조 덕분에 매우 빠른 I/O를 보장하는 장점이 있지만 EC2 인스턴스를 중지하거나 종료하면 인스턴스 스토어에 저장된 데이터가 모두 손실된다는 단점이 있다.
이러한 측면에서 임시적인 데이터 저장소로 사용하며, 장기적 보존이 필요한 데이터는 저장하지 않는다.

> ⚠️ **"기본적으로 존재한다"는 오해를 부른다.** 오늘날 대부분의 인스턴스는 **EBS를 루트 볼륨으로** 부팅하고, 인스턴스 스토어는 이를 지원하는 유형(`i`, `d`, `m5d` 등 이름에 `d`가 붙은 것)에만 **추가로** 붙는다. 기본값은 EBS다.
>
> 데이터가 사라지는 시점도 정확히 구분해야 한다. **재부팅(reboot)은 유지**, **중지(stop)·종료(terminate)·하드웨어 장애는 소멸**이다.

#### Amazon EBS(Elastic Block Store)
외장 하드디스크와 비슷한 개념으로 인스턴스에 연결 및 제거를 하는 형태로 구성되는 블록 스토리지이다.

인스턴스 스토어와 다르게 직접 연결된 구조가 아닌 인스턴스가 네트워킹을 통해 Amazon EBS에 접근하여 연결되는 구조로, 영구 보존이 가능한 스토리지이다.
즉 EC2 인스턴스가 중지되거나 종료되어도 Amazon EBS에 데이터는 그대로 유지할 수 있다.
EBS는 관리 콘솔로 스냅샷을 생성하여 백업하거나 EBS 연결을 해제한 후 다른 인스턴스에 연결할 수 있다는 특징이 있다.

> ⚠️ **"종료되어도 유지된다"에는 예외가 있다. 루트 볼륨은 인스턴스를 종료하면 함께 삭제된다.**
> 삭제 여부는 볼륨의 `DeleteOnTermination` 값으로 정해지며, 기본값은 볼륨 종류와 붙인 시점에 따라 다르다. 남기려면 인스턴스 시작 시 이 옵션을 꺼야 한다.

> **Q.** 인스턴스 스토어와 EBS 비교표 작성

| | **인스턴스 스토어** | **Amazon EBS** |
|---|---|---|
| 연결 방식 | 호스트에 **직접 부착** | **네트워크**로 연결 |
| 영속성 | 중지·종료 시 **소멸** | **유지** (루트 볼륨은 종료 시 삭제) |
| 속도 | 매우 빠름 | 빠름 (네트워크 경유) |
| 분리·재연결 | 불가 | **가능** (다른 인스턴스에 옮겨 붙임) |
| 스냅샷 백업 | 불가 | **가능** |
| 용량 변경 | 불가 (유형에 고정) | 가능 |
| 요금 | 인스턴스 요금에 포함 | **별도 과금** (중지 중에도) |
| 용도 | 캐시, 임시 파일, 버퍼 | OS 디스크, DB 데이터, 보존할 파일 |

### 2.2.4 Amazon EC2 네트워킹
EC2 인스턴스는 어떤 서비스를 수행하는 특수한 목적으로 만들어진 가상 서버 자원이다.
해당 서비스를 제공하려면 통신이 가능한 환경으로 구성해야 한다.

#### Amazon VPC(Virtual Private Cloud)
AWS 퍼블릭 클라우드 안에서 논리적으로 격리된 가상의 클라우드 네트워크이다.
EC2 인스턴스는 별도로 구성된 Amazon VPC 안에서 생성되며, 해당 VPC를 통해 네트워킹 된다.

#### 네트워크 인터페이스
EC2 인스턴스도 네트워킹을 수행할 수 있는 네트워크 인터페이스가 필요하다.
AWS에서는 ENI(Elastic Network Interface)라는 논리적 네트워크 인터페이스가 VPC 내에 생성되며, ENI를 EC2 인스턴스에 연결해서 네트워킹을 수행한다.

#### IP 주소
네트워크 인터페이스에는 IP 주소가 있으며 IP 주소로 대상을 구분하고 네트워킹을 수행한다.
IP 주소는 프라이빗 IP와 퍼블릭 IP로 나뉜다.
프라이빗 IP는 내부 구간의 통신용 사설 IP고, 퍼블릭 IP는 외부 구간의 통신용 IP이다.

> ⚠️ **퍼블릭 IP는 인스턴스를 중지했다 시작하면 바뀐다.** 도메인이나 방화벽 화이트리스트에 IP를 물려 놨다면 전부 깨진다.
> 고정이 필요하면 **Elastic IP**(고정 퍼블릭 IP)를 할당한다.
> 반면 **프라이빗 IP는 인스턴스가 살아 있는 동안 바뀌지 않는다.**
>
> **퍼블릭 IPv4는 연결 여부와 관계없이 과금된다.** 오래된 교재·블로그에는 "붙여 두면 무료, 놀리면 과금"으로 되어 있는데 2024년 2월에 바뀐 내용이다.

### 2.2.5 Amazon EC2 보안

#### 보안 그룹(security group)
보안 그룹은 EC2 인스턴스의 송수신 트래픽을 제어하는 가상의 방화벽 역할을 한다.

EC2 인스턴스 기준으로 수신 트래픽에 대한 인바운드 규칙과 송신 트래픽에 대한 아웃바운드 규칙으로 되어 있으며, 대상 트래픽 허용 여부를 결정한다.
즉 EC2 인스턴스로 들어오는 트래픽을 허용하거나 반대로 나가는 트래픽을 허용하는 규칙을 정의할 수 있다.
트래픽을 정의하는 방법에 프로토콜, 포트 번호, IP 대역 등이 있다.

> **보안 그룹의 두 가지 성질** (일반 방화벽과 다른 점)
> - **허용(Allow) 규칙만 있다.** 거부 규칙을 쓸 수 없고, 규칙에 없으면 자동으로 차단된다.
> - **상태 저장(Stateful)이다.** 인바운드로 허용한 요청의 응답은 아웃바운드 규칙과 무관하게 자동으로 나간다.

#### 키페어(key pair)
EC2 인스턴스에 SSH로 접근할 때 자격을 증명하는 보안 키이다.
키 페어는 퍼블릭 키와 프라이빗 키로 구성되며, 퍼블릭 키는 EC2 인스턴스에 저장되고,
프라이빗 키는 사용자 컴퓨터에 별도로 저장된다. EC2 인스턴스를 생성한 후 가상 서버에 접근하여
설정이 필요하며 사용자가 보관하고 있는 프라이빗 키를 활용해서 자격을 증명하고 접근할 수 있다.

> ⚠️ **프라이빗 키는 생성 시 단 한 번만 내려받을 수 있고, AWS는 보관하지 않는다.** 분실하면 해당 인스턴스에 SSH로 접속할 방법이 없다.

> **Q.** VPC, 보안 그룹, 키페어의 각각 역할

셋 다 "접근"과 관련되지만 **막는 층이 다르다.**

| | 역할 | 통제 대상 | 비유 |
|---|---|---|---|
| **VPC** | 인스턴스를 **어느 네트워크에 놓을지** | 위치 | 어느 **건물·층**에 사무실을 둘지 |
| **보안 그룹** | 그 인스턴스에 **어떤 트래픽을 통과시킬지** | 통로 | 사무실 **출입문의 허용 명단** |
| **키페어** | 접속한 사람이 **본인인지 증명** | 신원 | 문을 연 뒤 확인하는 **신분증** |

```
외부 요청 → [VPC: 접근 가능한 위치인가]
          → [보안 그룹: 이 포트·IP가 허용 목록에 있는가]
          → [키페어: SSH 접속자가 맞는 키를 갖고 있는가]  → 접속 성공
```

세 개는 대체 관계가 아니라 **순서대로 통과해야 하는 관문**이다. 보안 그룹에서 22번 포트를 막으면 키가 맞아도 접속되지 않고, 키가 없으면 포트가 열려 있어도 로그인되지 않는다.

### 2.2.6 Amazon EC2 모니터링
EC2 인스턴스 모니터링은 서비스 안정성과 가용성, 성능 유지에 필요한 중요한 영역이다.
특히 불특정 다수에게 제공되는 서비스는 언제 어느 시점에 트래픽이 몰려 부하가 발생할지 알 수 없다.
EC2 인스턴스의 자원은 유한하며, 가용 범위를 초과하는 부하가 걸리면 장애가 발생할 수 있다.
이런 측면에서 모니터링은 실제 서비스를 운영할 때 중요하게 살펴볼 영역이며, 실제 모니터링 및 경보를 수행할 때는 다음과 같은 모니터링 계획을 정의해서 생성해야 한다.
* 모니터링 목표
* 모니터링 대상 자원
* 모니터링 빈도
* 모니터링 수행 도구
* 모니터링 작업을 수행할 사람
* 문제가 발생할 때 경보를 알려야 할 대상

EC2 모니터링은 수동 모니터링과 자동 모니터링으로 분류할 수 있으며, 각 분류에 따라 다양한 모니터링 도구가 있다.

#### 수동 모니터링 도구
관리자가 직접 관리 콘솔을 이용하여 모니터링을 수행하는 것이다.
EC2 대시보드에서 간단한 통계 정보를 확인하거나 Amazon CloudWatch라는 모니터링 전용 서비스를 이용한다.

#### 자동 모니터링 도구
대상 자원의 지표에 임곗값을 정하고, 조건을 만족하면 경보를 발생시키는 형태의 동적 모니터링 방법을 의미한다.
Amazon CloudWatch라는 경보 시스템을 이용하여 동적으로 단일 지표를 관할하고 지정된 임곗값을 기준으로 경보 작업을 수행할 수 있다. 이런 경보 작업은 Amazon SNS(Simple Notification Service)를 통해 관리자에게 알림을 전송하거나 오토 스케일링 서비스와 연계되어 인스턴스 확장 같은 후속 동작을 수행하도록 구성한다.

> **Q.** 자동 모니터링, 수동 모니터링 비교

| | **수동 모니터링** | **자동 모니터링** |
|---|---|---|
| 방식 | 사람이 콘솔을 열어 확인 | 임곗값 조건으로 자동 감시 |
| 시점 | **문제가 생긴 뒤** 찾아봄 | **조건 충족 즉시** 경보 |
| 도구 | EC2 대시보드, CloudWatch 지표 화면 | CloudWatch 경보 + SNS / Auto Scaling |
| 후속 동작 | 사람이 판단·조치 | 알림 전송, 인스턴스 자동 확장 |
| 한계 | 야간·주말에 놓침, 사람이 늘 봐야 함 | 임곗값을 잘못 잡으면 오탐·누락 |

실무에서는 둘을 함께 쓴다. **자동 경보로 알림을 받고, 수동 대시보드로 원인을 찾는다.**

> ⚠️ **CloudWatch가 기본으로 주는 지표에 메모리는 없다.** CPU·네트워크·디스크 I/O는 자동 수집되지만, **메모리 사용량과 OS·애플리케이션 로그는 CloudWatch Agent를 인스턴스에 설치**해야 올라간다. 하이퍼바이저 밖에서는 게스트 OS 내부를 볼 수 없기 때문이다.

---

> **Q.** EC2 서비스 — AMI부터 모니터링까지 전체적인 흐름도

```
 ① 무엇으로 만들까        AMI            OS + 소프트웨어 템플릿 선택
                            ↓
 ② 얼마나 크게            인스턴스 유형   m5.large 등 CPU·메모리 결정
                            ↓
 ③ 어디에 놓을까          VPC / 서브넷    격리된 네트워크 위치 지정
                            ↓
 ④ 어떻게 통신할까        ENI + IP        네트워크 인터페이스, 프라이빗·퍼블릭 IP
                            ↓
 ⑤ 누구를 들일까          보안 그룹       포트·IP 허용 규칙
                            ↓
 ⑥ 누가 접속할까          키페어          SSH 자격 증명
                            ↓
 ⑦ 어디에 저장할까        EBS / 인스턴스 스토어
                            ↓
                    ●  EC2 인스턴스 실행 (running)
                            ↓
 ⑧ 잘 돌고 있나           CloudWatch      지표 수집 → 임곗값 초과 시 경보
                            ↓
                    SNS 알림  /  Auto Scaling 확장
```

①~⑦은 **인스턴스를 만들 때 정하는 것**, ⑧은 **만든 뒤 운영하면서 보는 것**이다.
콘솔의 인스턴스 시작 마법사가 묻는 순서도 이와 거의 같다.

### ⚠️ 2.2 오해

- **"중지하면 요금이 0"** → 인스턴스 요금만 멈춘다. **EBS 볼륨과 퍼블릭 IPv4는 계속 과금.**
- **"종료해도 EBS 데이터는 남는다"** → **루트 볼륨은 종료 시 함께 삭제**된다.
- **"Elastic IP는 붙여 두면 무료"** → 지금은 **연결 여부와 무관하게 퍼블릭 IPv4가 과금**된다. (2024.02 변경)
- **"인스턴스 스토어가 기본 스토리지"** → 대부분의 인스턴스는 **EBS로 부팅**한다. 인스턴스 스토어는 지원 유형에만 추가된다.
- **"재부팅하면 인스턴스 스토어 데이터가 날아간다"** → **재부팅은 유지**된다. 소멸하는 건 중지·종료·하드웨어 장애다.
- **"퍼블릭 IP는 고정"** → 중지 후 시작하면 바뀐다. 고정하려면 **Elastic IP**.
- **"보안 그룹에 차단 규칙을 넣는다"** → **허용 규칙만** 존재한다. 목록에 없으면 자동 차단.
- **"CloudWatch가 메모리도 본다"** → 기본 지표에 **메모리·로그는 없다.** Agent 설치 필요.
