# Docker/CI/CD/관찰성 학습 템플릿

> 유형: **개념 + 명령어/설정 실습 + 파이프라인 구축**
> 적용: 학습_09_Docker_CICD_관찰성.md의 Step 1~19

## 공통 원칙

| 원칙 | 설명 |
|------|------|
| **왜 먼저** | "이것 없이 운영하면 이런 문제(수동 배포 실수, 장애 감지 못 함)" |
| **비유 먼저** | 컨테이너/파이프라인/모니터링 개념을 일상 비유로 직관 잡기 |
| **트레이드오프** | Dockerfile 최적화, 배포 전략, 모니터링 수준에 트레이드오프 명시 |

### 비유 예시
```
컨테이너 = "도시락 통. 음식(앱) + 수저(의존성) + 양념(설정)을 한 통에 담아서 어디서든 먹을 수 있음"
VM = "이동식 주방 트럭. 주방(OS) 통째로 가져감. 무겁지만 완전 독립"
Docker 이미지 = "도시락 레시피(Dockerfile). 레시피대로 만들면 항상 같은 도시락"
Docker Compose = "세트 메뉴 주문. '앱+DB+Redis+Kafka' 한 번에 주문(up), 한 번에 치움(down)"
CI/CD = "자동 공장 라인. 코드 커밋(원재료 투입) → 자동 빌드(조립) → 자동 테스트(검수) → 자동 배포(출하)"
Prometheus = "체온계/혈압계. 주기적으로 측정(Pull)해서 기록"
Grafana = "건강 대시보드. 측정값을 그래프로 보여줌. 이상하면 알림"
분산 추적 = "택배 추적. 주문번호(Trace ID)로 '어디를 거쳐 어디서 지연됐는지' 추적"
```

### 트레이드오프 예시
```
멀티 스테이지 빌드: 이미지 작음 ↔ Dockerfile 복잡
alpine 베이스: 이미지 작음 ↔ glibc 호환성 문제 가능
Rolling Update: 무중단 ↔ 구/신 버전 공존 시 호환 필요
Blue-Green: 즉시 롤백 ↔ 인프라 2배 비용
Canary: 리스크 최소 ↔ 구현/관리 복잡
모니터링 상세화: 장애 감지↑ ↔ 저장 비용↑ 노이즈↑
```

## 설명 흐름
1. **왜 써야 하는가**: "이것 없이 운영하면 이런 사고"
2. **비유로 직관 잡기**
3. **핵심 개념 설명** + 구조 다이어그램
4. **명령어/설정 파일 전체 예시** + "실행하면 이 결과"
5. **트레이드오프**: "이 설정의 비용은?"
6. **오해하기 쉬운 부분**:
```
"Docker = VM" → 컨테이너는 커널 공유. VM은 게스트 OS 통째로
"Docker Compose = 프로덕션 도구" → 단일 호스트만. 프로덕션은 K8s
"CI/CD를 구축하면 끝" → 파이프라인도 유지보수 필요. 느려지면 캐시/병렬화
"모니터링 = 로그 보기" → 메트릭(무엇이) + 로그(왜) + 트레이스(어디서). 3대 축
"Prometheus가 데이터를 푸시한다" → Pull 방식(타겟의 /metrics를 주기적 스크래핑)
```
7. **확인 질문**: 사용자 답변 → 피드백
```
Step 4: "이 Dockerfile의 레이어 캐시 비효율을 찾아보세요"
Step 5: "Docker Compose에서 depends_on만으로 충분한가?"
Step 10: "이 GitHub Actions에서 빌드가 느린 이유는?"
Step 15: "이 PromQL은 무엇을 측정하는가?"
Step 19: "응답이 느려졌다. 어떤 순서로 진단하겠는가?"
```
8. **정리 + 다음 안내**

## Step별 특이사항
- Docker Step(1~7): Dockerfile/Compose 작성 실습. PID 1 문제 + Graceful Shutdown
- CI/CD Step(8~12): GitHub Actions YAML 작성. 배포 전략(Rolling/Blue-Green/Canary) 비교
- 관찰성 Step(13~19): Prometheus PromQL + Grafana 대시보드. 비즈니스 메트릭 관점
- 장애 진단 Step(19): "응답이 느려졌다" → 메트릭→로그→트레이스 순서 연습
