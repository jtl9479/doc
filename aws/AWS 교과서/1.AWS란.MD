# AWS란

## 1.1 클라우드 컴퓨팅

### 1.1.1 클라우드 컴퓨팅이란

IT 자원을 구축하는 전통적인 방법 온프레미스 방법은 자체적인 공간과 자원을 이용하여
사용자가 직접 구축 및 운용하는 방식을 의미한다. 해당 방식은 사용자가 모든 것을 수행해야 하기 때문에
부담이 클 수밖에 없으며, 비용 또한 만만치 않다. 이러한 문제점을 고려하여 효율적인 IT 자원을 구축하는 방법인 클라우드 구축 방법이 떠오르고 있다.

클라우드 컴퓨팅은 인터넷을 통해 요구가 있을 때 즉시(온디맨드) IT 자원을 제공하며, 사용한 만큼
비용을 지불하는 서비스이다. 클라우드 단어 의미와 연결하여 생각하면, 인터넷 구간 어딘가에 구름 형태로 쌓여 실제 물리적인 자원은 보이지 않지만 IT 자원을 원하는 대로 가져다 사용할 수 있는 컴퓨팅 서비스를 의미한다.

> **핵심은 금액이 아니라 지출의 성격이다.**
> 온프레미스 = CapEx(선투자 후 감가상각), 클라우드 = OpEx(쓴 만큼 매달).
> 자원 확보도 수 주 → 수 분. 그래서 "클라우드는 싸다"보다 **"실패를 싸게 만든다"** 가 정확하다.

### 1.1.2 클라우드 컴퓨팅 이점

* 민첩성
```
클라우드를 통해 광범위한 기술에 쉽게 접근할 수 있어 거의 모든 것을 빠르고 혁신적으로 구축할 수 있다.
```
* 탄력성
```
기존 온프레미스 환경처럼 향후 비즈니스 확장을 고려한 IT자원을 사전에 과하게 구성할 필요가 없다.
필요한 만큼만 자원을 할당받아 사용하면 된다.

비즈니스 요구가 가변적인 상황에서 자원을 손쉽게 확장하거나 축소하여 탄력적으로 운영이 가능하다.
```
* 비용 절감
```
클라우드 컴퓨팅은 Pay Per Use로, IT자원을 사용한 만큼 비용을 지불한다.
```

> **AWS 공식 목록은 6가지.** 위 3개 + ① 선행 비용을 가변 비용으로 ② 규모의 경제로 인한 절감 ③ 용량 추정 불필요 ④ 데이터센터 운영비 제거 ⑤ 몇 분 만에 전 세계 배포.
>
> **책임 공유 모델**: AWS는 "클라우드**의** 보안"(물리·하드웨어·가상화), 사용자는 "클라우드**에서의** 보안"(OS 패치·IAM·보안그룹·암호화). 관리가 사라지는 게 아니라 **형태만 바뀐다.**

### 1.1.3 클라우드 컴퓨팅 서비스 유형

클라우드 사용자가 어느 영역까지 관리하는지, 반대로 클라우드 공급자가 어느 영역까지 관리하는지에 따라 유형을 분류한다.

* IaaS (Infrastructure as a Service)
```
인프라를 제공하는 클라우드 서비스 유형을 의미한다.
인프라에는 서버, 네트워크, 스토리지 등 하드웨어 영역과 가상화 기능이 해당된다.

클라우드 공급자는 인프라 영역을 관리하고 서비스 제공
클라우드 사용자는 나머지 영역(os, 미들웨어, 런타임, 데이터, 애플리케이션)을 직접 관리하는 구조
```
* PaaS (Platform as a Service)
```
플랫폼 형태로 제공되는 클라우드 서비스 유형을 의미한다.
클라우드 공급자가 자체적으로 구축한 플랫폼을 제공하며, 클라우드 사용자는 별도의 플랫폼을 구축하지 않고 애플리케이션을 개발 및 관리만 한다.

클라우드 사용자는 애플리케이션 영역(데이터, 애플리케이션)만 담당하고
클라우드 공급자가 나머지 영역(하드웨어, 가상화, 운영체제, 미들웨어, 런타임)을 관리 및 제공한다
```
* SaaS (Software as a Service)
```
소프트웨어 영역까지 클라우드 공급자가 관리 및 제공하는 유형을 의미한다.

클라우드 사용자는 별도의 애플리케이션을 설치하거나 운영할 필요 없이 클라우드 서비스를 제공받는다.

클라우드 공급자가 모든 것을 제공한다.
클라우드 사용자는 서비스만을 받는다.
```

#### 7개 계층 용어

> **Q.** 서버/스토리지/네트워킹, 가상화, 운영체제, 미들웨어, 런타임, 데이터, 애플리케이션 각각 단어가 무엇인지 간단한 설명 및 IaaS, PaaS, SaaS 예를 보여달라.

아래에서 위로 쌓아 올리는 순서다.

| 계층 | 설명 |
|------|------|
| 서버/스토리지/네트워킹 | 물리 장비. CPU·메모리 / 디스크 / 스위치·회선 |
| 가상화 | 물리 서버 1대를 VM 여러 대로 쪼개는 기술 (하이퍼바이저) |
| 운영체제 | VM 위에서 프로그램을 실행시키는 소프트웨어 (Linux, Windows Server) |
| 미들웨어 | OS와 앱 **사이**의 공통 소프트웨어 (Tomcat, Oracle, Kafka) |
| 런타임 | 코드가 실행되는 환경 (JVM, Node.js) |
| 데이터 | DB 레코드, 업로드 파일, 로그 |
| 애플리케이션 | 비즈니스 로직 (ERP 소스) |

> 미들웨어 vs 런타임: **런타임 = 내 코드를 돌려주는 엔진**(JVM 없으면 실행 불가), **미들웨어 = 내 코드가 가져다 쓰는 공통 소프트웨어**(Tomcat, Oracle).

#### 유형별 예시와 관리 경계

| 유형 | AWS | 일반 | 사용자가 관리하는 영역 |
|------|-----|------|---------------------|
| IaaS | EC2, S3, VPC | Azure VM, GCP Compute Engine | **OS 위 전부** (OS·미들웨어·런타임·데이터·앱) |
| PaaS | Elastic Beanstalk, RDS, Lambda | Heroku, App Engine | **데이터·앱만** |
| SaaS | WorkMail, QuickSight | Gmail, Slack, Notion | **없음** (데이터 입력만) |

> 트레이드오프는 하나다. **IaaS로 갈수록 통제권↑ 관리 부담↑, SaaS로 갈수록 편함↑ 통제권↓ 종속성↑.**
> Spring Boot 앱이면 EC2 → ECS/EKS → Fargate → Lambda 순으로 관리 부담이 줄고 제약이 는다.

### 1.1.4 클라우드 구축 모델
클라우드 서비스를 위한 자원의 소유권, 위치, 주체에 따라 퍼블릭 클라우드, 프라이빗 클라우드, 하이브리드 클라우드 구축 모델로 분류된다.

* 퍼블릭 클라우드 구축 모델(public cloud)
```
사용자가 클라우드 자원을 소유하지 않으며, 자체적인 공간에 위치하지 않고 클라우드 공급자가 서비스를 제공하는 환경이다.

퍼블릭 클라우드는 서비스의 주체가 클라우드 공급자이다. 대표적인 퍼블릭 클라우드 공급자는 아마존 웹 서비스, 구글 클라우드 플랫폼, 마이크로소프트 애저 등이 있다.

퍼블릭 클라우드는 온디맨드 형태로 사용자 요구에 따라 클라우드 공급자에게서 IT 자원을 할당받아 확장성이 우수하다.
```

* 프라이빗 클라우드 구축 모델
```
프라이빗 클라우드(private cloud)는 사용자 전용 클라우드 환경으로, 자원 소유권은 사용자한테 있고 프라이빗 클라우드는 온프레미스 환경에 구축되어 서비스를 받는 환경이다.

프라이빗 클라우드는 서비스 주체가 사용자이다.
프라이빗 클라우드는 온프레미스 환경에 구축되어 보안이 우수하지만, 퍼블릭 클라우드보다 서비스 확장성은 떨어진다.
```
* 하이브리드 클라우드 구축 모델
```
하이브리드 클라우드(hybrid cloud)는 다수의 클라우드 시스템이 혼합되어 있는 형태로 클라우드 시스템이 서로 연결된 모델이다.
```

#### 언제 쓰는가

> **Q.** 각 구축 모델별로 언제 사용해야 하며, 예시를 들어달라.

| 모델 | 쓰는 조건 | 예시 |
|------|----------|------|
| **퍼블릭** | 트래픽 변동이 크다 / 초기 자본이 없다 / 빠르게 검증 / 글로벌 | 스타트업, 이커머스 이벤트, 게임 런칭 |
| **프라이빗** | 규제상 외부 반출 금지 / 부하가 일정하고 장기 운영 / 초저지연 | 은행 계정계, 병원 EMR, 공장 MES |
| **하이브리드** | 민감 데이터만 내부 / 피크만 외부로(버스팅) / 단계적 전환 / DR | 유통사(개인정보는 사내, 웹은 AWS), 수강신청 |

> **판단 순서:** 규제가 외부 저장을 막는가 → 예면 프라이빗 / 부하가 24시간 일정하고 3년 이상인가 → 예면 비용 비교 / 아니면 퍼블릭.

> **주의 2가지**
> - **프라이빗 클라우드 ≠ 온프레미스.** 온프레미스는 *위치*, 프라이빗 클라우드는 *운영 방식*(셀프서비스·자동화·사용량 계측). 외부 DC에 두는 호스티드 프라이빗도 있다.
> - **하이브리드 ≠ 멀티 클라우드.** 하이브리드는 퍼블릭+프라이빗, 멀티 클라우드는 퍼블릭 여러 개(AWS+GCP).

### ⚠️ 1.1 오해

- **"클라우드는 항상 싸다"** → 변동성이 클 때만. 24시간 일정 부하는 자체 보유가 쌀 수 있고, 방치하면 더 비싸다.
- **"클라우드는 무조건 안전하다"** → 유출 사고 대다수는 사용자 설정 실수(S3 퍼블릭 공개, 과도한 IAM 권한).
- **"프라이빗은 보안이 우수하다"** → 위치가 보안을 보장하지 않는다. 유리한 건 *규제 대응과 통제권*.

## 1.2 AWS 서비스

### 1.2.1 AWS 소개
```
AWS는 아마존의 자회사로 다양한 퍼블릭 클라우드 컴퓨팅 서비스를 제공한다.
직접 장비를 구매하거나 임대하지 않고 필요한 만큼 자원을 공급하는 클라우드 컴퓨팅 서비스를 제공한다.
AWS는 37개의 리전과 117개의 가용 영역을 운영한다.  ← 책 집필 시점 기준
```

> **글로벌 인프라 3계층**
> - **리전(Region)**: 지리적으로 분리된 독립 구역. 서울 = `ap-northeast-2`
> - **가용 영역(AZ)**: 리전 내부의 물리적으로 분리된 데이터센터 묶음. 리전당 보통 3개 이상 (서울 4개)
> - **엣지 로케이션**: CloudFront가 쓰는 캐시 거점. 전 세계 수백 개
>
> AZ끼리는 저지연 전용 회선으로 연결돼 있어 **여러 AZ에 나눠 배포해도 성능 손해가 거의 없다.** 뒤에 나올 Multi-AZ·ELB·Auto Scaling이 전부 여기서 출발한다.
>
> 리전·AZ 개수는 매년 늘어나므로 **"○○년 기준"을 붙여 인용**할 것. 숫자보다 "30개 이상 리전, 리전당 3개 이상 AZ" 구조가 중요하다.

### 1.2.2 AWS 서비스 라인업
```
해당 책에서는 23개의 범주 중에서 컴퓨팅, 네트워킹, 스토리지, 데이터베이스, 보안자격 5개에 대해 알려준다.
```

* 컴퓨팅
```
AWS 컴퓨팅은 퍼블릭 클라우드의 서버 자원에 대해 가상 머신을 생성하고, 비용 및 용량을 관리할 수 있는 서비스들로 구성되어 있다.

대표적 서비스로 Amazon Elastic Compute Cloud(Amazon EC2)가 있으며 해당 서비스 덕분에
클라우드에서 안전하고 크기 조정이 가능한(resizable) 컴퓨팅 자원을 제공받을 수 있다. 2장, 9장에서 설명한다.
```
* AWS 네트워킹 및 콘텐츠 전송
```
AWS 네트워킹 및 콘텐츠 전송은 퍼블릭 클라우드에 생성한 다양한 자원이 통신할 수 있도록 지원하는 네트워크 서비스들로 구성되어 있다.

대표적 서비스로 Amazon Virtual Private Cloud(VPC), Amazon CloudFront, Amazon Route 53 등이 있으며 해당 서비스로 생성된 클라우드 자원의 통신 환경을 구성할 수 있다.

3장 AWS 네트워킹 서비스, 4장 부하 분산 서비스, 7장 AWS 고급 네트워킹 서비스에서 설명한다.
```

* AWS 스토리지
```
AWS 스토리지는 퍼블릭 클라우드에 안정적이고 확장성이 높은 스토리지 서비스들로 구성되어 있다.

Amazon Simple Storage Service(S3), Amazon Elastic File System(EFS), Amazon Elastic Block Store(EBS) 등이 있으며 해당 서비스에서 클라우드에서 빠르고 안정적으로 데이터를 저장할 수 있다.
```

* AWS 데이터베이스
```
AWS 데이터베이스는 데이터베이스 목적과 용도에 따라 퍼블릭 클라우드에서 다양한 데이터베이스 엔진을 제공하는 완전 관리형 서비스이다. 대표적으로는 Amazon Relational Database Service(RDS) 등이 있으며 DB 유형에 따라 선택해서 사용할 수 있다. 6장 AWS 데이터베이스 서비스에서 설명한다.
```

* AWS 보안 자격 증명 및 규격 준수
```
AWS 보안 자격 증명 및 규격 준수는 퍼블릭 클라우드 자원과 사용자 자격 증명 및 접근 관리, 데이터·네트워크·애플리케이션 보호와 위협 탐지 및 모니터링을 위한 서비스로 구성되어 있다.
대표적으로는 AWS Identity & Access Management(IAM)가 있으며 8장 AWS IAM 서비스에서 설명한다.
```

#### 범주별로 언제 쓰는가

| 범주 | 온프레미스에서는 | 언제 쓰나 (ERP 기준) |
|------|-----------------|---------------------|
| **컴퓨팅** | 서버 구매 → 랙 장착 → OS 설치 | WAS 상시 구동 → EC2 / 월말 배치 → Spot·Batch / 첨부파일 검사 → Lambda |
| **네트워킹** | 스위치·L4·방화벽 정책 | 사설망 → VPC / 부하 분산 → ELB / 도메인 → Route 53 / 사내망 연결 → VPN·Direct Connect |
| **스토리지** | NAS·SAN·백업 테이프 | OS·DB 파일 → EBS / 첨부파일 → S3 / 여러 WAS 공유 → EFS / 장기 보존 → Glacier |
| **데이터베이스** | Oracle 설치·패치·이중화 | 기존 DB 이전 → RDS / 캐시 → ElastiCache / 로그 대용량 → DynamoDB |
| **보안·자격 증명** | AD/LDAP, 권한 대장 | 사람 권한 → IAM 사용자·그룹 / **서비스 권한 → IAM 역할** / 비밀번호 → Secrets Manager / 감사 → CloudTrail |

> **가장 중요한 실무 원칙:** 액세스 키를 코드·깃허브에 올리지 말 것. EC2·Lambda에는 반드시 **IAM 역할**을 붙인다.

> **접두어 규칙:** 혼자서 완결된 서비스는 `Amazon`(EC2, S3, RDS, VPC), 다른 서비스를 보조·관리하는 도구는 `AWS`(IAM, Lambda, CLI, CloudFormation). 절대적이진 않지만 문서 읽을 때 유용하다.

#### 스토리지 3형제 — S3 / EBS / EFS

가장 많이 나오는 비교다.

| | S3 | EBS | EFS |
|---|---|---|---|
| 유형 | 객체 | 블록 | 파일 |
| 비유 | 창고 | 노트북에 꽂은 SSD | 팀 공유 드라이브 |
| 동시 연결 | 무제한 (HTTP) | 원칙적으로 EC2 1대 | 여러 대 동시 마운트 |
| 부분 수정 | 불가 (통째로 교체) | 가능 | 가능 |
| 용도 | 첨부파일·로그·백업 | OS 디스크, DB 파일 | 여러 서버가 공유하는 파일 |

```
통째로 올리고 내리기만 → S3
서버 1대가 디스크처럼   → EBS
여러 서버가 동시에      → EFS
```

### ⚠️ 1.2 오해

- **"리전 = 데이터센터 1개"** → 리전은 여러 AZ의 묶음, AZ는 다시 데이터센터 여러 개.
- **"EC2를 정지하면 비용 0"** → 인스턴스 요금만 멈춘다. EBS 볼륨·Elastic IP는 계속 과금.
- **"RDS도 DB 서버니까 뭐든 할 수 있다"** → OS 접근 불가. 설정은 파라미터 그룹으로만.
- **"IAM은 유료"** → IAM 자체는 무료.
