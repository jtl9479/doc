**분기 배정**: 3분기 (2026.10 ~ 2026.12)

### Step 1. MSA 개요 — 모놀리스 vs MSA, 왜 MSA인가

| 학습 항목 | 학습 목표 |
|----------|----------|
| 모놀리스란 | 하나의 배포 단위에 모든 기능이 포함된 구조. 하나의 코드베이스, 하나의 DB, 하나의 배포. 장점(단순, 디버깅 쉬움, 트랜잭션 용이)을 설명 가능. |
| MSA란 | 서비스를 비즈니스 기능 단위로 분리하여 독립적으로 개발/배포/확장하는 아키텍처. 각 서비스가 자체 DB를 가짐(Database per Service). |
| 왜 MSA인가 | 모놀리스의 한계(코드베이스 거대화 → 빌드/배포 느림, 한 기능 변경이 전체에 영향, 특정 기능만 확장 불가, 기술 스택 고정)가 MSA 도입 동기임을 설명 가능. |
| MSA의 핵심 특성 | ① 서비스별 독립 배포, ② 서비스별 독립 DB, ③ 서비스 간 네트워크 통신(HTTP/메시지), ④ 팀별 서비스 소유(Conway's Law)를 설명 가능. |
| 모놀리스 → 모듈러 모놀리스 → MSA | 단계적 전환 경로. 처음부터 MSA가 아니라 모듈러 모놀리스에서 시작하는 것이 현실적인 이유를 설명 가능. (DDD 학습 Step 13과 연계) |

### Step 2. MSA의 장단점과 도입 판단 기준

| 학습 항목 | 학습 목표 |
|----------|----------|
| 장점 | 독립 배포(다른 서비스 영향 없이), 독립 확장(트래픽 많은 서비스만), 기술 다양성(서비스별 다른 언어/DB), 팀 자율성, 장애 격리(한 서비스 장애가 전체 중단 아님). |
| 단점 | 분산 시스템 복잡성(네트워크 장애, 데이터 일관성), 운영 비용 증가(서비스별 모니터링/배포/로깅), 디버깅 어려움(분산 추적 필요), 서비스 간 통신 오버헤드, 데이터 정합성 보장 어려움. |
| MSA 도입 판단 기준 | "모놀리스가 감당 못 하는 구체적 문제가 있는가?" → 있으면 MSA 검토, 없으면 모놀리스 유지. 팀 규모(2-pizza rule), 배포 빈도, 확장 요구, 도메인 복잡도에 따른 판단 기준을 설명 가능. |
| "MSA가 답이 아닌 경우" | 팀이 작을 때(3~5명), 도메인이 단순할 때, 운영 인프라(K8s, 모니터링)가 갖춰지지 않았을 때 MSA는 오히려 비용만 증가함을 설명 가능. |
| ERP에 MSA가 적합한가 | ERP는 모듈 간 데이터 정합성이 매우 중요(수주→재고→매출→회계). MSA로 분리하면 정합성 보장이 극도로 어려워짐. **모듈러 모놀리스가 더 현실적**인 이유를 본인 경험으로 설명 가능. |

### Step 3. 서비스 간 통신 — 동기(REST/gRPC) vs 비동기(메시지)

| 학습 항목 | 학습 목표 |
|----------|----------|
| 동기 통신 (REST) | HTTP 기반, 요청-응답. 단순하고 직관적. 단점: 호출 대상 서비스 장애 시 호출자도 영향(결합도 높음), 지연 누적(서비스 체인). |
| 동기 통신 (gRPC) | Protocol Buffers 기반, HTTP/2, 바이너리 직렬화. REST 대비 빠르고 스키마 강제. 서비스 간 내부 통신에 적합. 개념 수준 설명 가능. |
| 비동기 통신 (메시지) | Kafka/RabbitMQ/SQS를 통한 이벤트 기반 통신. 서비스 간 결합도 낮음(발행자는 소비자를 모름). 단점: 최종 일관성(Eventual Consistency), 디버깅 어려움, 메시지 순서/중복 처리 필요. |
| 동기 vs 비동기 선택 기준 | 즉시 응답 필요 → 동기, 결합도 감소 + 처리량 중요 → 비동기. 실무에서 혼합 사용(조회는 동기, 상태 변경은 비동기)이 일반적임을 설명 가능. |
| 요청-응답 vs 이벤트 기반 | 요청-응답: "주문 서비스 → 재고 서비스: 재고 있어?" (동기). 이벤트 기반: "주문 서비스 → 이벤트 발행: 주문 생성됨 → 재고 서비스가 이벤트 소비" (비동기). 차이를 시나리오로 설명 가능. |

### Step 4. API Gateway 패턴

| 학습 항목 | 학습 목표 |
|----------|----------|
| API Gateway란 | 클라이언트와 내부 서비스 사이의 단일 진입점. 라우팅, 인증, 속도 제한, 로깅, 프로토콜 변환 등을 처리. |
| 왜 필요한가 | 클라이언트가 여러 서비스를 직접 호출하면: URL 관리 어려움, 인증 로직 중복, 서비스 위치 노출. Gateway가 이를 통합 관리하는 이유를 설명 가능. |
| BFF (Backend for Frontend) | 프론트엔드(웹, 모바일) 유형별로 별도 Gateway를 두는 패턴. 각 클라이언트에 최적화된 API를 제공하는 이유를 설명 가능. |
| 구현체 | Spring Cloud Gateway, Kong, AWS API Gateway, Nginx의 존재와 차이를 개념 수준 설명 가능. |
| Gateway의 위험 | Gateway가 단일 장애점(SPOF)이 되지 않도록 이중화해야 하는 이유. Gateway에 비즈니스 로직을 넣으면 안 되는 이유(관심사 분리)를 설명 가능. |
| K8s에서의 API Gateway | K8s Ingress Controller(Nginx, AWS ALB)가 API Gateway 역할을 부분적으로 대체 가능(라우팅, TLS). 다만 인증/속도 제한 등 고급 기능은 별도 Gateway(Kong, Spring Cloud Gateway) 또는 Service Mesh(Istio)가 필요한 이유를 설명 가능. 이론 패턴(API Gateway)과 K8s 실체(Ingress)의 매핑을 설명 가능. |

### Step 5. 서비스 디스커버리

| 학습 항목 | 학습 목표 |
|----------|----------|
| 서비스 디스커버리란 | MSA에서 서비스 인스턴스의 위치(IP/포트)가 동적으로 변하므로(스케일링, 재시작), 호출자가 대상 서비스를 찾는 메커니즘. |
| 클라이언트 사이드 디스커버리 | 클라이언트가 서비스 레지스트리(Eureka 등)에서 위치를 조회 → 직접 로드밸런싱. Spring Cloud + Eureka 조합. |
| 서버 사이드 디스커버리 | 로드밸런서(K8s Service, AWS ELB)가 대신 라우팅. 클라이언트는 로드밸런서 주소만 앎. K8s에서는 Service + DNS가 자동 디스커버리를 제공하는 이유를 설명 가능. |
| K8s 환경에서 | K8s Service가 서비스 디스커버리를 내장하므로 별도 Eureka가 불필요한 이유를 설명 가능. K8s Service(ClusterIP) + DNS(서비스명으로 접근) = 서버 사이드 디스커버리 자동 제공. K8s CoreDNS가 service-name.namespace.svc.cluster.local로 해석하는 과정을 설명 가능. "K8s를 쓰면 Eureka/Consul이 필요 없다"는 판단 근거를 설명 가능. |

### Step 6. Saga 패턴 — Orchestration vs Choreography

| 학습 항목 | 학습 목표 |
|----------|----------|
| 분산 트랜잭션의 문제 | MSA에서 여러 서비스에 걸친 트랜잭션을 하나의 DB 트랜잭션으로 처리 불가(서비스별 DB). 2PC(Two-Phase Commit)의 문제점(블로킹, 코디네이터 SPOF, 성능 저하)을 설명 가능. |
| Saga란 | 각 서비스가 로컬 트랜잭션을 실행하고, 실패 시 이전 서비스에 **보상 트랜잭션(Compensating Transaction)**을 실행하여 롤백하는 패턴. |
| Choreography (안무) | 이벤트 기반. 각 서비스가 이벤트를 발행하면 다음 서비스가 소비 → 처리 → 이벤트 발행. 중앙 조율자 없음. 장점(결합도 낮음, 단순). 단점(전체 흐름 파악 어려움, 서비스 많아지면 복잡). |
| Orchestration (지휘) | 중앙 Orchestrator(Saga Manager)가 각 서비스에 명령을 보내고 응답을 받아 흐름 제어. 장점(전체 흐름 명확, 디버깅 쉬움). 단점(Orchestrator가 SPOF/병목 가능, 결합도 약간 높음). |
| 보상 트랜잭션 | "주문 생성 → 결제 성공 → 재고 차감 실패" 시: 결제 취소(보상) → 주문 취소(보상) 역순 실행. 보상이 항상 가능하지 않은 경우(이미 발송된 이메일)의 대응을 설명 가능. |
| ERP 연결 | "수주 확정 → 재고 예약 → 출고 지시" 흐름이 Saga와 동일 구조. 출고 실패 시 재고 예약 해제 + 수주 상태 복원이 보상 트랜잭션임을 설명 가능. |
| Saga vs 2PC 선택 | MSA에서는 Saga가 사실상 표준. 2PC는 단일 DB 또는 XA 트랜잭션에서만 사용. "왜 MSA에서 2PC를 쓰지 않는가"를 설명 가능. |

### Step 7. Outbox 패턴 — 트랜잭션 + 이벤트 발행 보장

| 학습 항목 | 학습 목표 |
|----------|----------|
| 이중 쓰기 문제 | DB 저장 + Kafka 전송을 동시에 해야 하는데, DB는 성공하고 Kafka 전송은 실패하면 데이터 불일치. 둘을 하나의 트랜잭션으로 묶을 수 없는 이유를 설명 가능. |
| Outbox 패턴 | DB에 비즈니스 데이터와 **Outbox 테이블**(이벤트 메시지)을 같은 트랜잭션으로 저장 → 별도 프로세스(Polling 또는 CDC)가 Outbox를 읽어 Kafka로 전송. DB 트랜잭션 내에서 이벤트 발행을 보장하는 원리를 설명 가능. |
| Polling 방식 | 주기적으로 Outbox 테이블에서 미전송 이벤트를 조회 → Kafka 전송 → 전송 완료 표시. 단순하지만 지연 발생. |
| CDC 방식 | Debezium 등으로 DB 변경 로그(Oracle Redo Log, MySQL Binlog)를 실시간 감지 → Kafka 전송. Polling보다 지연 적음. 개념 수준 설명 가능. |
| 멱등성과 연계 | Outbox 전송 시 중복 전송 가능(Polling 재시도). 컨슈머 측에서 멱등성을 보장해야 하는 이유를 설명 가능. (Kafka 학습 Step 9와 연계) |

### Step 8. CQRS — 읽기/쓰기 분리

| 학습 항목 | 학습 목표 |
|----------|----------|
| CQRS란 | Command(쓰기)와 Query(읽기)의 모델/저장소를 분리하는 패턴. 쓰기는 정규화된 도메인 모델, 읽기는 비정규화된 뷰. |
| 왜 필요한가 | 읽기와 쓰기의 요구사항이 다른 경우(읽기: 다양한 조회 조건, 빠른 응답. 쓰기: 비즈니스 규칙 검증, 트랜잭션). 하나의 모델로 양쪽을 만족시키기 어려운 이유를 설명 가능. |
| CQRS 구현 | 쓰기: Command → Domain Model → DB. 읽기: DB 변경 → 이벤트 → 읽기 전용 뷰(View DB) 갱신 → Query → View DB. |
| CQRS 장점 | 읽기/쓰기 독립 확장(읽기 서버만 증설), 읽기 최적화(비정규화 뷰), 쓰기 최적화(도메인 모델 집중). |
| CQRS 단점 | 최종 일관성(읽기 뷰 갱신 지연), 복잡성 증가(두 개 모델 관리), 이벤트 처리 실패 대응 필요. |
| CQRS가 필요한 경우와 불필요한 경우 | 읽기/쓰기 비율이 극단적(읽기 >> 쓰기), 읽기 성능이 병목, 복잡한 조회 요구 → CQRS 적합. 단순 CRUD → 불필요(over-engineering). 판단 기준을 설명 가능. |
| 데이터 중복 vs API 조인 (심화) | "다른 서비스의 정보가 필요할 때 어떻게 하는가?"의 두 가지 전략: ① **API 조인**(실시간 호출): 항상 최신 데이터, 하지만 Latency 증가 + 호출 대상 장애 시 영향. ② **데이터 복사(로컬 캐시/뷰)**:이벤트로 동기화, 빠른 조회, 하지만 최종 일관성 + 데이터 관리 복잡. 트레이드오프를 설명 가능. ERP 예: 수주 서비스가 거래처 이름을 표시할 때 → 거래처 서비스에 매번 API 호출(최신, 느림) vs 수주 DB에 거래처명 복사(빠름, 변경 시 동기화 필요). 비즈니스 요구(실시간 정확도 vs 조회 성능)에 따라 판단 가능. |

### Step 9. Event Sourcing — 이벤트 기반 상태 관리

| 학습 항목 | 학습 목표 |
|----------|----------|
| (DDD 학습 Step 14와 동일 내용 연계) | DDD에서 학습한 이벤트 소싱 개념을 MSA 관점에서 복습. 서비스 간 이벤트 전파와 상태 복원의 관계를 설명 가능. |
| MSA에서의 이벤트 소싱 | 각 서비스가 이벤트 스토어에 이벤트를 저장 → 다른 서비스가 이벤트를 소비하여 자체 뷰를 구축. CQRS와 자연스럽게 결합되는 이유를 설명 가능. |
| 이벤트 소싱 + Saga | 이벤트 소싱으로 상태 변경을 기록하면 보상 트랜잭션이 "역이벤트 발행"으로 단순화되는 이유를 설명 가능. |

### Step 10. Circuit Breaker — 장애 전파 방지

| 학습 항목 | 학습 목표 |
|----------|----------|
| 장애 전파 (Cascading Failure) | 서비스 A → B → C 호출 체인에서 C가 느려지면 B가 대기 → B의 스레드 고갈 → A도 영향. 하나의 장애가 전체 시스템으로 전파되는 시나리오를 설명 가능. |
| Circuit Breaker란 | 전기 회로의 차단기 비유. 호출 실패가 임계치를 넘으면 회로를 "열어" 더 이상 호출하지 않고 즉시 실패 반환(Fail Fast). 장애 전파를 차단하는 원리를 설명 가능. |
| 상태 전이 | **Closed**(정상, 호출 통과) → 실패 임계치 초과 → **Open**(차단, 즉시 실패) → 일정 시간 후 → **Half-Open**(일부 호출 허용하여 테스트) → 성공하면 Closed / 실패하면 Open. 상태 전이를 그림으로 그릴 수 있음. |
| Resilience4j | Java용 경량 장애 대응 라이브러리. CircuitBreaker, Retry, RateLimiter, Bulkhead, TimeLimiter 모듈을 제공. Spring Boot 연동 방법을 설명 가능. |
| Resilience4j CircuitBreaker 설정 | failureRateThreshold(실패율 임계치), waitDurationInOpenState(Open 유지 시간), slidingWindowSize(측정 윈도우), permittedNumberOfCallsInHalfOpenState(Half-Open 시 허용 호출 수) 각 설정의 의미를 설명 가능. |
| Fallback | Circuit Breaker가 Open 상태일 때 대체 응답(캐시된 데이터, 기본값, 에러 메시지)을 반환하는 패턴을 설명 가능. |

---

### Step 11. 기타 장애 대응 패턴 — Retry, Timeout, Bulkhead, Rate Limiting

| 학습 항목 | 학습 목표 |
|----------|----------|
| Retry | 일시적 장애(네트워크 순단, 타임아웃)에 대한 재시도. 고정 간격, 지수 백오프(Exponential Backoff), 지터(Jitter) 전략의 차이를 설명 가능. 멱등하지 않은 연산에 Retry하면 안 되는 이유를 설명 가능. |
| Timeout | 무한 대기 방지. 응답을 기다리는 최대 시간 설정. 너무 짧으면(정상 요청 실패), 너무 길면(자원 고갈). 적절한 타임아웃 설정 기준을 설명 가능. |
| Bulkhead | 격벽 패턴. 서비스별/기능별로 스레드 풀/커넥션을 격리하여 하나의 장애가 전체 자원을 고갈시키지 않게 방지. 타이타닉호의 격벽 비유로 설명 가능. |
| Rate Limiting | 단위 시간당 요청 수를 제한. DDoS 방어, 서비스 보호. Token Bucket, Sliding Window 알고리즘을 개념 수준 설명 가능. |
| 패턴 조합 | Circuit Breaker + Retry + Timeout을 함께 사용하는 실전 패턴. "Retry는 Circuit Breaker 안에" 원칙(Open 상태에서 Retry하면 무의미)을 설명 가능. |

### Step 12. 분산 추적 + 로깅 — MSA 환경 관찰성

| 학습 항목 | 학습 목표 |
|----------|----------|
| MSA에서 디버깅이 어려운 이유 | 하나의 요청이 여러 서비스를 거치므로 "어느 서비스에서 문제가 발생했는가"를 파악하려면 분산 추적이 필수. 모놀리스와의 차이를 설명 가능. |
| Trace ID / Span ID | 요청에 고유 Trace ID를 부여하고, 서비스 간 전파하여 전체 경로를 추적. 각 서비스 내 작업은 Span으로 기록. (관찰성 학습 Step 18과 연계) |
| 중앙 집중 로깅 | 각 서비스 로그를 하나의 시스템(ELK, Loki)에 수집. Trace ID로 검색하여 요청 흐름을 추적하는 패턴을 설명 가능. |
| 분산 환경 장애 진단 순서 | 알림(에러율 증가) → Grafana(어떤 서비스?) → 분산 추적(어디서 느림?) → 로그(왜?) 순서를 설명 가능. |

### Step 13. MSA 실전 — ERP 도메인에 MSA 적용 검토

| 학습 항목 | 학습 목표 |
|----------|----------|
| ERP를 MSA로 분리한다면 | 수주(SM), 구매(PM), 생산(PD), 재고(IS), 회계(AC)를 독립 서비스로 분리하는 시나리오. Bounded Context(DDD)가 서비스 경계가 됨을 설명 가능. |
| 분리 시 정합성 문제 | "수주 → 재고 차감 → 매출 반영"이 분산 트랜잭션이 됨. Saga로 처리 시 보상 트랜잭션(재고 복원, 매출 취소)의 복잡성을 설명 가능. |
| "ERP에 MSA가 필요한가?" 판단 | 데이터 정합성 요구가 매우 높은 ERP에서 MSA의 최종 일관성(Eventual Consistency)은 위험. **모듈러 모놀리스 → 필요한 부분만 점진적 분리**가 현실적인 이유를 본인 경험으로 설명 가능. |
| 분리 적합한 후보 | 알림, 로깅, 파일 관리 등 핵심 도메인과 결합도가 낮은 서비스부터 분리하는 전략을 설명 가능. |

---

### Step 14. MSA 안티패턴 — 분산 모놀리스, 잘못된 서비스 분리

| 학습 항목 | 학습 목표 |
|----------|----------|
| 분산 모놀리스 (Distributed Monolith) | 서비스를 분리했지만 동기 호출 체인으로 강하게 결합 → 모놀리스의 단점(변경 전파) + MSA의 단점(분산 복잡성)을 동시에 가지는 최악의 상태. 식별 기준을 설명 가능. |
| 너무 작은 서비스 (Nano Service) | CRUD 하나당 서비스 1개 → 운영 비용 폭증, 서비스 간 통신 오버헤드. "서비스는 비즈니스 기능 단위로 나눈다"는 원칙을 설명 가능. |
| 공유 DB | 여러 서비스가 같은 DB를 직접 접근 → 서비스 독립성 상실, 스키마 변경이 다른 서비스에 영향. Database per Service 원칙이 중요한 이유를 설명 가능. |
| 동기 호출 지옥 | 모든 서비스 간 통신이 동기(REST) → 장애 전파, 지연 누적. 비동기 이벤트로 결합도를 낮춰야 하는 경우를 판단 가능. |
| MSA를 위한 MSA | 비즈니스적 필요 없이 "MSA가 트렌드니까" 도입 → 복잡성만 증가. "MSA가 필요한가?"를 먼저 묻는 것이 시니어의 역할임을 설명 가능. |

### Step 15. 모놀리스 탈출 전략 — Strangler Fig 패턴

| 학습 항목 | 학습 목표 |
|----------|----------|
| Strangler Fig 패턴이란 | 모놀리스를 한 번에 MSA로 전환하지 않고, **새 기능은 새 서비스로 개발 + 기존 기능을 점진적으로 추출**하여 모놀리스를 서서히 교살(strangle)하는 전략. 교살자 무화과나무(Strangler Fig)의 비유를 설명 가능. |
| 전환 단계 | ① 모놀리스 앞에 프록시/라우터 배치 → ② 새 기능은 새 서비스로 개발, 프록시가 라우팅 → ③ 기존 기능을 하나씩 새 서비스로 추출 → ④ 모놀리스가 점점 작아짐 → ⑤ 최종적으로 모놀리스 제거. 각 단계를 설명 가능. |
| 왜 빅뱅 전환이 위험한가 | 전체 시스템을 한 번에 MSA로 재작성("Big Bang Rewrite")하면: 기간 폭증, 기존 버그 재현 실패, 비즈니스 중단 위험. Strangler Fig이 안전한 이유를 설명 가능. |
| ERP 적용 | 모놀리스 ERP에서 알림/로깅 같은 독립적 기능부터 분리 시작 → 핵심 도메인(수주/재고)은 마지막에 분리하는 전략. 본인 ERP 경험으로 "어디부터 자를 것인가" 설명 가능. |
| Anti-Corruption Layer (ACL) | 새 서비스가 모놀리스의 레거시 모델에 오염되지 않도록 변환 계층을 두는 패턴. DDD의 ACL과 동일 개념임을 연결하여 설명 가능. |

### Step 16. MSA 테스트 전략 — Contract Testing, Pact

| 학습 항목 | 학습 목표 |
|----------|----------|
| MSA 테스트의 어려움 | 단위 테스트는 서비스 내부만 검증. 서비스 간 통신(API 호환성)은 단위 테스트로 검증 불가. 통합 테스트는 모든 서비스를 동시에 띄워야 하므로 느리고 불안정. |
| 테스트 유형 | 단위 테스트(서비스 내부) → **계약 테스트(서비스 간 API 호환)** → 통합 테스트(전체 흐름) → E2E 테스트. 각 레벨의 역할과 비용을 설명 가능. |
| Consumer-Driven Contract (CDC) 테스트 | 소비자(Consumer)가 "나는 이 API에서 이런 요청을 보내고 이런 응답을 기대한다"는 계약(Contract)을 정의 → 제공자(Provider)가 이 계약을 만족하는지 검증. 서비스 A의 API 변경이 서비스 B를 깨뜨리지 않는지 자동 확인하는 원리를 설명 가능. |
| Pact | CDC 테스트의 대표 도구. Consumer 측에서 Pact 파일(계약) 생성 → Provider 측에서 Pact 파일로 검증하는 흐름을 개념 수준 설명 가능. |
| 계약 테스트 vs 통합 테스트 | 계약 테스트: 서비스 독립적으로 실행 가능, 빠름, API 호환성 검증. 통합 테스트: 전체 서비스 기동 필요, 느림, 실제 흐름 검증. 둘 다 필요하지만 계약 테스트가 MSA에서 특히 중요한 이유를 설명 가능. |
| Spring Cloud Contract | Spring 생태계의 CDC 테스트 도구. Pact와의 차이(Spring Cloud Contract: Groovy/YAML DSL, Provider 중심. Pact: 다중 언어, Consumer 중심)를 개념 수준 설명 가능. |
